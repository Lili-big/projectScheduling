# 功能规格：resource_path_continuity 候选路径无窗口化

> 当前实现校正（2026-07-09）：`resource_path_continuity` 已从当前目标项体系中移除；旧输入字段仅作为废弃兼容字段被忽略。当前目标项为 `control_node_late`、`makespan_and_soft_milestone`、`resource_idle`。第一阶段路径连续性、无窗口候选路径和资源路径罚分均为历史设计，不再建路径 circuit 或产生路径罚分；机械钻组聚合、组内升序和同组同资源保留为基础规则。

**功能目录/分支**：`021-resource-path-unbounded`

**创建日期**：2026-07-09

**状态**：草稿

**输入**：用户要求优化 `resource_path_continuity` 目标项：
1. 机械类的桩基（旋挖、冲击和回旋）仍然把同一结构物里的多根桩聚合成一个“钻机组节点”。
2. 移除候选路径窗口的约束。
3. 机械类旋挖钻组无论是否开启 `resource_path_continuity`，均按墩号聚合和排序；移除 `resource_path_continuity` 的资源顺序罚分机制。

## 来源与评审上下文（必填）

- **来源文档**：`AGENTS.md`、`agent.md`、`README.md`、`docs/排程算法当前实现交底文档_v1.2.md`、`specs/017-stage1-route-continuity/`。
- **评审结论**：用户已明确要求调整排程算法目标项。本变更会改变 CP-SAT 中机械钻机组路径候选生成、顺序罚分、诊断和不可行语义，按项目契约进入 Spec Kit。
- **使用的 Demo/代码事实**：
  - `backend/app/solver.py` 中 `MECHANICAL_DRILL_RESOURCE_TYPES` 当前包含 `rotary_drill`、`circulation_drill`、`impact_drill`。
  - `_build_drill_group_nodes()` 已将机械桩基按同资源组、同结构物、同构件类型、同施工工艺聚合为内部钻机组节点，输出结果仍展开原始桩基任务。
  - `_drill_group_stage1_transition_decision()` 当前将同幅可施工序列距离 `> 2`、跨幅真实墩号差 `> 1` 判为拒绝原因。
  - 历史实现中 `_build_drill_group_stage1_route_terms()` 只把允许的候选弧加入第一阶段路径 circuit，窗口外弧不进入模型；窗口导致不可行时会出现 `stage1_route_window_infeasible` 语义。
  - `backend/tests/test_scheduler.py` 中已有测试明确断言同幅窗口、跨幅窗口、拒绝弧计数和窗口不可行行为，本变更需要成组更新这些断言。
- **不在范围内**：
  - 不取消机械钻机组节点聚合，不改变组内桩基连续施工顺序。
  - 不新增前端目标项，不改变 `resource_path_continuity` 的开关和权重配置入口。
  - 不改变桩基任务生成、工期计算、工艺前后置、命名资源互斥、硬里程碑定义。
  - 不引入真实转场时间、道路距离、设备迁移费用或地图路径。
  - 不主动扩展到非机械钻资源的普通资源路径连续性，除非实现检查确认该逻辑仍影响机械钻机组主求解路径。
  - 不修改 `README.md`，不默认提交 git。

## 用户场景与测试（必填）

### 用户故事 1 - 保留机械桩基钻机组节点（优先级：P1）

计划工程师开启资源连续性目标时，希望同一结构物内多根机械桩基仍被视为一个粗粒度钻机组节点，避免目标项把同墩多根桩拆成多个可跳转路径节点。

**优先级理由**：这是用户明确要求保留的不变量。若聚合丢失，路径连续性会在同一结构物内部产生无意义跳转，排程粒度和既有诊断都会漂移。

**独立测试**：构造同一墩台多根旋挖、冲击或回旋桩基任务，开启 `resource_path_continuity` 后求解，验证钻机组数量按结构物聚合，结果任务仍保持原始桩基任务 ID。

**验收场景**：

1. **假设** 同一结构物内有 3 根旋挖桩基，**当** 系统构建资源路径节点，**则** 仅形成 1 个钻机组节点，组内包含 3 个原始桩基任务。
2. **假设** 同一项目内存在旋挖、冲击、回旋三类机械桩基资源，**当** 任务候选资源均属于对应机械类资源组，**则** 这些任务仍按同结构物聚合为钻机组节点。
3. **假设** 排程成功，**当** 用户查看任务结果，**则** 不出现 `drill_group:` 虚拟任务 ID，仍展示原始桩基任务。

---

### 用户故事 2 - 移除候选路径窗口硬过滤（优先级：P1）

计划工程师希望机械钻机组候选路径不再因为同幅跳得远或跨幅墩号差大被禁止，同时也不再通过 `resource_path_continuity` 对资源顺序施加罚分。远距离转移应允许进入模型，候选弧和距离信息只作为诊断保留。

**优先级理由**：这是本次优化的核心。现有窗口硬过滤会把部分可行路径排除在模型外，在固定资源精排中可能造成不可行、过长工期或早停质量差。

**独立测试**：构造同幅稀疏墩组 `[1, 2, 4, 7]` 和跨幅远距离墩组，开启 `resource_path_continuity` 后验证远距离候选弧被允许，窗口拒绝计数不再因距离增加。

**验收场景**：

1. **假设** 同幅可施工序列为 `[1, 2, 4, 7]`，**当** 计算 `1# -> 7#`，**则** 该转移允许进入候选路径，序列距离为 3，顺序罚分为 0。
2. **假设** 左幅 `1#` 与右幅 `4#` 都是同一资源可施工钻机组，**当** 计算跨幅转移，**则** 该转移允许进入候选路径，不再因真实墩号差为 3 被拒绝，顺序罚分为 0。
3. **假设** 两个节点缺少桥梁、幅别或墩号位置，**当** 构建候选路径，**则** 仍不得强行生成空间候选弧，并保留缺少位置诊断。

---

### 用户故事 3 - 诊断说明窗口已移除且不再罚分（优先级：P2）

计划工程师查看结果时，需要知道系统已经采用无窗口候选路径，同时仍能看到候选弧数量、距离和非距离原因的拒绝统计；但这些资源顺序信息不再进入罚分和加权目标。

**优先级理由**：移除硬窗口后，旧的 `same_side_window_exceeded`、`cross_side_gap_exceeded` 语义容易误导用户。诊断需要帮助用户理解“远距离被允许且不再按资源顺序罚分”。

**独立测试**：执行包含同幅远距离、跨幅远距离、位置缺失和目标关闭的样例，验证诊断中候选弧数、0 罚分、候选模式和拒绝原因符合新语义。

**验收场景**：

1. **假设** 同幅 4 个可施工钻机组均属于同一资源，**当** 第一阶段构建候选路径，**则** 有向候选弧数为 `4 * 3 = 12`，不会再只有窗口内的 10 条。
2. **假设** 远距离同幅或跨幅转移被允许，**当** 用户查看拒绝原因，**则** 不应看到它们被统计为窗口超限拒绝。
3. **假设** `resource_path_continuity` 关闭，**当** 用户查看诊断，**则** 第一阶段路径节点、候选弧和罚分为 0 或 `not_enabled`，不影响其他硬约束。

### 边界与异常场景

- 当 `resource_path_continuity` 关闭时，不构建第一阶段钻机组路径候选，不产生本功能新增罚分。
- 当不存在机械钻机组或每台机械钻资源可施工节点不足 2 个时，候选路径为未评估或无转移，罚分为 0。
- 当任务缺少可识别桥梁、幅别、墩号或结构类型时，不因为“无窗口化”而强行连边；仍按 `missing_location` 或同类诊断处理。
- 当两个钻机组不属于同桥梁、同资源组、同构件类型、同施工工艺时，仍不得互相连边。
- 当候选弧数量增加导致求解耗时上升时，不得重新引入固定距离窗口作为隐藏硬过滤；应通过验证结果说明性能风险，必要时再进入单独优化需求。
- 当旧字段 `stage1_route_sparse_same_side_window`、`stage1_route_sparse_cross_side_window` 仍保留时，只能作为历史兼容信息，不得表示当前仍按窗口拒绝候选弧。

## 需求（必填）

### 功能需求

- **FR-001**：系统必须继续识别 `rotary_drill`、`circulation_drill`、`impact_drill` 为机械钻资源类型。
- **FR-002**：系统必须继续把机械类桩基按同资源组、同结构物、同构件类型、同施工工艺聚合为一个钻机组节点；组内桩基按默认升序排列，组间按空间位置和墩号稳定排序。
- **FR-003**：系统必须保持组内原始桩基任务连续施工，并在最终 `ScheduleResult.tasks` 中输出原始任务，不输出虚拟钻机组任务。
- **FR-004**：当 `resource_path_continuity` 开启且机械钻机组存在时，系统必须为同一机械资源可施工的全部合法钻机组有序对生成候选转移，不得因同幅序列距离或跨幅墩号差超过旧窗口而拒绝。
- **FR-005**：系统必须继续拒绝自环之外的无效空间候选，包括缺少位置、桥梁不同、资源组不同、构件类型不同或施工工艺不同的转移。
- **FR-006**：同幅转移必须继续按当前资源实际可施工序列计算 `same_side_sequence_distance`，但不得据此产生顺序罚分。
- **FR-007**：跨幅转移必须允许任意有效 `cross_side_support_gap`，但不得据此产生顺序罚分。
- **FR-008**：`resource_path_continuity` 不得再把同幅距离、跨幅切换、跳墩或资源路径顺序作为软罚分加入目标函数；相关结果字段应返回 0 或未建模语义。
- **FR-009**：系统不得再把 `same_side_window_exceeded` 或 `cross_side_gap_exceeded` 作为距离超限拒绝原因；为兼容保留这些字段时，远距离有效转移不得增加这些计数。
- **FR-010**：系统不得再因为候选路径窗口导致 `stage1_route_window_infeasible`；第一阶段不可行只能来自真实 CP-SAT 约束、资源、前后置、里程碑或其他非距离窗口原因。
- **FR-011**：系统应在诊断中标明第一阶段候选路径采用无窗口模式，至少可通过结构化字段或明确的候选弧、拒绝计数体现。
- **FR-012**：系统必须更新或替换既有窗口相关自动化测试，覆盖机械桩基聚合、同幅远距离允许、跨幅远距离允许、目标关闭和诊断兼容。
- **FR-013**：系统必须复核固定资源当前方案和最少资源候选二次精排是否复用该路径逻辑；若某路径不再调用第一阶段钻机组路径，应在测试或注释中明确其不受本变更影响。

### 关键实体（涉及数据时填写）

- **机械钻机组节点**：同资源组、同结构物、同构件类型、同施工工艺下的机械桩基内部路径节点，包含一个或多个原始桩基任务。
- **无窗口候选转移**：同一机械资源可施工的两个合法钻机组节点之间的有向转移，不因同幅距离或跨幅墩号差被硬过滤。
- **同幅距离诊断**：同幅候选转移基于当前资源可施工序列计算的距离，仅用于解释和测试，不进入罚分。
- **跨幅距离诊断**：跨幅候选转移基于真实墩号差计算的距离，仅用于解释和测试，不进入罚分。
- **候选模式诊断**：说明第一阶段路径候选采用窗口过滤还是无窗口模式的结果解释信息。

## 成功标准（必填）

### 可衡量结果

- **SC-001**：同一结构物内 3 根机械桩基在第一阶段只形成 1 个钻机组节点，最终结果仍包含 3 个原始桩基任务 ID。
- **SC-002**：同幅可施工序列 `[1, 2, 4, 7]` 中，`1# -> 7#` 被允许，`same_side_sequence_distance = 3`，顺序罚分为 0。
- **SC-003**：左幅 `1# -> 右幅 4#` 被允许，`cross_side_support_gap = 3`，顺序罚分为 0。
- **SC-004**：同幅 4 个可施工钻机组、1 台机械钻资源时，第一阶段候选有向弧数为 12，`same_side_window_exceeded` 计数为 0。
- **SC-005**：左右幅共 12 个同范围钻机组、1 台机械钻资源时，第一阶段候选有向弧数等于 `12 * 11 = 132`，不再停留在旧窗口规则下的 68。
- **SC-006**：原“窗口不可行且不添加远距离兜底”的样例更新后不得再因 `stage1_route_window_infeasible` 失败；若其他硬约束允许，应能返回可行路径。
- **SC-007**：关闭 `resource_path_continuity` 后，第一阶段路径状态为 `not_enabled` 或等价未评估语义，节点数、候选弧数和罚分为 0。
- **SC-008**：`backend/tests/test_scheduler.py -k "stage1_route or mechanical_drill or drill_group or resource_path_continuity"` 中与本功能相关的测试全部通过，完整 `backend/tests/test_scheduler.py` 回归不出现与本变更相关的失败。

## 默认假设

- 默认“移除候选路径窗口约束”指移除机械钻机组第一阶段路径候选中的距离硬过滤；仍保留同桥梁、同资源组、同构件类型、同施工工艺、位置可识别等合法性过滤。
- 默认 `resource_path_continuity` 不再承担资源路径顺序优化；同幅距离和跨幅距离只保留为候选路径诊断，不再转化为软罚分。
- 默认本变更先覆盖 Python 后端主求解链路和后端测试；前端只在既有诊断展示需要适配新增可选字段时做小范围兼容。
- 默认不把候选弧数量增长本身视为失败，除非现有验证样例在项目既有时间限制内明显退化。
