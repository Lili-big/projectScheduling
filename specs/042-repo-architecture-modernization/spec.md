## 用户场景与测试（必填）

### 用户故事 1 - 快速理解项目与定位修改入口（优先级：P1）

新加入的产品、算法或研发人员从仓库入口文档出发，可以辨认主产品、辅助工具、业务文档、规格、交付物和本地运行产物的边界，并在有限时间内找到某个业务能力对应的前端入口、后端入口、核心领域逻辑和验证方式。

**优先级理由**：当前最直接的问题是目录与文档无法稳定表达项目真实边界；如果不能先建立共同地图，后续代码拆分只会形成新的混乱。

**独立测试**：选择“综合排程”“架梁专项”“计划管控”“AI 参数助手”四条典型能力，让未参与重构的维护者只使用 `README.md`、`agent.md` 和架构索引，在 10 分钟内分别指出运行入口、主要模块、共享契约和验证命令。

**验收场景**：

1. **假设** 维护者首次进入仓库，**当** 阅读根目录入口文档，**则** 能区分主应用源码、辅助工具、产品文档、Spec Kit 产物、正式交付物和本地产物。
2. **假设** 维护者需要修改某项业务能力，**当** 查阅项目手册，**则** 能找到对应的前端模块、后端模块、关键数据对象和测试入口，而不需要全文搜索整个仓库。
3. **假设** 某项能力仍处于未完成规格状态，**当** 查阅文档，**则** 文档明确区分“当前已实现”“规格目标”“尚未完成”，不把规划内容描述为现状。

---

### 用户故事 2 - 在清晰边界内安全修改代码（优先级：P1）

研发人员可以按业务能力或技术职责修改一个相对独立的模块，不必同时进入超大入口文件、全量数据类型文件或单体样式文件；模块间依赖方向清晰，原有外部行为和计算结果保持兼容。

**优先级理由**：后端求解、场景编排与模型，以及前端工作台、共享类型与样式已经形成明显热点，持续在原文件追加能力会提高回归风险和协作冲突。

**独立测试**：分别完成一个后端接口维护样例、一个排程诊断维护样例和一个前端功能面板维护样例，确认修改范围可局限在对应模块及其测试，并通过行为基线验证对外兼容。

**验收场景**：

1. **假设** 研发人员需要维护某组接口，**当** 定位并修改该能力，**则** 接口声明、请求编排、错误映射和领域逻辑具有清晰分工。
2. **假设** 研发人员需要维护排程求解逻辑，**当** 定位相关规则，**则** 能区分输入准备、约束构造、目标构造、求解阶段、结果转换和诊断评价。
3. **假设** 研发人员需要维护某个前端业务页，**当** 修改该页，**则** 页面状态、领域计算、API 调用和展示组件不再集中在全局工作台入口。
4. **假设** 重构前后使用同一组固定输入，**当** 执行回归验证，**则** 公开接口、关键计算结果和主要用户流程保持等价。

---

### 用户故事 3 - 稳定运行、测试与部署（优先级：P1）

开发和交付人员继续使用统一、明确的命令启动、测试、构建和部署项目；架构调整的每个阶段都保持仓库可运行，并能快速判断失败属于环境、接口、领域逻辑还是构建配置。

**优先级理由**：重构必须在持续可验证的前提下推进，否则大规模移动和拆分会放大当前未完成能力带来的不确定性。

**独立测试**：在干净依赖环境中执行文档列出的后端测试、前端测试、前端构建、单服务启动和健康检查，验证命令、入口和结果与文档一致。

**验收场景**：

1. **假设** 现有调用方继续使用原公开接口，**当** 完成任一重构阶段，**则** 不需要修改调用路径或请求格式。
2. **假设** 开发者使用原有根目录命令，**当** 启动或构建项目，**则** 命令仍可用，或由兼容入口给出明确迁移提示。
3. **假设** 某个阶段尚未完成全部拆分，**当** 合并该阶段，**则** 已迁移和未迁移模块能够共同运行，且回归门禁通过。

---

### 用户故事 4 - 持续维护文档与仓库卫生（优先级：P2）

项目维护者可以按明确规则新增文档、规格、辅助工具、交付物和临时产物；`README.md` 面向使用者提供最短可用入口，`agent.md` 面向 Agent 和维护者提供事实地图，详细架构资料独立维护，避免两个入口文档继续膨胀或相互复制。

**优先级理由**：一次性整理不能解决长期熵增，需要让文档角色、归档策略和更新检查成为可重复的维护约束。

**独立测试**：模拟新增一个业务模块、一份 PRD、一个客户交付物和一个本地调试产物，验证维护者能根据规则确定放置位置、索引更新和是否纳入版本控制。

**验收场景**：

1. **假设** 维护者新增文档或交付物，**当** 选择存放位置，**则** 能依据文档分类和保留策略作出唯一判断。
2. **假设** 维护者更新业务模块、接口或运行命令，**当** 完成变更，**则** 有清晰检查项判断是否同步更新 `README.md`、`agent.md` 或详细架构文档。
3. **假设** 仓库存在缓存、日志、构建产物或个人环境文件，**当** 执行仓库卫生检查，**则** 这些本地产物不会被误当作正式源码或业务交付物。
4. **假设** 历史规格或客户交付物不再属于当前主链路，**当** 整理目录，**则** 通过索引、归档或交付物分区保留可追溯性，而不是直接删除。

### 边界与异常场景

- 当前 `041` 规格存在已完成、部分完成和未完成任务；架构重构只能迁移已存在实现并保持任务状态，不得借重构宣称未完成功能已经交付。
- 某些模块在拆分过程中存在循环依赖时，必须先增加兼容层或明确依赖方向，不得通过复制代码形成两套规则。
- 历史测试、脚本或文档引用旧路径时，路径迁移必须同步更新引用；暂时无法迁移时应保留兼容入口并记录移除条件。
- 固定输入的求解结果可能包含非确定性字段或运行时间差异；等价性验证应比较业务不变量、任务日期、资源分配、里程碑和诊断语义，而不是比较无关运行元数据。
- 本地未跟踪的缓存、密钥、构建产物和用户输出不属于本次迁移对象，不得批量移动或删除。用户已明确要求治理的根目录 `*.log` 作为唯一例外：逐文件纳入二次确认清单，只移动到 `.local-data/logs/legacy/`，不删除、不纳入 Git。
- 已跟踪的客户交付物和业务输出必须保留，不能用“生成物”名义一律忽略；正式交付物与可重新生成的临时产物需要分区管理。
- 如果拆分会改变公开 API、共享字段、排程结果、部署方式或引入新依赖，必须停止并回到规格澄清，不得作为内部重构直接实施。

## 需求（必填）

### 功能需求

- **FR-001**：仓库必须定义并呈现主应用、辅助工具、产品与研发文档、Spec Kit 产物、测试夹具、正式交付物和本地产物的一级边界。
- **FR-002**：仓库根目录必须只保留进入项目、安装运行、构建部署和协作治理所需的入口文件，以及经确认必须位于根目录的配置或示例数据。
- **FR-003**：后端必须按接口适配、应用编排、领域规则、基础设施和共享契约分离职责，并为现有公开入口提供兼容边界。
- **FR-004**：排程求解能力必须能够按输入准备、约束、目标、求解阶段、结果转换和诊断进行定位与独立验证，同时保持现有算法语义不变。
- **FR-005**：场景生成、方案比较、资源搜索、计划管控、架梁专项和 AI 辅助能力必须具有可识别的模块所有权，跨模块调用必须通过明确入口完成。
- **FR-006**：后端公开数据契约必须按业务域可定位，并维持现有导入路径或提供受测试保护的兼容导出。
- **FR-007**：前端全局工作台必须只承担应用装配、导航和跨功能协调；业务状态、业务计算、API 调用和展示细节必须下沉到对应功能边界。
- **FR-008**：前端共享契约、领域辅助函数、功能组件和样式必须按稳定职责组织，禁止继续将不相关能力集中追加到单一全局文件。
- **FR-009**：重构必须保持现有公开 API 路径、请求响应字段语义、关键状态码、启动命令和部署入口兼容。
- **FR-010**：重构必须建立可重复的行为基线，覆盖核心求解、场景生成、架梁专项、计划管控、AI 助手、前端工作流和构建流程。
- **FR-011**：每个实施阶段必须可以独立运行和回退，且在进入下一阶段前通过该阶段定义的回归门禁。
- **FR-012**：架构升级不得新增产品功能、改变业务规则，或将 `041` 的未完成任务纳入“顺手修复”。
- **FR-013**：辅助工具必须与主应用依赖和发布边界分离；移动后仍需保留自身说明、运行入口和产物策略。
- **FR-014**：正式交付物、可复现样例和临时生成物必须采用不同的存放与版本控制策略，且已有正式资产不得删除。
- **FR-015**：`README.md` 必须面向首次使用者说明项目定位、当前能力边界、快速启动、验证、部署、目录地图和详细文档入口。
- **FR-016**：`agent.md` 必须面向 Agent 和维护者说明项目事实、模块所有权、数据与调用链、关键兼容边界、修改路线、验证矩阵和需要确认的风险点。
- **FR-017**：详细架构说明必须从入口文档中独立出来，记录系统上下文、模块边界、依赖方向、关键调用链和架构决策，避免 `README.md` 与 `agent.md` 重复堆积。
- **FR-018**：文档必须明确区分当前实现、规格目标、历史说明和待确认事项，并为移动或归档的文档更新全部仓库内引用。
- **FR-019**：项目必须提供仓库结构与文档一致性检查，至少能发现失效链接、错误运行命令、误纳入的本地产物和入口文档遗漏。
- **FR-020**：重构默认复用现有依赖、模型、服务、组件和测试设施；任何新依赖或框架调整都必须另行确认。
- **FR-021**：后台服务落盘日志必须统一进入 `.local-data/logs/<启动时间>/`；仓库根目录不得作为日志目录，既有根日志只能在逐文件确认后移动且不得自动删除。

### 关键实体（涉及数据时填写）

- **模块边界**：一组具有明确职责、所有权、公开入口和依赖方向的代码或工具集合。
- **公开契约**：供前端、后端、测试、部署或外部调用方依赖的接口路径、数据形状、状态语义、命令和导入入口。
- **行为基线**：用于证明重构前后业务行为等价的固定输入、可比较输出、不变量和验证命令集合。
- **文档入口**：针对不同读者承担唯一主要职责的入口文档，包括使用入口、项目事实手册、详细架构说明和领域文档索引。
- **仓库资产**：源码、配置、文档、规格、测试夹具、辅助工具、正式交付物或本地产物及其分类、保留和版本控制策略。
- **迁移批次**：可独立实施、验证和回退的一组目录或模块调整，包含范围、兼容策略、验证证据和完成状态。

- **SC-003**：所有重构批次完成后，现有公开 API 路径保留率为 100%，共享字段和关键状态码不存在未经批准的不兼容变化。

- **SC-007**：`README.md`、`agent.md`、详细架构说明和主要文档索引中的仓库内链接有效率达到 100%，运行命令与当前配置一致。
- **SC-008**：随机抽查不少于 10 个近期能力或接口，`agent.md` 对其模块所有权、当前状态和验证路径的描述与代码及测试事实一致率达到 100%。

- **SC-010**：重构后新增一个模拟业务模块、文档、正式交付物和本地产物时，维护者均能依据治理规则一次选择正确位置，无需新增根目录临时分类。
- **SC-011**：资产迁移完成后根目录 `*.log` 数量为 0；统一后台启动入口的 stdout/stderr 路径 100% 位于 `.local-data/logs/`，且日志误纳入 Git 的数量为 0。

## 默认假设

- 本次“架构升级”默认指行为保持型模块化重构和仓库治理，不包含业务规则重写、框架迁移或微服务拆分。
- 当前仓库是唯一实施范围；其他本地仓库、外部部署环境和历史应用不在本次操作权限内。
- `specs/041-girder-scheduling-integration/` 代表当前集成状态的重要事实来源，但其中未完成任务继续由 `041` 管理。
- 现有公开 API、根目录启动命令和部署入口应尽量保持不变；内部路径可以迁移，但必须提供明确兼容层和测试。
- 已跟踪的正式业务输出和客户交付物继续保留；本地未跟踪文件默认不移动、不删除。逐文件清单中的根目录运行日志经二次确认后仅移动到 `.local-data/logs/legacy/`。
- 首轮重构不引入新的运行时依赖；若现有测试工具不足，优先使用标准库或现有依赖完成验证。
- 文档采用“入口简洁、细节下沉、索引连接”的分层方式：`README.md` 服务首次使用者，`agent.md` 服务 Agent/维护者，详细架构和领域说明放入 `docs/`。
