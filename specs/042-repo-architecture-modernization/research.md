# Phase 0 研究：项目架构治理与模块化升级

**日期**：2026-07-16

## 研究范围与现状证据

- 后端：`main.py` 577 行并注册 45 个 `/api` 路由；`models.py` 1973 行、153 个模型；`scenario.py` 3687 行、128 个顶层函数；`solver.py` 8427 行、214 个顶层函数；`services/` 混放多个业务域。
- 前端：`app/App.tsx` 4824 行，包含 37 个 `useState`、156 个函数和 9 个内联组件；`types/scheduler.ts` 1901 行、202 个导出类型，被 41 个模块消费；`schedulerApi.ts` 暴露 40 个函数；`styles.css` 4927 行。
- 测试：后端当前 `328 passed, 1 skipped`；前端 21 个 Node 用例全部通过；前端生产构建通过。后端 `test_scheduler.py` 单文件约 6836 行、170 个测试，前端缺少 App 编排、真实 HTTP 和样式回归保护。
- 仓库：根目录有 16 个已跟踪文件；`docs/` 27 个文件且无索引；`specs/` 315 个已跟踪文件且无总索引；`ai-ppt-system/` 70 个已跟踪文件，源码与生成物混放；`outputs/` 20 个已跟踪文件，正式交付物、脚本、预览和检查中间件混放。
- 文档：真实后端有 45 个 `/api` 路由，`README.md` 只列 18 个、`agent.md` 只列 16 个；两者未完整覆盖架梁专项、综合排程、计划管控、进度预测和 AI 资源助手。`agent.md` 还引用不存在的 `netlify/functions/api.mts`。

## 决策 1：采用模块化单体与兼容门面

- **决策**：保持单一 FastAPI 后端和单一 React 前端，通过内部包边界拆分职责；旧入口文件转为兼容重导出或转发层。
- **理由**：当前问题是单体内部边界失控，而不是运行进程不足。模块化单体可以保持部署、调试和演示方式不变，并允许每批独立验证。
- **已评估的替代方案**：微服务拆分会新增部署、网络、数据一致性和可观测性成本；一次性重写会在现有回归覆盖不足时放大风险，均不采用。

## 决策 2：先固化行为基线，再移动代码

- **决策**：在任何目录迁移前生成 OpenAPI 路由清单、Pydantic schema、旧导入路径、固定场景业务不变量、前端失效规则、构建体积和资产清单。
- **理由**：现有测试大量直接调用内部函数，真实 HTTP、兼容入口和跨端契约保护不足。仅依赖现有绿灯无法证明结构迁移没有改变外部行为。
- **已评估的替代方案**：先移动再补测试会把既有差异和迁移回归混在一起；仅比较完整 JSON 会受运行时间等非业务元数据干扰。

## 决策 3：后端先拆 HTTP 与契约，再拆场景和求解器

- **决策**：顺序为 `main.py` routers/bootstrap → `models.py` contracts → 业务服务所有权 → `scenario.py` application/generation → `solver.py` strategies/constraints/objectives/results/diagnostics。
- **理由**：HTTP 和数据契约边界最容易快照验证；求解器的迭代顺序、时间预算和私有函数 monkeypatch 风险最高，应在兼容设施成熟后自底向上迁移。
- **已评估的替代方案**：先拆 `solver.py` 虽能最快降低文件规模，但会在缺少 OpenAPI/schema/导入门禁时扩大不可见回归；按技术层一次性搬完会形成大爆炸式改动。

## 决策 4：固定后端依赖方向

- **决策**：依赖方向为 `api -> application -> domain`；配置、文件仓储和外部模型客户端由 bootstrap/application 装配；跨业务域通过公开 façade 调用。
- **理由**：当前 `scenario.py` 导入 `solver.py` 私有函数、架梁/计划管控散落在 `services/`，说明缺少稳定端口。固定方向可以避免拆分后形成新的循环依赖。
- **已评估的替代方案**：保留泛化 `services/` 并只缩短文件，无法解决业务所有权；引入完整依赖注入框架超出范围。

## 决策 5：前端按业务纵切，保留旧类型与 API 出口

- **决策**：`app` 只负责装配；业务状态、组件和 presenter 归属 `features`；纯规则留在 `domain`；共享 DTO 放入按域 `contracts`；API 按域拆分。`types/scheduler.ts`、`api/schedulerApi.ts` 和根 `App.tsx` 保留兼容重导出。
- **理由**：现有 `domain/` 和 `features/` 已提供可复用骨架，兼容出口可避免一次修改 41 个类型消费者和 40 个 API 调用方。
- **已评估的替代方案**：引入 Redux、CSS Modules、新路由或新测试框架会把结构治理扩大为技术迁移；先机械改所有 import 不能直接改善业务所有权。

## 决策 6：前端拆分顺序由纯逻辑到工作流、由组件到样式

- **决策**：先抽纯函数和小组件，再迁移任务/结果 presenter，最后拆求解 controller 和跨功能状态；CSS 在组件所有权稳定后迁移，保留选择器和导入顺序。
- **理由**：场景指纹失效、对比结果和综合快照联动是主要行为风险；样式级联顺序是主要视觉风险。先建立可测试边界可以降低两者同时变化的概率。
- **已评估的替代方案**：一次性重写 `App.tsx` 或先拆全局 CSS 都会产生难以定位的行为/视觉回归。

## 决策 7：仓库采用入口简化、知识下沉和资产分区

- **决策**：`README.md` 负责首次使用；`agent.md` 负责当前事实和修改地图；详细内容进入 `docs/architecture/`；`docs/README.md`、`specs/README.md` 管理索引。辅助工具进入 `tools/`，正式最终交付件进入 `deliverables/`，可再生成中间件进入默认忽略的 `artifacts/`。
- **理由**：当前入口文档既重复又落后，辅助工具、正式交付物和生成物并列会误导维护者和发布流程。分层后每类资产有唯一职责和保留策略。
- **已评估的替代方案**：只改目录图不移动资产无法解决跟踪策略；批量删除所有生成物会误删正式业务交付件；把所有历史资料统一搬迁会破坏大量规格引用。

## 决策 8：历史规格保持原路径，文档与资产分批迁移

- **决策**：现有 `specs/<编号>-<slug>/` 不移动、不重编号；新增总索引记录 active/completed/superseded。文档和资产先建立逐文件清单与迁移表，提交用户二次明确确认后，才对确认过的文件使用 `git mv` 或取消跟踪，并同步更新当前引用；历史失效引用分类记录，不做无差别替换。
- **理由**：历史规格包含重复编号、旧来源丢失和未实施预期路径，自动重命名或全局替换会破坏审计语义。样例 Excel还被导入逻辑、Docker 和历史 quickstart 依赖，必须先提供兼容搜索。
- **已评估的替代方案**：一次性重编号所有规格、直接移动根 Excel或清空 `outputs/` 风险不可接受。

## 决策 9：文档更新分为事实修正与最终收敛两次

- **决策**：第一批先修复错误路由、模块、Netlify 路径和能力状态；结构稳定后再完成最终目录、模块所有权、调用链和验证矩阵。
- **理由**：等到全部代码迁移后才修文档会让实施期继续依赖错误事实；一开始写死最终路径又会在迁移调整时快速过时。
- **已评估的替代方案**：只在最后更新或每次小移动都重写整份文档，分别会造成长期失真或高噪声。

## 决策 10：兼容层在本功能内不删除

- **决策**：`app.main:app`、`app.models`、`app.scenario`、`app.solver`、`frontend/src/App.tsx`、`types/scheduler.ts`、`api/schedulerApi.ts`、根 npm 命令和公开 API 在本功能结束时仍存在。
- **理由**：兼容层使分批迁移可回退，并保护历史测试、脚本、文档和潜在外部调用方。移除属于破坏性版本治理，不是本次内部重构的必要条件。
- **已评估的替代方案**：迁移完成即删除旧入口可以减少文件，但会把内部整理变成对调用方的强制升级。

## 未采用的新依赖

- 不引入 Redux/Zustand、CSS Modules、前端组件测试框架、Python DI 框架、monorepo 工具、依赖图服务或文档站点生成器。
- 架构、链接、路由和兼容检查优先用 Python/Node 标准库、FastAPI/Pydantic 现有能力和当前测试设施实现。
- 实施前分别冻结 `requirements.txt`、根/前端/辅助工具 `package.json` 与锁文件的运行时依赖清单；出现新增包、版本升级或锁文件依赖树变化时必须阻断，除非另行获得用户确认。
