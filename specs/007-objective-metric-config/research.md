# Phase 0 研究：精排目标指标前端全量展示与配置

## 决策 1：以后端目标指标目录作为权威来源

**结论**：建立后端目标指标目录，前端使用同一组稳定 `term_id`、默认权重和解释文案。前端可以保留展示文案兜底，但不能只靠硬编码列表决定哪些目标项存在。

**原因**：目标项是否参与求解由后端 `model.Minimize(...)` 决定。当前前端硬编码 7 项，已经与后端隐藏目标项产生偏差。

**备选方案**：

- 只在前端补 3 个新项：短期可行，但下次后端新增目标项仍会再次漂移。
- 只在文档说明隐藏项：无法满足“支持配置”的需求。

## 决策 2：隐藏加权项提升为可见目标项

**结论**：将 `target_relaxation`、`unconfigured_normal_balance`、`resource_slot_balance` 纳入前端可见目标指标体系。其中 `unconfigured_normal_balance` 应成为可配置目标项；`target_relaxation` 和 `resource_slot_balance` 的具体权重关系由实现保持行为等价，但必须在配置和结果贡献中可见。

**原因**：这三类指标已经在当前后端求解或 `weighted_objective` 中产生影响，用户无法理解或调整会造成调参盲区。

**备选方案**：

- 继续继承父项权重并只显示在结果里：解释性增强不足，不能满足“支持配置”。
- 直接重构全部目标函数权重层级：影响过大，不符合本次范围。

## 决策 3：诊断项只读展示，不进入权重配置

**结论**：`continuity_score`、`jump_pier_count`、`side_switch_count`、`direction_reversal_count`、`normal_balance_score`、`path_group_diagnostics` 等指标作为结果诊断展示，除非后端将其作为独立项加入目标函数，否则不提供启用开关和权重输入。

**原因**：这些指标用于解释排程质量或风险，不都是独立目标函数项。混入配置表会误导用户，以为可以直接优化某个统计。

**备选方案**：

- 把所有结果指标都做成权重项：业务含义错误，也会扩大算法改造范围。
- 完全不展示诊断项：不利于结果解释和方案复盘。

## 决策 4：统一目标贡献列表作为结果解释主入口

**结论**：后端在 `objective_breakdown` 中输出统一贡献列表，前端结果页优先展示该列表。旧结果没有列表时，前端回退到既有字段。

**原因**：当前字段散落在 `objective_breakdown` 和 `stats` 中，前端难以验证 `weighted_objective`。统一列表能同时支持配置回显、结果解释和验收测试。

**备选方案**：

- 前端自行从散字段拼表：会复制后端知识，容易漏项。
- 只显示总分：不满足“指标项都需要展示”的诉求。

## 决策 5：默认值保持旧行为等价

**结论**：旧场景缺失新增目标项时，后端自动补齐默认值，并保证默认行为尽量等价于当前实现。

**原因**：目标项配置是共享契约，旧 Demo 数据、历史配置和用户保存场景不能因为新增字段而失效。

**备选方案**：

- 要求用户手动迁移旧场景：使用成本高，且容易误配。
- 放弃新增项默认启用：可能改变当前求解结果，不符合兼容要求。
