# Phase 0 研究：现浇连续梁联级班组占用

## 决策 1：连续梁联的身份口径

**决策**：连续梁联默认按 `bridge_id + work_section_id + group_index` 识别。

**理由**：当前连续梁任务生成时已经携带桥梁、工区/幅别和连续梁组号；左幅和右幅天然位于不同 `work_section_id`，可以表达“左幅一联、右幅一联分别占用班组”。

**已评估的替代方案**：
- 仅按 `group_index` 聚合：不同幅别或不同桥梁的同号连续梁会被错误合并。
- 按 `structure_id` 聚合：会落到 T 构或边跨段粒度，无法表达整联占用。
- 新增用户手填联号作为唯一口径：更灵活，但第一版会扩大结构参数录入范围。

## 决策 2：班组数量语义

**决策**：`cast_in_place_continuous_beam_team.quantity` 表示最多可同时施工的连续梁联数。

**理由**：这与用户确认的资源组织语言一致：1 个班组跨联串行，2 个班组最多两联并行。该语义也能自然进入最少资源建议和资源成本测算。

**已评估的替代方案**：
- 继续表示可同时执行的连续梁任务数：会把联内任务误当资源并发，无法满足本功能。
- 新增独立“连续梁联班组数量”配置：可读性好，但会与现有资源池数量重复，增加配置同步风险。

## 决策 3：联内任务不纳入连续梁班组任务级互斥

**决策**：同一联内连续梁任务不再逐个占用连续梁班组的任务级时间片；联内并行只受既有工艺、下部结构、同步、合龙和里程碑等约束。

**理由**：用户明确要求“某联分配资源后，联内任务只要具备条件就能干”。如果继续对每个任务建立班组互斥，规则会退回当前模型。

**已评估的替代方案**：
- 对联内任务提高并行上限：仍然需要选择任务级资源，且很难表达整联班组归属。
- 把整联合成一个粗任务：会破坏任务视图、工艺逻辑和现有连续梁专用约束。

## 决策 4：联级占用窗口用于跨联互斥

**决策**：每个连续梁联的占用窗口由该联实际生成任务的最早开始和最晚完成确定；同一连续梁班组的联级占用窗口不得重叠。

**理由**：该口径能表达“班组负责这一联施工组织”而不是“班组执行某一个任务”。窗口由真实任务结果派生，能覆盖联内所有连续梁施工阶段。

**已评估的替代方案**：
- 只用 0 号块到最后合龙作为窗口：对缺失任务或特殊配置不够稳健。
- 用固定工期估算窗口：与实际排程脱节，可能产生错误等待。

## 决策 5：结果侧需要联级资源解释

**决策**：排程结果需要提供连续梁任务所属联、联级班组归属和联级占用起止信息；旧结果缺失这些信息时前端兼容展示。

**理由**：联级占用后，部分联内任务可能不再显示任务级连续梁班组分配。如果没有联级解释，用户会误以为任务缺资源或资源分配丢失。

**已评估的替代方案**：
- 只在后端内部建模，不输出解释信息：实现更小，但不满足用户理解和验收。
- 给每个任务复制同一个班组分配：展示直观，但容易被误读为任务级互斥仍存在。

## 决策 6：所有求解分支保持一致语义

**决策**：固定资源、最少资源和资源成本相关求解均使用同一连续梁联级占用语义。

**理由**：用户会通过 `quantity = 1/2` 判断当前资源和增配资源对工期的影响；不同分支语义不一致会导致方案对比不可解释。

**已评估的替代方案**：
- 第一版只改固定资源主链路：范围小，但最少资源建议会继续按任务级资源推算，输出互相矛盾。

## 决策 7：Netlify 演示 API 作为实现阶段检查项

**决策**：计划阶段不默认扩大到 Netlify，但任务中保留检查 `netlify/functions/api.mts` 是否存在同类资源语义的工作项。

**理由**：本项目 Python 后端是工程化和测试主实现；Netlify 主要用于部署演示。若其逻辑没有连续梁 CP-SAT 等价实现，则不应强行扩展。

**已评估的替代方案**：
- 同步修改 Netlify：可能扩大无关范围。
- 完全忽略 Netlify：若演示 API 存在相同结果入口，会造成部署演示与本地不一致。
