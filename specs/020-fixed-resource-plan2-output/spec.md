## 用户场景与测试（必填）

### 用户故事 1 - 当前资源目标失败仍保留方案1（优先级：P1）

计划工程师运行固定资源模拟求解时，如果当前资源可以排出一份计划但强制里程碑没有满足，系统必须保留这份当前资源计划作为方案1，让用户能看到现有资源与目标节点之间的差距，而不是只看到资源建议失败或无结果。

**优先级理由**：这是本次需求的核心价值。没有方案1，用户无法判断当前资源已经排到哪里、晚点多少天、后续新增资源建议是否可信。

**独立测试**：准备一个当前资源可形成排程但硬里程碑晚点的场景，执行固定资源模拟求解，验证返回和页面展示中方案1存在、状态为当前资源目标未满足，并包含任务、资源分配和里程碑迟延信息。

**验收场景**：

1. **假设** 当前资源能生成可查看排程但至少一个强制里程碑晚点，**当** 用户执行固定资源模拟求解，**则** 系统必须把当前资源排程作为方案1输出，并标明业务目标未满足。
2. **假设** 当前资源目标失败且进入资源增量建议，**当** 新增资源分支尚未完成或最终无候选方案，**则** 方案1仍可查看，且不被资源建议失败覆盖。

---

### 用户故事 2 - 新增资源成功时输出方案2（优先级：P1）

计划工程师需要在同一次固定资源求解中同时看到“当前资源方案”和“新增资源候选方案”。当新增资源分支最终找到可展示结果时，系统必须把新增资源结果作为方案2输出，方便用户比较新增资源前后的工期、里程碑和资源数量变化。

**优先级理由**：这是固定资源目标失败后的主要下一步。如果候选资源满足目标却没有作为方案2展示，用户无法直接比较资源增量带来的收益。

**独立测试**：准备一个当前资源目标失败、增加资源后可满足目标的场景，执行固定资源模拟求解，验证结果包含方案1和方案2，方案2标明新增资源候选，并展示新增资源数量、总工期和里程碑满足状态。

**验收场景**：

1. **假设** 当前资源方案可查看但目标失败，且新增资源分支找到满足目标的候选排程，**当** 用户查看求解结果，**则** 系统必须展示方案1当前资源和方案2新增资源候选。
2. **假设** 方案2存在，**当** 用户在方案输出区域切换方案，**则** 方案2必须显示自己的任务、资源、里程碑和诊断信息，不复用方案1的明细。

---

### 用户故事 3 - 新增资源失败时明确提示方案2未输出（优先级：P2）

计划工程师需要知道系统已经尝试新增资源，但没有得到可展示的方案2。系统必须只返回方案1，并给出清晰提示，避免用户误以为没有进入新增资源分支，或误把推荐失败理解为当前资源也没有结果。

**优先级理由**：该故事降低误解和排查成本，尤其适用于资源上限不足、关键路径不可压缩、候选复排失败或求解限时未确认等场景。

**独立测试**：准备当前资源可查看但目标失败、资源增量分支无可展示候选的场景，执行固定资源模拟求解，验证结果只包含方案1，页面或诊断明确提示“方案2未输出”及原因。

**验收场景**：

1. **假设** 当前资源方案可查看但目标失败，且新增资源分支没有可展示候选，**当** 用户查看求解结果，**则** 系统只展示方案1，不展示空的方案2入口。
2. **假设** 新增资源分支因资源上限不足、关键路径不可行、候选复排失败或限时未确认而没有方案2，**当** 用户查看诊断信息，**则** 系统必须提示方案2未输出，并说明原因类别。

### 边界与异常场景

- 当前资源求解状态为未确认时：系统不得把未确认结果包装成方案1成功结果，也不得进入确定性新增资源方案输出；需提示当前求解限时内无法确认。
- 当前资源物理不可行时：系统不得输出方案1当前资源，也不得展示方案2；需提示资源、工艺关系或覆盖配置无法形成可行排程。
- 当前资源目标已满足时：系统只返回当前资源方案，并提示无需新增资源；不得输出方案2。
- 新增资源分支只返回诊断、资源上限失败、关键路径不可压缩或候选复排未达标时：系统只输出方案1，并提示方案2未输出。
- 新增资源分支返回多个尝试记录时：用户可查看推荐尝试摘要，但只有最终可展示候选能成为方案2。
- 结果展示不得出现“方案2按钮存在但无任务明细”“方案2复用方案1明细”“当前资源结果被候选失败状态覆盖”等混乱状态。

## 需求（必填）

### 功能需求

- **FR-001**：系统必须在固定资源求解中区分“当前资源主结果”和“新增资源候选结果”，并保持二者的方案编号稳定：当前资源为方案1，新增资源候选为方案2。
- **FR-002**：当当前资源求解得到可查看排程但业务目标未满足时，系统必须将当前资源排程输出为方案1，并保留任务、资源分配、里程碑结果、目标达成状态和诊断信息。
- **FR-003**：当当前资源方案目标未满足时，系统必须进入新增资源分支，并记录资源增量建议的状态、原因和尝试摘要。
- **FR-004**：当新增资源分支最终得到可展示候选方案时，系统必须将该候选作为方案2输出，并标明其为新增资源候选。
- **FR-005**：当新增资源分支没有得到可展示候选方案时，系统必须只返回方案1，并向用户明确提示方案2未输出。
- **FR-006**：方案2未输出提示必须说明原因类别，至少覆盖资源上限不足、关键路径不可压缩、候选复排未满足目标、求解限时未确认和最大资源场景生成失败。
- **FR-007**：系统不得因为新增资源分支失败而把方案1的状态改写成无结果、不可查看或候选失败；方案1必须继续表达当前资源方案自身的目标未满足状态。
- **FR-008**：当方案2不存在时，页面不得展示可切换但无内容的方案2入口；当方案2存在时，页面必须支持用户在方案1和方案2之间切换并查看各自明细。
- **FR-009**：方案列表、诊断摘要和里程碑状态必须使用同一套目标达成口径，避免一个位置显示“已找到候选资源”，另一个位置显示“无候选方案”。
- **FR-010**：系统必须保留已有固定资源目标已满足、当前资源未确认、当前资源物理不可行等场景的现有含义，不得为了输出方案1/方案2而改变这些状态。

### 关键实体（涉及数据时填写）

- **方案1当前资源结果**：代表当前资源数量下的可查看排程，关键属性包括求解状态、业务目标达成状态、里程碑迟延、任务列表、资源分配和诊断信息。
- **方案2新增资源候选结果**：代表资源增量分支最终形成的可展示候选排程，关键属性包括候选资源数量、新增资源数量、业务目标达成状态、任务列表、资源分配和候选验证状态。
- **资源增量建议状态**：代表新增资源分支是否找到候选、为什么没有找到候选、尝试了哪些资源组合，以及是否需要用户调整资源上限、目标工期或求解限时。
- **目标达成状态**：代表当前方案或候选方案是否满足强制里程碑和固定工期目标，是判定方案编号、展示文案和诊断原因的共同依据。

## 成功标准（必填）

### 可衡量结果

- **SC-001**：在当前资源可查看但里程碑未满足的测试场景中，100% 的固定资源求解结果都包含方案1当前资源排程。
- **SC-002**：在新增资源分支成功的测试场景中，100% 的结果都同时展示方案1和方案2，且方案2的资源数量大于或等于方案1并清晰标出新增资源。
- **SC-003**：在新增资源分支无可展示候选的测试场景中，100% 的结果只展示方案1，并出现用户可见的“方案2未输出”提示。
- **SC-004**：用户在方案输出区域不会看到空方案、重复方案或编号跳跃；方案数量与实际可查看结果数量一致。
- **SC-005**：至少覆盖 5 类失败原因的验收样例：关键路径不可压缩、资源上限不足、候选复排未满足目标、求解限时未确认、最大资源场景生成失败。

## 默认假设

- 默认假设：本功能的“当前资源有结果”指当前资源求解状态为可查看排程，且包含任务、资源分配和里程碑结果；`UNKNOWN` 或物理不可行不按可查看方案处理。
  影响：未确认和物理不可行场景不会被包装成方案1/方案2，只保留诊断提示。
- 默认假设：“新增资源分支有结果返回”指最终形成可展示候选方案，并通过既有目标达成口径；仅有搜索尝试、失败诊断或未达标复排不算方案2。
  影响：候选复排失败、资源上限不足、关键路径不可压缩等场景只显示方案1，并提示方案2未输出。
- 默认假设：方案2最多输出一个最终候选；新增资源分支的多轮尝试作为诊断摘要展示，不作为多个方案按钮。
  影响：本期不做多候选排序、资源方案列表或成本方案并列展示。
- 默认假设：本功能优先对齐本地 Python 后端和当前 React 页面；Netlify 演示镜像若不承载完整求解能力，不作为本期验收主路径。
  影响：后续计划阶段需确认是否同步 Netlify 演示 API 文案或兼容字段。
