# 功能规格：根目录生命周期工作区治理

**功能目录/分支**：`045-lifecycle-workspace-governance`

**创建日期**：2026-07-16

**状态**：草稿

**输入**：用户确认将仓库按产品全生命周期从根目录重新组织，并补充独立 JSON 展示、AI 案例总结、客户验证工作包以及日志缓存分级和后续自动归类要求。

## 来源与评审上下文（必填）

- **来源文档**：`AGENTS.md`、`agent.md`、`README.md`、`docs/README.md`、`docs/architecture/repository-governance.md`、`docs/architecture/module-map.md`、`specs/042-repo-architecture-modernization/*`、本功能 `discovery.md`。
- **评审结论**：用户已否决只在 `docs/` 内建立生命周期导航的 044 方向，并确认采用“根目录生命周期阶段—独立工作包—输入/脚本/成果/本地产物”的三层治理模型。
- **使用的 Demo/代码事实**：当前代码、文档、工具、验证脚本、独立 JSON 查看器、交付构建器、输出和 Skill 分散在多个技术类型目录；运行入口、Spec Kit 和 Skill 发现路径存在固定路径依赖。
- **不在范围内**：不改变排程业务规则、算法目标、接口字段、页面行为、持久化数据语义或正式交付内容；不删除用户输入、正式交付物、本地状态或未获批资产；不提交、推送或部署。

## 用户场景与测试（必填）

### 用户故事 1 - 按产品阶段理解整个仓库（优先级：P1）

产品、调研、研发、验证和交付人员进入仓库后，可以直接从根目录找到自己所处阶段，并在阶段内看到相关文档、代码、脚本、输入和成果，而不需要先理解 `docs`、`tools`、`outputs` 等技术目录。

**优先级理由**：这是本次重构的核心价值，也是用户否决 044 的根本原因。

**独立测试**：从根目录分别定位一项调研分析、方案、需求、Demo 代码、客户验证和正式交付工作，在两次目录进入内找到其阶段入口和主要资产。

**验收场景**：

1. **假设** 维护者只知道任务所处生命周期阶段，**当** 查看根目录，**则** 可以直接进入唯一阶段并找到阶段说明。
2. **假设** 资产同时被多个阶段使用，**当** 查找其主要归属，**则** 只存在一个主文件，其他阶段通过链接说明关系。
3. **假设** 维护者进入 Demo 阶段，**当** 查找运行代码，**则** 后端、前端、部署、样例和 Demo 工具位于同一阶段边界内。

---

### 用户故事 2 - 独立理解和运行一个工作包（优先级：P1）

维护者可以把独立 JSON 展示、客户验证、AI 案例总结等内容作为完整工作包查看，明确其目的、输入、脚本、运行命令、成果和清理边界。

**优先级理由**：仅按阶段分目录仍会让脚本和成果失联；工作包是长期可维护的最小单元。

**独立测试**：随机选择 JSON 展示、泸古验证和 AI 案例总结三个工作包，不查阅外部资料即可说明如何运行、成果在哪里以及哪些文件可以清理。

**验收场景**：

1. **假设** 工作包含可复用脚本，**当** 查看工作包入口，**则** 可以识别输入、命令、成果和失败检查方式。
2. **假设** 工作包同时有正式成果和本地预览，**当** 查看保留策略，**则** 两者具有不同且明确的清理等级。
3. **假设** AI 案例成果暂时无法绑定生成脚本，**当** 迁移该成果，**则** 标记为待关联而不是虚构脚本或删除成果。

---

### 用户故事 3 - 后续任务自动选择归属（优先级：P1）

Agent 或维护者执行新任务时，必须先声明生命周期阶段、工作包、资产类型、保留策略和主要所有者，然后在对应位置创建或更新文件。

**优先级理由**：用户明确要求这不是一次性整理，必须阻止结构再次失控。

**独立测试**：使用调研总结、方案比较、PRD 导出、Demo 功能、客户验证、AI 案例六种模拟任务执行归类，全部命中唯一阶段和工作包策略。

**验收场景**：

1. **假设** 新任务属于既有工作包，**当** 创建资产，**则** 使用该工作包的既有输入、脚本和成果边界。
2. **假设** 新任务无法归入现有工作包，**当** 需要新增工作包，**则** 先创建说明和机器描述，再创建业务资产。
3. **假设** 新资产试图写入根目录或通用 `tools`、`outputs`，**当** 执行治理检查，**则** 检查失败并指出推荐归属。

---

### 用户故事 4 - 安全识别和清理本地产物（优先级：P2）

维护者可以按持久状态、用户输入、正式成果、诊断日志、可再生成物、缓存和临时文件查看本地资产，并在不误删业务数据的情况下清理允许类别。

**优先级理由**：日志和缓存数量持续增长，但当前 `.local-data` 混合了不可删除状态和可清理文件。

**独立测试**：生成分类预览，确认每个候选文件都有类别、大小、原因和操作建议；默认运行不删除任何文件。

**验收场景**：

1. **假设** 未提供删除授权，**当** 运行清理入口，**则** 只输出预览且文件数量不变。
2. **假设** 资产属于数据库、配置、用户输入或正式交付物，**当** 选择清理缓存，**则** 该资产不会进入删除候选。
3. **假设** 日志仍可能对应运行进程，**当** 请求清理日志，**则** 在确认进程和保留边界前停止。

---

### 用户故事 5 - 保持 Demo 与项目流程可用（优先级：P2）

目录迁移后，维护者仍能使用更新后的统一入口完成安装、启动、测试、构建、验证、规格化开发和 Skill 调用，业务行为与迁移前一致。

**优先级理由**：根目录重构范围大，不能以牺牲现有 Demo 和项目流程为代价。

**独立测试**：运行冻结的后端、前端、架构、文档、部署、Spec Kit 和 Skill 发现门禁，并比较迁移前后的公开行为。

**验收场景**：

1. **假设** 代码和规格已迁入新阶段，**当** 使用根入口命令，**则** 所有命令定位到新路径且结果与冻结基线一致。
2. **假设** 历史文档或规格仍含旧路径，**当** 查阅历史内容，**则** 原文保持并由迁移记录解释旧路径。

### 边界与异常场景

- 工作包无法唯一归类时，必须先标记为待分类并停止物理迁移，不得复制到多个阶段。
- 目标路径存在同名文件或哈希不一致时，整条迁移停止，不覆盖目标。
- 当前工作树中的未提交修改和并行 043 资产必须保持内容与状态，不得被批量重写。
- 工具要求固定根路径时，允许保留最小发现入口，但业务内容必须有明确阶段所有权和兼容说明。
- 历史规格和文档中的旧路径不批量改写；当前入口和当前文档必须更新。
- 无法确认生成来源的成果必须保留并标记 `orphaned`，不得擅自删除或伪造来源。
- 二进制只能通过哈希、可读取性、索引和生成关系验证时，必须如实记录验证边界。
- 日志、缓存或临时文件清理前发现活动进程、锁文件或未知用户资产时，必须停止并报告。

## 需求（必填）

### 功能需求

- **FR-001**：仓库根目录必须以 `00-governance` 至 `06-delivery` 表达项目治理和完整产品生命周期阶段。
- **FR-002**：每个阶段必须提供目的、进入条件、退出条件、权威资产、工作包索引和相邻阶段说明。
- **FR-003**：除明确的工具发现入口、根说明和平台配置外，业务文档、脚本、代码、样例和成果必须归入唯一阶段。
- **FR-004**：每个独立工作包必须记录目的、阶段、输入、脚本、命令、成果、跟踪策略、清理等级和主要所有者。
- **FR-005**：独立 JSON 任务展示和排程结果展示必须区分可复用工具、可分发样例、真实验证输入和本地生成成果。
- **FR-006**：AI 案例总结必须形成独立交付工作包，并关联来源、脚本、草稿、当前成果和历史版本；无法确认的关系必须显式标记。
- **FR-007**：客户验证相关计划、数据、分析脚本、构建脚本、报告和结果必须按项目/主题工作包聚合。
- **FR-008**：需求、方案、Demo、验证和交付工具不得继续集中在无阶段语义的通用根目录中。
- **FR-009**：Agent 工作契约必须要求任务开始前声明阶段、工作包、资产类型、保留策略和主要所有者。
- **FR-010**：治理检查必须拒绝根目录业务资产、未知通用目录、重复主归属、无描述工作包、孤立脚本和无策略生成物。
- **FR-011**：无法匹配现有工作包的新任务必须先建立工作包入口和描述，再创建业务资产。
- **FR-012**：本地产物必须至少分为持久状态、用户输入、正式成果、诊断日志、可再生成物、缓存和临时文件七类。
- **FR-013**：清理入口必须默认只预览，并展示路径、类别、大小、归类原因和建议动作。
- **FR-014**：持久状态、用户输入和正式成果不得进入自动删除候选；日志清理必须检查活动进程和保留边界。
- **FR-015**：所有物理迁移必须提供逐资产源路径、目标路径、哈希、跟踪策略、引用影响、清理等级和回退动作，并取得执行确认。
- **FR-016**：当前入口、命令、链接、构建和测试必须切换到新路径；历史内容通过迁移记录解释，不批量改写。
- **FR-017**：目录迁移不得改变公开接口、业务规则、前后端共享契约、持久化语义、正式交付内容和可复现样例结果。
- **FR-018**：项目治理契约必须在资产迁移前显式升级，以允许生命周期阶段成为新的权威所有权边界。
- **FR-019**：Spec Kit 和 Skill 发现必须在新结构下继续可用，并为必须留在根目录的兼容入口记录原因。
- **FR-020**：清单外资产、未提交修改、用户本地文件和并行功能目录必须保持原路径、内容和跟踪状态，除非获得单独确认。

### 关键实体（涉及数据时填写）

- **生命周期阶段**：仓库第一层业务所有权，具有编号、目的、进入/退出条件和工作包索引。
- **工作包**：围绕一个可独立理解任务形成的最小维护单元，关联输入、脚本、成果和本地产物。
- **资产**：文档、代码、脚本、输入、样例、结果、交付物、日志或缓存，具有唯一主要归属和保留策略。
- **保留等级**：决定资产能否跟踪、归档、重建或清理的分类，不得把业务状态和用户输入降级为缓存。
- **迁移条目**：记录资产从旧所有权到新所有权的路径、哈希、引用、状态和回退动作。
- **兼容入口**：因工具发现或平台要求保留在根目录的最小入口，本身不拥有业务内容。

## 成功标准（必填）

### 可衡量结果

- **SC-001**：六类核心生命周期任务均能从根目录在两次目录进入内定位到唯一阶段和工作包入口。
- **SC-002**：抽样 JSON 展示、客户验证和 AI 案例三个工作包，100% 能在 60 秒内说明输入、运行命令、成果和清理边界。
- **SC-003**：六类模拟新任务的阶段、工作包、资产类型和保留策略归类准确率为 100%。
- **SC-004**：受治理范围内的业务资产 100% 具有唯一主要阶段；根目录新增业务文档、脚本、结果和日志数量为 0。
- **SC-005**：清理预览覆盖全部已登记本地产物，默认运行删除数量为 0，受保护资产进入删除候选数量为 0。
- **SC-006**：经确认的迁移条目 100% 满足源/目标、哈希、跟踪策略、引用和回退检查。
- **SC-007**：当前文档和入口中的已迁移旧路径引用为 0，历史内容和迁移映射保持可追溯。
- **SC-008**：Demo 公开行为、接口、共享契约、固定样例和正式交付物哈希零未批准变化。
- **SC-009**：后端、前端、架构、文档、部署、Spec Kit 和 Skill 发现门禁全部通过，或仅保留实施前已记录的环境限制。
- **SC-010**：任一新增工作包缺少说明、机器描述或保留策略时，治理检查能够稳定失败并给出推荐归属。

## 默认假设

- 用户确认包括把后端、前端归入 `04-demo`，把规格归入 `03-requirements`，并同步更新所有路径依赖。
- `.agents/`、`.specify/`、根入口文档和平台要求的少量配置保留在根目录，作为兼容入口而非业务所有权目录。
- 工作包的可复用源文件和批准样例可被跟踪，本地产物由工作包声明忽略或清理策略。
- 实施采用分批迁移和逐项确认，不把本次结构确认解释为删除本地资产的授权。
- 新治理结构需要同步更新 Constitution、`AGENTS.md`、`agent.md`、根 README、阶段索引、Spec Kit 脚本和仓库校验。
