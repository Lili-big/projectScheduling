# 研究结论：根目录生命周期工作区治理

## 1. 第一层采用生命周期阶段

- **决策**：根目录业务所有权使用 `00-governance` 至 `06-delivery`，不再以 `docs`、`tools`、`outputs` 作为长期第一层。
- **理由**：用户按工作阶段查找资产；当前类型目录把同一任务的材料、脚本和结果拆散。
- **已评估的替代方案**：只在 `docs` 内建立生命周期导航（已被用户否决）；保留类型目录并增加标签（无法解决根目录理解问题）。

## 2. 独立内容采用工作包

- **决策**：凡是具有独立输入、脚本和成果的内容建立工作包，并提供 README 与机器描述。
- **理由**：JSON 展示、客户验证和 AI 案例需要单独理解、运行、归档和清理。
- **已评估的替代方案**：统一放入全局 `tools`/`outputs`（脚本和成果继续失联）；按文件扩展名分目录（无法表达业务目的）。

## 3. Demo 代码实体迁入生命周期阶段

- **决策**：`backend`、`frontend`、样例、运行工具和 Demo 专用工具迁入 `04-demo`，根命令作为兼容入口。
- **理由**：Demo 是生命周期一环；只移动文档不能达到用户确认的根目录模型。
- **已评估的替代方案**：代码留根、仅做阶段索引（继续形成两套所有权）；复制代码到阶段目录（产生双源）。

## 4. Spec Kit 使用过渡式迁移

- **决策**：`.specify` 留根，规格树迁入 `03-requirements/specs`；先支持双路径，再切活动路径。
- **理由**：既满足生命周期归属，又避免在迁移中中断门禁工具。
- **已评估的替代方案**：根 `specs` 永久保留（不符合目标）；一次移动后再修工具（中间状态不可恢复）。

## 5. Skill 区分发现入口与业务所有权

- **决策**：通用 Spec Kit Skill 保留 `.agents/skills`；业务 Skill 内容归入对应阶段，根发现位置保留最小入口并验证引用。
- **理由**：Codex 需要可发现路径，用户又需要知道业务 Skill 服务哪个阶段。
- **已评估的替代方案**：全部 Skill 移走（可能无法发现）；全部保留但只写索引（业务内容仍与阶段分离）。

## 6. 本地产物按风险而非扩展名分类

- **决策**：使用 `persistent-state`、`user-input`、`formal-output`、`diagnostic-log`、`rebuildable`、`cache`、`temporary` 七类。
- **理由**：同为 JSON/Excel 的文件可能分别是数据库状态、客户输入、正式交付或可再生成结果，不能按扩展名决定删除。
- **已评估的替代方案**：整个 `.local-data` 可清理（会误删状态）；仅依赖 `.gitignore`（不能表达保留风险）。

## 7. 清理入口默认 dry-run

- **决策**：默认只列出候选；只有明确类别和执行参数才允许清理，日志还需进程检查。
- **理由**：用户要求便于清理，不等于授权删除；当前存在活动日志、用户输入和未知孤立成果。
- **已评估的替代方案**：按天数自动删除（无法判断业务价值）；完全不提供工具（持续依赖人工检索）。

## 8. AI 案例成果采用孤立关系状态

- **决策**：成果可定位但生成脚本关系不清时标记 `orphaned`，保留成果并允许后续补绑定。
- **理由**：不能虚构来源，也不能因缺少脚本删除正式或历史成果。
- **已评估的替代方案**：推断某个构建器为来源（证据不足）；把成果归缓存（风险不可接受）。
