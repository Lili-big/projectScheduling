# 功能规格：精排失败最佳努力方案

**功能目录/分支**：`005-best-effort-refinement`

**创建日期**：2026-07-04

**状态**：草稿

**输入**：用户确认口径：“当精排失败时，把强制节点（目前是里程碑）、固定工期的限制放开，基于当前资源、当前求解时间内最合理的一版精排计划。”

## 来源与评审上下文

- **来源文档**：`AGENTS.md`、`agent.md`、`README.md`、`docs/固定资源满足分支详细排程算法文档_v1.5.md`、`docs/精排目标函数算法需求文档_v3.8.md`、`specs/003-refinement-milestone-objective/spec.md`、`specs/004-normal-work-balance/spec.md`。
- **代码事实**：当前固定资源链路先运行容量快排，再运行 `solve_control_priority_schedule()` 命名资源精排；严格精排成功时主结果来源为 `current_resources_control_priority_balanced`，严格精排不可用时当前回退到 `current_resources_capacity_shortest_fallback`。最少资源候选二次精排失败时当前回退到已验证候选，来源为 `minimum_resources_refinement_fallback`。
- **评审结论**：建议推进。当前回退结果可检查资源数量和里程碑偏差，但不是“当前资源下最合理的命名资源精排计划”，会造成同结构同工序资源绑定等精排目标没有继续发挥作用。需要新增严格失败后的最佳努力精排分支。
- **与既有规格关系**：`003-refinement-milestone-objective` 中“严格精排必须满足硬里程碑”的规则继续有效；本功能只在严格精排失败后进入放松目标的兜底分支。`004-normal-work-balance` 中资源连续、路径连续、普通工程均衡等目标在最佳努力分支中继续参与排序。
- **不在范围内**：不放开工序依赖、资源互斥、资源启用数量、同结构同工序资源绑定、工作面并行上限等物理施工和资源硬约束；不改变固定资源容量快排的基准测算职责；不新增持久化表；不修改 `README.md`；不提交 git。

## 用户场景与测试

### 用户故事 1 - 固定资源精排失败后返回最佳努力精排（优先级：P1）

作为计划工程师，我希望在当前资源下严格精排无法满足强制节点或固定工期时，系统不要直接退回容量快排，而是返回一个仍遵守资源和工序硬约束、但把目标工期放松后的最合理精排方案，便于我判断“在现有资源下能做到什么程度”。

**优先级理由**：这是用户当前截图问题的直接根因。容量快排能给出可查看排程，但它不是命名资源精排结果，可能绕开精排层面的连续性和同结构同工序偏好。

**独立测试**：构造一个当前资源无法满足强制里程碑、但放松里程碑后仍可排程的场景；运行固定资源求解后，主结果应为最佳努力精排来源，并输出强制节点迟延、放松约束和严格精排失败原因。

**验收场景**：

1. **假设** 当前资源容量快排有可行结果，严格命名资源精排因硬里程碑或固定工期返回 `INFEASIBLE` 或未在时限内返回可用结果，**当** 用户运行“固定资源条件下，推算最短工期”，**则** 系统返回 `current_resources_best_effort_refinement` 作为主结果，而不是直接返回 `current_resources_capacity_shortest_fallback`。
2. **假设** 严格精排可以返回 `OPTIMAL` 或 `FEASIBLE`，**当** 用户运行固定资源求解，**则** 系统仍返回严格精排结果，不触发最佳努力分支。
3. **假设** 放松目标后的精排仍无法在当前求解时间内返回可用结果，**当** 用户运行固定资源求解，**则** 系统保留现有容量快排回退结果，并说明严格精排和最佳努力精排都未得到可用结果。

---

### 用户故事 2 - 最少资源候选精排失败时保留可解释的最佳努力候选（优先级：P2）

作为计划工程师，我希望在最少资源候选已经通过容量模型验证、但二次精排无法满足固定工期目标时，也能看到当前候选资源下的最佳努力精排版本，而不是只看到未精排候选。

**优先级理由**：该链路与当前资源精排共用“候选可行、二次精排失败、回退展示”的问题，但它不是用户本次截图的第一现场，可排在 P1 后。

**独立测试**：构造一个最少资源候选可生成、严格候选精排因固定工期或硬里程碑不可用的场景；系统应在候选资源数量不变的前提下返回 `minimum_resources_best_effort_refinement`，并保留推荐数量和目标迟延说明。

**验收场景**：

1. **假设** 最少资源候选排程已通过固定数量验证，严格候选精排失败，**当** 用户运行“固定工期条件下，推算最少资源”，**则** 系统返回该候选资源数量下的最佳努力精排结果，并标明目标未满足。
2. **假设** 候选精排严格成功，**当** 用户查看推荐方案，**则** 继续显示 `minimum_resources_control_priority_balanced`，不降级为最佳努力。
3. **假设** 最佳努力候选也无法返回可用结果，**当** 用户查看推荐方案，**则** 系统继续保留现有已验证候选回退结果，并输出失败原因。

---

### 用户故事 3 - 页面清楚区分严格满足和最佳努力（优先级：P2）

作为计划工程师，我希望页面明确告诉我当前方案是严格满足强制节点，还是放松强制节点/固定工期后的最佳努力版本，避免把迟延方案误认为目标已达成。

**优先级理由**：最佳努力方案会故意允许目标迟延，如果展示口径不清，会削弱强制节点和固定工期的业务含义。

**独立测试**：使用最佳努力结果 payload 打开前端结果区；结果来源标签、精排诊断、里程碑状态和固定工期偏差均应展示“最佳努力/目标未满足”的口径。

**验收场景**：

1. **假设** 后端返回 `current_resources_best_effort_refinement`，**当** 用户查看“精排诊断”，**则** 页面显示“最佳努力精排”，并列出严格精排失败原因和被放松的目标。
2. **假设** 最佳努力方案存在强制里程碑迟延，**当** 用户查看里程碑结果，**则** 状态仍为迟延，不得展示为已满足。
3. **假设** 后端返回既有严格精排来源，**当** 用户查看页面，**则** 页面文案保持严格精排可用于复核，不出现放松目标提示。

## 边界与异常场景

- 严格精排成功时，不运行或不展示最佳努力结果，避免让用户误以为目标被放松。
- 最佳努力分支只放松“目标类硬约束”：已匹配强制里程碑不再作为必须早于目标日期的约束，固定工期 `max_makespan_days` 或 fallback target 不再作为必须不超过的约束。
- 最佳努力分支必须继续遵守施工逻辑、任务持续时间、资源互斥、命名资源数量、同结构同工序资源绑定、资源池启用状态和工作面并行上限。
- 未匹配任务的强制里程碑继续按“未评估/诊断”处理，不作为放松目标参与罚分。
- 如果求解器返回 `UNKNOWN` 且没有可用 incumbent，系统不得伪造最佳努力结果，应保留现有回退并说明求解未得到可用结果。
- 如果严格失败是模型无效、输入缺资源或任务图错误导致，最佳努力分支不得掩盖错误，应保留错误诊断。
- 当前资源固定资源链路为 P1；最少资源候选二次精排为 P2；资源成本优化、Netlify 演示 API 和历史方案对比不进入首期实现。

## 需求

### 功能需求

- **FR-001**：系统必须先运行既有严格精排；只有严格精排未返回 `OPTIMAL` 或 `FEASIBLE` 时，才允许尝试最佳努力精排。
- **FR-002**：最佳努力精排必须复用当前资源或候选资源数量，不得自动增加资源，不得突破资源池 `quantity` 或已验证候选数量。
- **FR-003**：最佳努力精排必须放松已匹配强制里程碑的硬日期约束，并把迟延天数纳入高优先级软目标。
- **FR-004**：最佳努力精排必须放松固定工期硬约束，并把超出固定工期的天数纳入高优先级软目标。
- **FR-005**：最佳努力精排必须继续使用现有精排目标体系，包括控制节点迟延、控制缓冲、控制链等待、资源工作量均衡、资源空闲、资源路径连续、总工期和普通工程均衡。
- **FR-006**：最佳努力目标排序必须优先压低强制节点迟延和固定工期超期，其优先级不得低于普通资源均衡和普通工程均衡。
- **FR-007**：最佳努力结果必须在 `stats` 或 `objective_breakdown` 中输出来源、严格精排状态、严格失败原因、放松约束清单、目标迟延天数、固定工期超期天数和最佳努力分值。
- **FR-008**：固定资源链路的最佳努力主结果来源必须与既有回退区分，建议使用 `current_resources_best_effort_refinement`。
- **FR-009**：最少资源候选链路的最佳努力推荐结果来源必须与既有候选回退区分，建议使用 `minimum_resources_best_effort_refinement`。
- **FR-010**：当最佳努力精排也未返回可用结果时，系统必须保留现有回退行为，并增加“最佳努力精排也未得到可用结果”的诊断。
- **FR-011**：前端必须新增最佳努力来源标签和诊断文案，明确该结果是“目标放松后的精排方案”，不得把它显示为目标已满足。
- **FR-012**：相关后端测试必须覆盖严格成功不变、严格失败转最佳努力、最佳努力失败保留回退、同结构同工序资源绑定仍生效。
- **FR-013**：相关前端验证必须覆盖新来源标签、最佳努力诊断和目标迟延展示。

### 关键实体

- **严格精排尝试**：按既有硬里程碑和固定工期约束运行的 `solve_control_priority_schedule()` 结果，是最佳努力分支的前置判断。
- **最佳努力精排结果**：在当前资源或候选资源数量不变的情况下，放松目标类硬约束后得到的命名资源精排方案。
- **放松目标约束**：被从硬约束转换为软目标的强制里程碑或固定工期目标。
- **目标迟延记录**：描述目标类型、目标日期或目标天数、实际完成日期或实际工期、迟延天数和关联任务范围。
- **结果来源**：用于前后端区分严格精排、容量回退、最少资源候选回退和最佳努力精排的 `schedule_source`。
- **最佳努力分值**：用于解释最佳努力结果排序的综合指标，不承诺全局最优，除非求解状态为 `OPTIMAL`。

## 成功标准

### 可衡量结果

- **SC-001**：在严格精排可行的测试场景中，100% 保持现有严格精排来源和结果口径，不出现最佳努力标签。
- **SC-002**：在严格精排因强制里程碑或固定工期不可行、但放松目标可排程的测试场景中，100% 返回最佳努力精排来源，而不是容量快排回退来源。
- **SC-003**：最佳努力结果中，100% 输出被放松目标的迟延天数或固定工期超期天数。
- **SC-004**：最佳努力结果中，资源互斥、同结构同工序资源绑定和工作面并行上限测试全部通过。
- **SC-005**：当前资源最佳努力结果在页面上显示“最佳努力精排/目标未满足”口径，并保留里程碑迟延状态。
- **SC-006**：相关后端测试和前端构建通过，且现有严格精排、容量快排、最少资源候选回退标签不回归。

## 默认假设

- “精排失败”指严格命名资源精排未返回 `OPTIMAL` 或 `FEASIBLE`，或因硬里程碑/固定工期目标导致无可用主结果；输入错误和模型无效不应被最佳努力掩盖。
- “当前求解时间”默认表示最佳努力尝试也受当前请求配置的 `time_limit_seconds` 约束，不自动提高单次求解时间上限；由于严格尝试和最佳努力尝试是两次求解，总响应时间可能包含两次尝试耗时，实现阶段必须记录或诊断各自耗时。
- “固定工期的限制”在当前系统中主要对应强制里程碑目标、最少资源/资源成本链路的 fallback target，以及精排入口可能传入的 `max_makespan_days`。
- 最佳努力结果用于复核和决策，不等同于目标满足方案；若用户需要满足强制节点，仍应通过资源建议或人工调整资源/工艺来生成严格可行方案。
