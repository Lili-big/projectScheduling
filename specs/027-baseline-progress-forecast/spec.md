# 功能规格：基准计划、进度反馈与滚动预测

**功能目录/分支**：`027-baseline-progress-forecast`

**创建日期**：2026-07-12

**状态**：已实施并完成收敛验证

**输入**：从 AI 多方案比选产生的三个已求解方案中选择一个作为执行基准，按任务填报实际进度，结合状态日期进行未来进度预测、按期风险分析和调整方案比选。

## 来源与评审上下文

- **来源文档**：`AGENTS.md`、`agent.md`、`README.md`、`docs/基建智能计划管控中枢整体产品方案_v1.0.md`、`docs/计划发布与审批入口需求文档_v1.0.md`、`specs/022-ai-resource-scheduling-assistant/`、`specs/026-resource-plan-policy-baseline/`。
- **评审结论**：需求成立并建议推进，但应作为“基准计划确认—实际进度快照—滚动预测—调整方案—新执行版本”的完整闭环，而不是孤立的进度填报页面。
- **已确认产品口径**：基准计划必须持久化；进行中任务优先按剩余工程量和实际工效计算剩余工期，缺失时允许人工填报；历史进度允许更正但必须留痕；第一版调整方案限定为“不调整、增加瓶颈资源、关键任务优先”。
- **当前项目事实**：现有系统能生成、求解和比较三套资源方案，但三方案及求解结果主要保存在页面会话中；没有基准计划版本、实际进度快照、滚动预测和调整版本实体。
- **不在本期范围**：完整审批引擎、移动端填报、第三方进度系统同步、物资和成本实绩、复杂工艺替换、多项目资源调拨、GIS、自动发布以及由 LLM 直接决定调整方案。

## Clarifications

### Session 2026-07-12

- Q：基准计划是否跨刷新持久化？ → A：必须持久化为可跨刷新和后端重启继续使用的计划版本。
- Q：进行中任务剩余工期如何确定？ → A：优先按剩余工程量和实际工效计算，缺少可靠数据时使用人工预计剩余工期。
- Q：历史实际进度能否修改？ → A：允许更正，但保留原值、更正值、更正人、更正时间和更正原因。
- Q：第一版调整方案范围？ → A：只比较不调整、增加瓶颈资源、关键任务优先三类方案。

## 用户场景与测试

### 用户故事 1 - 选择并确认基准计划（优先级：P1）

计划工程师在三方案完成求解后，选择一个可行方案作为后续执行和进度比较的基准，并在刷新页面或重启服务后继续访问同一版本。

**优先级理由**：没有稳定基准，实际进度、偏差和预测都缺少比较对象。

**独立测试**：求解三版方案，选择其中一个可行方案形成基准版本；刷新或重启后重新加载，逐任务核对计划日期、资源分配、逻辑关系、里程碑和求解摘要。

**验收场景**：

1. **假设** 某方案求解结果为可行或最优，**当** 用户确认其为基准计划，**则** 系统生成不可被后续预测覆盖的基准计划版本。
2. **假设** 某方案尚未求解、不可行、未知或失败，**当** 用户尝试选择，**则** 系统阻止操作并说明原因。
3. **假设** 基准计划已经保存，**当** 用户刷新页面或后端重启后重新进入，**则** 系统能恢复同一版本和全部任务快照。

---

### 用户故事 2 - 按状态日期填报实际进度（优先级：P1）

现场或计划人员选择一个状态日期，对基准任务填报未开始、进行中、已完成、暂停或取消状态及相应实绩，系统校验并保存进度快照。

**优先级理由**：实际进度是滚动预测的核心事实输入。

**独立测试**：对同一基准版本提交包含五种任务状态的进度快照，验证必填字段、日期、完成量、剩余工期、冲突提示和更正记录。

**验收场景**：

1. **假设** 任务进行中且提供总工程量、已完工程量和实际工效，**当** 保存快照，**则** 系统计算完成比例和预计剩余工期。
2. **假设** 任务进行中但缺少可靠工程量或实际工效，**当** 用户填写预计剩余工期，**则** 系统接受人工值并标识来源。
3. **假设** 用户更正已保存的实际进度，**当** 提交更正原因，**则** 新快照生效且旧值和更正记录仍可追溯。
4. **假设** 实际日期、状态或工程量相互矛盾，**当** 保存快照，**则** 系统区分阻断错误与可接受警告，不静默修正事实。

---

### 用户故事 3 - 滚动预测并判断按期风险（优先级：P1）

计划工程师基于一个基准版本和最新有效进度快照发起滚动预测，查看基准、实际、预测三态，判断项目和强制里程碑能否按期完成。

**优先级理由**：这是把进度填报转化为计划决策价值的核心步骤。

**独立测试**：分别使用进度一致、关键任务延迟、资源不足、数据缺失四类快照生成预测，验证历史事实冻结、剩余任务重排、完成日期、里程碑偏差、风险和可信度。

**验收场景**：

1. **假设** 实际进度与基准一致，**当** 生成预测，**则** 预测完成日期与基准基本一致且不产生错误延期预警。
2. **假设** 已完成任务存在实际日期，**当** 生成预测，**则** 算法不得修改这些日期。
3. **假设** 某进行中任务尚有剩余工作，**当** 生成预测，**则** 仅对剩余部分及未开始任务安排状态日期之后的计划。
4. **假设** 当前资源和剩余任务无法满足强制里程碑，**当** 生成预测，**则** 系统仍返回最佳可行预测和明确的里程碑延期风险，而不是用目标日期强行压缩结果。
5. **假设** 关键进度数据缺失或过期，**当** 用户请求预测，**则** 系统降低可信度或阻止确定性结论，并列明缺失项。

---

### 用户故事 4 - 比较调整方案并形成新执行版本（优先级：P2）

当预测存在延期风险时，计划工程师比较不调整、增加瓶颈资源、关键任务优先三种未来方案，选择其中一个形成新的执行计划版本，同时保留原基准和全部历史。

**优先级理由**：风险识别之后需要形成可执行处置，但应建立在前三个故事稳定后。

**独立测试**：构造瓶颈资源导致里程碑延期的快照，分别求解三类方案，比较工期、里程碑、资源和成本；采用一个方案后验证新旧版本关系。

**验收场景**：

1. **假设** 预测存在延期风险，**当** 用户生成调整方案，**则** 系统至少返回三种策略各自的可行性、预测完成日期、里程碑偏差和资源变化。
2. **假设** 增加瓶颈资源不能带来有效收益，**当** 比较方案，**则** 系统展示边际收益不足，不因资源更多而自动推荐。
3. **假设** 用户采用一个可行调整方案，**当** 确认采用，**则** 系统创建新执行计划版本并记录来源预测、调整原因和新旧版本关系，不覆盖原基准。
4. **假设** LLM 可用，**当** 展示风险和方案差异，**则** LLM只能解释确定性结果，不得改写实际进度、求解结果或用户选择。

### 边界与异常场景

- 同一项目同一计划类型最多有一个当前生效执行版本；历史版本保留只读。
- 进度快照必须关联基准或执行版本以及唯一状态日期；同一版本同一状态日期再次提交按“更正”处理而不是无痕覆盖。
- 状态日期不能早于计划开始日期或晚于填报当天；未来实际日期不得保存。
- 完成比例不能倒退，除非走带原因的更正流程；已完成任务完成比例必须为 100%。
- 已取消任务必须有原因；其后续任务如何处理必须在预测诊断中显式说明。
- 如果任务标识在当前基准中不存在，进度不得自动挂到名称相似任务上。
- 预测结果必须记录使用的基准版本、快照、场景输入指纹和求解来源；任一输入变化后旧预测标记为过期。
- 求解无解、超时或模型无效时，各策略独立返回状态和诊断，不得用旧预测冒充新结果。
- 基准计划与最新执行版本始终可查看，任何预测和调整都不得删除历史事实。

## 需求

### 功能需求

- **FR-001**：系统必须只允许从已完成求解且状态为可行或最优的资源方案创建基准计划。
- **FR-002**：基准计划必须完整快照项目标识、方案与资源配置、任务标识、计划起止日期、工期、资源分配、逻辑关系、里程碑、求解摘要、输入指纹及确认信息。
- **FR-003**：基准计划必须持久化，并在页面刷新和后端重启后可恢复；后续预测不得修改其快照。
- **FR-004**：系统必须为计划版本提供 `draft`、`active`、`superseded` 状态，并保持同一项目同一计划类型至多一个 `active` 版本。
- **FR-005**：系统必须允许用户按状态日期创建实际进度快照，并将每条进度关联到稳定任务 ID。
- **FR-006**：任务进度状态必须至少包含 `not_started`、`in_progress`、`completed`、`paused`、`cancelled`。
- **FR-007**：进行中任务必须优先根据剩余工程量和实际工效计算剩余工期；无法可靠计算时必须要求人工预计剩余工期并记录来源。
- **FR-008**：系统必须对各任务状态执行字段校验，包括实际日期、完成比例、已完工程量、剩余工程量、实际工效、剩余工期和暂停/取消原因。
- **FR-009**：实际进度更正必须形成审计记录，保存原值、新值、更正原因、更正人和更正时间，不得无痕覆盖。
- **FR-010**：系统必须将日期倒置、未来实绩、已完成但未达到 100%、工程量越界等问题作为阻断错误；将前后置现场冲突等可接受事实作为警告并降低预测可信度。
- **FR-011**：滚动预测必须以一个计划版本、一个有效进度快照和一个状态日期为唯一输入组合，并记录输入指纹。
- **FR-012**：预测必须冻结已完成任务的实际日期；进行中任务仅预测剩余部分；未开始任务不得安排在状态日期之前。
- **FR-013**：预测必须继续执行剩余任务的工艺逻辑、资源容量、日历和合法并行约束。
- **FR-014**：预测不得用强制里程碑反向强行压缩“当前趋势”结果；必须先计算当前条件下的最早可行预测，再将预测日期与里程碑目标比较。
- **FR-015**：当前趋势预测必须保留基准资源投入和既定未来执行顺序；发生实际冲突时只向后顺延，不主动优化出一个更好方案冒充当前趋势。
- **FR-016**：预测输出必须包含项目预测完成日期、总偏差、任务三态、里程碑预测与偏差、关键线路候选、资源瓶颈、数据质量和预测可信度。
- **FR-017**：系统必须明确给出 `on_track`、`at_risk`、`late`、`insufficient_data` 四类按期判断，并提供可追溯证据。
- **FR-018**：预测输入变化时，之前的预测和调整方案必须标记为 `stale`，不得继续作为当前结论。
- **FR-019**：风险调整必须生成且只生成 `as_is`、`add_bottleneck_resources`、`prioritize_critical_tasks` 三类策略。
- **FR-020**：`as_is` 必须与当前趋势预测使用相同资源和未来顺序；`add_bottleneck_resources` 只允许增加诊断识别出的瓶颈资源且受用户确认上限约束；`prioritize_critical_tasks` 保持资源数量不变并允许重排未开始任务以优先关键线路和强制里程碑。
- **FR-021**：每个调整策略必须独立执行排程求解并返回可行性、工期、里程碑、资源增量、演示成本变化、等待和转场影响。
- **FR-022**：系统不得仅根据资源数量或 LLM 主观判断推荐策略；推荐必须基于求解结果、强制里程碑满足情况和确定性边际收益规则。
- **FR-023**：用户采用调整方案时，系统必须创建新的执行计划版本，保留原基准、来源预测、策略输入、采用原因、确认人、确认时间和父版本关系。
- **FR-024**：LLM只允许解释预测风险和调整方案差异，不得修改实际进度、求解输入、求解结果、推荐结论或计划版本状态；LLM不可用时使用本地解释。
- **FR-025**：页面必须提供基准计划确认入口、进度反馈入口、状态日期和任务填报区、三态对比区、风险摘要、调整方案卡以及历史版本入口。
- **FR-026**：页面必须覆盖加载、空态、保存成功、字段错误、冲突警告、预测中、部分策略失败、全部失败、结果过期和重试状态。
- **FR-027**：接口和前端类型必须同步覆盖计划版本、进度快照、预测请求/响应、调整方案和版本采用结果，并保持现有三方案生成与求解接口向后兼容。
- **FR-028**：本期持久化必须满足单机 Demo 的跨刷新、跨后端重启和并发写入保护；不声明为正式企业级多用户计划库。

### 算法规则

#### 输入

- 已确认计划版本及完整任务、逻辑、资源、日历和里程碑快照。
- 最新有效进度快照、状态日期、完成量、实际工效和人工剩余工期。
- 三类调整策略的受控参数。

#### 硬约束

- 已完成任务实际日期不可改变。
- 进行中任务实际开始事实不可改变，只安排剩余工作。
- 未开始任务和所有剩余工作不得早于状态日期。
- 剩余任务继续满足有效工艺逻辑、资源容量、日历和不可并行规则。
- `as_is` 保持原资源数量、已分配资源和未来任务顺序。
- 调整策略不得改变历史实绩和已完成范围。

#### 软约束与目标优先级

1. 首先保证模型有效并生成最早可行的剩余计划。
2. 在调整策略中优先降低强制里程碑迟延和项目完工迟延。
3. 在工期收益相近时，减少新增资源、演示成本、等待和转场扰动。
4. `prioritize_critical_tasks` 对关键线路和强制里程碑相关未开始任务赋予更高优先级，但不得破坏硬约束。

#### 无解与降级

- 当前趋势预测不以强制里程碑作为可行性硬门槛；超过目标日期时返回延期预测。
- 调整策略无解或超时时保留其他策略结果，并返回独立诊断。
- 缺少关键实际数据时返回 `insufficient_data`，不得输出无依据的确定性按期结论。

### 关键实体

- **计划版本**：一个持久化、不可变的任务和求解结果快照，区分基准版本、执行版本和历史版本。
- **任务基准快照**：任务在某计划版本中的计划日期、工期、资源、顺序和逻辑关系。
- **进度快照**：某状态日期下所有已填报任务的实际状态和实绩集合。
- **进度更正记录**：一次历史实绩更改的前后值和审计信息。
- **滚动预测**：基于计划版本和进度快照生成的剩余任务预测及风险结论。
- **调整方案**：某一预测之上的三类受控策略输入、求解结果和比较指标。
- **计划变更记录**：采用调整方案形成新执行版本时保存的新旧版本关系和原因。

## 成功标准

### 可衡量结果

- **SC-001**：用户可以在三方案求解完成后 3 次操作内将一个可行方案确认为基准计划，并在刷新或后端重启后 100% 恢复任务快照。
- **SC-002**：所有实际进度记录与稳定任务 ID 的关联准确率为 100%，未知任务不得自动模糊匹配。
- **SC-003**：阻断类进度错误拦截率为 100%，所有历史更正均保留完整审计记录。
- **SC-004**：滚动预测中已完成任务实际日期被改写的次数为 0，未开始任务预测早于状态日期的次数为 0。
- **SC-005**：进度与基准一致的样例中，预测不得产生虚假延期；关键任务延迟样例中，系统必须识别受影响项目或里程碑。
- **SC-006**：每次有效预测均能返回按期状态、项目完成预测、里程碑偏差和至少一条可追溯证据；数据不足时 100% 标记为 `insufficient_data`。
- **SC-007**：风险场景中三类调整策略均有独立状态；任何单一策略失败不影响其他策略结果展示。
- **SC-008**：采用调整方案后，新执行版本与父版本、来源预测和采用原因关联完整率为 100%，原基准被覆盖次数为 0。
- **SC-009**：LLM 不可用时，基准确认、进度保存、滚动预测、方案比较和版本采用五项核心流程仍可完成。

## 默认假设

- MVP 面向单机 Demo 和单一计划工程师操作，不实现正式用户权限与组织级隔离；确认人和更正人使用页面输入或本地默认身份。
- 基准计划来源限定为 AI 多方案比选中的已求解可行方案，不在本期接入其他计划导入来源。
