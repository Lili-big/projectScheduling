# 研究结论：基准计划、进度反馈与滚动预测

## 决策 1：基准保存完整快照而不是只保存方案 ID

- **决策**：保存场景快照、生成输入、求解结果、资源方案、任务日期和输入指纹。
- **理由**：任务生成规则或项目参数后续可能变化，只有完整快照能稳定比较实际和预测并复现原计划。
- **已评估的替代方案**：只保存 `scenario_id` 或方案名称无法跨版本还原任务和资源分配。

## 决策 2：MVP 使用独立版本化本地 JSON 存储

- **决策**：新增 `.local-data/plan-control-store.json`，使用 schema version、临时文件原子替换和进程内写锁。
- **理由**：与现有本地配置模式一致，不新增依赖，满足单机 Demo 跨刷新和后端重启。
- **已评估的替代方案**：浏览器本地存储无法成为后端预测的可信来源；立即引入数据库超出 MVP；追加到 scheduler-config 会混淆配置与业务历史。

## 决策 3：预测求解残余网络而不是重算整个历史

- **决策**：状态日期以前的实际事实留在历史层，CP-SAT 只处理进行中剩余部分和未开始任务，最后合并为三态结果。
- **理由**：求解器不应改写实际日期，残余网络更符合滚动计划语义并减少模型规模。
- **已评估的替代方案**：把全部历史任务固定到原模型会增加约束复杂度，并可能因现场逻辑冲突导致无谓无解。

## 决策 4：增加向后兼容的任务执行约束

- **决策**：`ScheduleInput` 增加默认空列表 `execution_constraints`，支持任务最早开始、固定开始和固定资源。
- **理由**：进行中任务应从状态日期继续，`as_is` 还需要保留原资源事实；通用执行约束也便于测试。
- **已评估的替代方案**：只增加合成逻辑边无法固定 offset 0 或具体资源；把字段直接放入 `Task` 会污染任务定义与执行状态边界。

## 决策 5：当前趋势不以强制里程碑作为硬截止

- **决策**：当前趋势先求最早可行剩余计划，再比较里程碑目标并报告迟延。
- **理由**：若继续强制目标，真正的延期场景只会返回无解，无法回答预计何时完成。
- **已评估的替代方案**：保持强里程碑可用于调整方案目标验证，但不适合无干预预测。

## 决策 6：`as_is` 保持基准资源顺序

- **决策**：从基准资源分配提取每个资源上的未来任务序列并形成顺序约束；发生实际延误时整体向后传播。
- **理由**：如果允许自由优化，所谓“不调整”可能自动得到更好排程，掩盖真实风险。
- **已评估的替代方案**：只固定资源数量仍允许求解器重排任务，不等于沿原方案执行。

## 决策 7：历史更正采用新快照加审计记录

- **决策**：同版本同状态日期更正时创建新修订，旧修订保留，另存字段级变更记录。
- **理由**：既满足现场纠错，也能追溯预测曾使用的具体快照。
- **已评估的替代方案**：原地覆盖会破坏审计与预测复现；完全禁止更正不符合现场数据治理。

## 决策 8：LLM只做解释

- **决策**：按期状态、风险、瓶颈、三策略指标和推荐均由确定性规则及 CP-SAT 结果产生，LLM 只转写解释。
- **理由**：实际进度和计划版本属于审计事实，调整方案必须可复现。
- **已评估的替代方案**：让 LLM 直接重排或推荐会绕过硬约束和版本确认。
