# 研究结论：统一工点与结构物主数据

## 1. 统一主数据边界

- **决策**：以“项目主数据版本 → 工点 → 结构物 → 构件参数”为唯一持久化层级。`ProjectModel` 改为桥梁排程投影，`GirderWorkPoint` 改为架梁路线派生视图，不再作为并列权威数据。
- **理由**：当前混乱来自桥梁结构与架梁工点分别维护并在后续映射。单一层级可以让结构物天然归属于工点，路线、方案和计划只引用稳定业务 ID。
- **已评估的替代方案**：继续保留 `project + workpoints` 并增强映射；把工点字段直接塞入 `ProjectBridge`；长期双写。前者保留两套语义，后两者分别限制非桥工点和引入一致性风险。

## 2. 旧数据结构复用方式

- **决策**：复用旧字段含义而不是旧存储形状。`ProjectBridge` 的标识、名称、排序和工点类型进入统一工点；`WorkSection` 的工区和幅别成为结构物分组属性；`StructureModel` 与 `UpperStructureComponent` 合并为统一结构物类别；`ComponentModel` 的工程量与结构参数进入构件及参数；`GirderWorkPoint` 的里程与稳定引用进入统一工点或路线派生逻辑。
- **理由**：这能保留桥梁任务生成所需信息，同时消除持久化层的桥梁专用根对象和独立架梁工点副本。
- **已评估的替代方案**：原样嵌套旧 Pydantic 模型；完全重命名并重新定义所有字段。原样复用无法统一非桥工点，完全重建会放大排程回归风险。

## 3. 本地结构化存储

- **决策**：使用 `.local-data/project-master.db` 的 SQLite 关系型存储，直接使用 Python 标准库 `sqlite3`，启用外键、事务、WAL、busy timeout 和 schema 版本；通过 `ProjectMasterRepository` 隔离具体存储。
- **理由**：用户确认本地单机 MVP 和结构化持久化。SQLite 无新增运行时依赖，支持关系约束、事务、索引和重启恢复；独立仓储接口可为未来 PostgreSQL 保留迁移边界。
- **已评估的替代方案**：继续 JSON、引入 SQLAlchemy、直接 PostgreSQL。JSON 难以维护关系约束和大快照；SQLAlchemy 对当前单库增加依赖；PostgreSQL 超出本地单机 MVP。

## 4. 与计划管控存储的关系

- **决策**：项目主数据只写 SQLite；现有 `plan-control-store.json` 继续保存计划、方案和实绩，但新记录只保存 `project_data_version_id` 与必要指纹，不再嵌入完整项目主数据版本。
- **理由**：主数据与计划生命周期不同，继续塞入 19MB 级 JSON 会扩大读写成本和一致性边界；版本引用足以支持联算和失效判断。
- **已评估的替代方案**：把所有计划管控数据一起迁入 SQLite；在 JSON 与 SQLite 双写项目版本。前者扩大范围，后者违反用户确认的不双写原则。

## 5. Excel 模板与稳定标识

- **决策**：新工作簿固定包含“填写说明、工点信息、结构物信息、构件参数”四张表；`workpoint_id`、`structure_id`、`component_id` 是稳定业务标识，名称和里程不参与对象身份判定；新模板不兼容旧文件。
- **理由**：三张数据表与领域层级一一对应，避免把多构件参数塞进一个单元格；稳定 ID 是全量快照差异和跨版本引用的前提。
- **已评估的替代方案**：单表扁平导入、名称+里程匹配、任意工作表自动理解。单表产生大量重复，模糊匹配会误判，自动理解重新引入历史导入不确定性。

## 6. 阻断导入与草稿版本

- **决策**：每次上传都保存新的 `ImportBatch`。存在阻断问题时，批次状态为 `blocked`，保存问题与来源但不物化主数据版本；无阻断时才在事务中创建 `draft` 版本及完整关系记录；相同业务内容的重复上传保存为 `unchanged` 批次并引用已有版本。用户可取消 `blocked/ready` 批次：保留批次、问题和取消审计，删除未确认草稿业务行，当前确认版本不变。首期不在线编辑无效行。
- **理由**：数据库外键和业务约束不应允许无效主数据进入版本表；导入批次已经承担可检查草稿语义。
- **已评估的替代方案**：允许无效 `draft` 进入主数据表；只在内存返回错误。前者破坏数据不变量，后者无法重启恢复和追溯。

## 7. 全量快照、差异与幂等

- **决策**：以规范化后的完整业务内容计算指纹。相同指纹创建新的 `unchanged` 批次并通过 `existing_version_id` 引用已有业务版本，不创建重复版本；不同指纹按稳定 ID 计算对象与字段级新增、修改、删除。删除存在有效方案/计划/实绩引用的对象时阻断确认。
- **理由**：全量快照必须防止漏行静默删除，也必须避免重复文件制造重复版本。
- **已评估的替代方案**：增量 upsert、按文件哈希幂等、删除自动级联。增量无法证明完整性，文件哈希会把格式变化当业务变化，级联会破坏计划可追溯性。

## 8. 版本状态与并发

- **决策**：版本状态为 `draft → confirmed → superseded`。确认操作使用单事务和期望当前版本/指纹校验；同一项目仅一个 `confirmed` 当前版本。确认新版本时原当前版本转为 `superseded`。
- **理由**：不可变快照和乐观并发可防止两个导入会话相互覆盖，符合现有版本语义。
- **已评估的替代方案**：确认版本原地修改；多个活动版本；仅用进程锁。三者分别破坏审计、造成输入歧义或无法处理多请求竞争。

## 9. 桥梁排程适配

- **决策**：确认版本通过纯适配器生成 `ProjectModel`。桥梁工点映射为 `ProjectBridge`；结构物按 `section_code + side` 形成 `WorkSection`；下部结构映射 `StructureModel + ComponentModel`；上部跨/联映射 `UpperStructureComponent`。对外共享契约继续使用现有 `project_data_version_id` 指向 SQLite 中的确认版本，完整排程输入继续使用现有 `input_fingerprint`，不新增并列的 `project_master_version_id/project_master_fingerprint`；求解器继续读取现有投影。
- **理由**：用户要求本期只做桥梁排程且不改变算法。投影能把存储重构与 CP-SAT 模型隔离，并提供固定输入等价测试。
- **已评估的替代方案**：让求解器直接查询数据库；一次性重写 `ScenarioInput` 和任务生成。两者会把存储细节带入算法或扩大本期风险。

## 10. 架梁路线工点

- **决策**：桥梁路线节点由 `workpoint_id + side` 派生，非桥路线工点直接引用统一 `workpoint_id`；路线、梁场、设备、通行条件和实绩仍属于方案/实绩领域。旧 `GirderWorkPoint` 只允许作为兼容/展示投影，不再持久化为第二套主数据。
- **理由**：一座桥梁只维护一个工点，同时路线仍需要左右幅粒度；派生节点能满足两者而不复制工点。
- **已评估的替代方案**：左右幅拆成两个工点；路线继续维护独立工点表。均与用户确认的统一层级冲突。

## 11. 前端入口与大数据加载

- **决策**：复用现有 `projectFiles` 导航槽位并将标签改为“项目主数据”，实现独立 `projectMasterData` feature。现有参数助手迁移为独立导航入口，移除桥梁结构 Excel 导入动作且不参与主数据持久化。工点列表分页/筛选，单工点按需加载结构物和构件；导入批次通过轮询或刷新读取状态。
- **理由**：复用导航标识减少全局状态改动，按需加载避免一次返回 50,000 构件；独立 feature 符合 042 架构所有权。
- **已评估的替代方案**：把全部逻辑继续写入 `Workspace.tsx`；一次加载完整版本；复用架梁专项面板。三者分别违反模块边界、影响性能或继续混淆专项与主数据。

## 12. 旧接口与数据的退役边界

- **决策**：不迁移旧数据、不兼容旧 Excel、新 UI 不调用旧结构/工点导入。为保护当前仓库回归，旧 API 若仍被内部测试依赖可短期保留为明确弃用的兼容入口，但不得读取或写入新主数据，也不得成为新流程运行依赖；实际移除可在兼容审计后完成。
- **理由**：用户明确放弃旧交互，但仓库 042 正冻结现有路由和导入契约，直接删除可能把本功能扩大为无关破坏性变更。
- **已评估的替代方案**：立即删除所有旧端点；长期保留并双写。前者与当前架构兼容门禁冲突，后者违反用户目标。
