# 研究结论：实际进度工程量一致性

## 决策 1：总工程量引用计划版本，不复制到进度快照

- **决策**：总工程量使用活动 `PlanVersion` 中对应任务的 `quantity`；展示文本使用该任务在计划确认时冻结的 `quantity_label`。`ProgressEntry` 不新增 `total_quantity`。
- **理由**：计划版本已经是进度快照的不可变基准，重复保存总量会产生双重权威来源；采用计划引用可以保证历史计划和进度始终按同一版本解释。
- **已评估的替代方案**：在每条进度中复制总工程量；会增加迁移、审计和计划调整后的歧义，拒绝采用。

## 决策 2：比例和已完量均可输入，剩余量只读派生

- **决策**：页面允许编辑实际完成比例或实际已完工程量，任一编辑立即同步另外两项；剩余工程量不可直接编辑。保存请求必须携带一致值，后端再次校验。
- **理由**：现场既存在按百分比估算也存在按实体工程量计量的场景；保留两个入口比强制单一填报口径更实用，而只读剩余量可以消除当前三个独立输入的矛盾。
- **已评估的替代方案**：只允许填百分比、只允许填已完量、增加“填报口径”下拉框；前两者限制现场用法，后者增加每行操作复杂度，均不采用。

## 决策 3：后端验证一致性，不猜测冲突请求的权威字段

- **决策**：对新保存请求，后端验证比例、已完量和剩余量的公式关系；冲突时返回可定位到任务的校验错误，不再沿用“已完量静默覆盖比例”的行为。
- **理由**：前端已即时同步，正常请求不存在冲突；服务端静默选取某个字段会隐藏其他客户端或异常状态的数据错误，降低审计可信度。
- **已评估的替代方案**：已完量优先、比例优先、剩余量优先；三种方案都会丢弃用户输入且无法解释冲突来源，拒绝采用。

## 决策 4：计算保留有效精度，展示舍入不回写

- **决策**：完成比例展示至多两位小数；数量保留任务所需有效小数。公式计算和保存使用未因展示格式化而反复舍入的数值；一致性比较允许极小的浮点误差。
- **理由**：百分比与数量互算可能产生循环小数，若每次编辑都用展示值覆盖原值，会出现累计漂移；容差校验可以避免正常浮点表示被误判。
- **已评估的替代方案**：强制所有数量两位小数、使用字符串作为权威值；会损失米制小数精度或增加模型复杂度，不采用。

## 决策 5：五种任务状态使用统一工程量矩阵

- **决策**：未开始自动为 `0% / 0 / 总量`；进行中按任一输入同步；已完成自动为 `100% / 总量 / 0`；暂停保留实绩并人工给出剩余工期；取消保留物理实绩和物理剩余量，但排程剩余工期为 0。
- **理由**：工程量描述物理完成情况，排程剩余工期描述任务是否继续执行，两者在取消状态下含义不同，不能把取消等同于物理全部完成。
- **已评估的替代方案**：取消时把剩余量置 0、暂停时清空实绩；都会破坏真实进度记录，拒绝采用。

## 决策 6：历史快照只派生展示，不静默修复

- **决策**：历史快照缺失已完量或剩余量时，页面可根据计划总量和历史比例派生显示；旧值冲突时显示质量提示。只有用户主动更正并保存时才生成新修订，原快照不重写。
- **理由**：Spec 027 已把进度快照和更正记录作为审计证据；加载时自动写回会破坏历史真实性。
- **已评估的替代方案**：启动迁移、读取时自动补齐、只展示空值；前两者破坏审计，后者不能满足四列核验目标，均不采用。

## 决策 7：不扩展 Netlify 参考 API

- **决策**：本功能只修改完整 FastAPI 计划管控链路和 React 页面，不在 `netlify/demo-functions/api.mts` 增加计划管控镜像。
- **理由**：当前 Netlify 参考 API 未实现基准计划、进度快照和滚动预测；为本功能单独复制接口会扩大范围且形成不可运行的半套能力。
- **已评估的替代方案**：同步新增 Netlify 进度接口；超出当前部署边界，不采用。
