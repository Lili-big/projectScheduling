# Phase 0 研究：固定资源方案2输出提示

## 决策：保留 `result` 作为方案1，`alternative_results` 作为方案2来源

**理由**：当前项目已经使用 `ScenarioSolveResult.result` 表示主结果，`alternative_results` 表示候选结果。继续沿用这个结构可以避免新增顶层响应模型，也能让前端已有方案切换逻辑继续工作。

**已评估的替代方案**：
- 新增顶层 `plans` 数组：结构更统一，但会影响现有前端、后端测试和兼容接口，超出本次边界。
- 只依赖前端根据 `alternative_results.length` 判断：可以实现部分展示，但无法稳定表达“方案2未输出”的原因。

## 决策：新增稳定的方案2输出状态元数据

**理由**：现有 `resource_recommendation_status` 表达资源建议状态，但它同时承担资源搜索、上限、候选验证等含义。新增一个面向展示的状态可以让前端直接判断“方案2已输出 / 未输出 / 不适用”，并保留原因类别。

**已评估的替代方案**：
- 复用 `resource_recommendation_status` 文案：实现最省，但容易让前端用字符串拼接和多分支判断，后续状态扩展风险高。
- 只追加诊断消息：用户能看到提示，但方案输出区域无法可靠决定是否展示方案2说明。

## 决策：方案2只代表最终可展示候选

**理由**：现有算法交底文档明确推荐资源候选必须经过完整目标函数复排且通过目标达成口径后才作为候选方案展示。本功能继续沿用该产品口径，避免把失败候选、最佳努力结果或容量模型诊断误展示为方案2。

**已评估的替代方案**：
- 将任意新增资源分支排程都作为方案2：信息更全，但会把未满足目标的候选误认为推荐方案。
- 展示多个候选方案：适合后续方案比选，不属于本次“有/无方案2”优化。

## 决策：不修改 `solver.py`

**理由**：本功能不改变求解模型、目标函数、硬约束或资源搜索策略，只改变固定资源分支的结果输出和页面提示。修改求解器会扩大风险面。

**已评估的替代方案**：
- 在求解器内部标记方案编号：求解器不掌握业务方案输出上下文，职责边界不合适。

## 决策：先用后端测试锁定契约，再补前端展示

**理由**：核心正确性在后端结果结构；前端只负责呈现。后端测试应先验证方案1保留、方案2成功输出、方案2未输出提示的元数据与 `alternative_results` 一致，再用前端构建确认展示代码类型和编译通过。

**已评估的替代方案**：
- 只改前端文案：无法保证接口返回的一致性。
- 只改后端测试不改前端：用户仍可能看不到“方案2未输出”提示。
