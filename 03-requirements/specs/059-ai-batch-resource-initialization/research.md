# 研究结论：AI 批量初始化工点工装资源

## 决策 1：复用现有真实 LLM 配置族，但使用严格调用语义

**决策**：复用 `AI_RESOURCE_ASSISTANT_PROVIDER`、`AI_RESOURCE_ASSISTANT_ENDPOINT`、`AI_RESOURCE_ASSISTANT_MODEL`、`AI_RESOURCE_ASSISTANT_API_KEY`、超时、温度和结构化输出配置。批量初始化要求外部 provider、endpoint、model 和 API Key 完整；缺失或调用失败直接返回失败，不使用本地回退。

**理由**：仓库已经加载根 `.local.env`，已有 OpenAI-compatible Chat Completions 客户端、响应解析和密钥隔离。继续使用同一配置族能避免用户维护重复密钥，同时“严格失败”满足用户要求的真实大模型能力。

**评估的替代方案**：

- 新增 `AI_RESOURCE_INITIALIZER_*`：隔离更强，但当前只有一个资源模型使用场景，会重复 provider、endpoint、model 和 API Key 配置，暂不采用。
- 复用三方案的本地确定性回退：会让用户误以为已调用真实模型，与需求冲突，拒绝。
- 前端直接调用模型：会暴露 API Key 并绕过后端确定性校验，拒绝。

## 决策 2：后端生成结构汇总和候选资源

**决策**：接口接收当前完整场景，路由按 `project_data_version_id` 物化权威项目模型；后端从项目投影、工艺库和资源目录生成每个工点的结构汇总与缺失候选资源。前端不上传独立候选资源清单。

**理由**：当前资源配置页的工点来自项目主数据版本，后端也已有 `derive_resource_catalog` 与 `derive_workpoint_possible_resource_types`。在后端重建上下文可防止被篡改的候选资源进入模型或校验边界，并保证后续 API 调用与排程投影一致。

**评估的替代方案**：

- 前端把 `workpointStructureSummaryProjection` 和候选资源直接提交：实现快，但前后端会出现两个权威来源且请求可被任意修改，拒绝。
- 把原始项目主数据快照完整发送给 LLM：信息冗余、上下文大且可能包含无关来源字段，拒绝。

## 决策 3：模型只决定数量，资源身份和属性由系统决定

**决策**：模型只能在每个工点的缺失候选集合中选择资源类型，并给出正整数 `quantity` 与 `max_quantity`。资源池 ID、中文标签、作用域、模式、状态、日历和适用工艺由后端确定性构造。

**理由**：资源身份、作用域和工艺兼容属于系统契约，不应交给概率模型。限制模型输出可以降低越权和幻觉风险，也便于逐记录验证。

**评估的替代方案**：

- 让模型返回完整 `ResourcePool`：字段过多，容易修改共享范围、ID、成本或日历，拒绝。
- 让模型只返回资源类型而使用固定数量：无法实现“推荐初始化资源投入”的核心价值，拒绝。

## 决策 4：整批原子校验，最多一次纠错

**决策**：模型第一次返回非法结果时，后端把结构化错误反馈给同一模型进行一次纠错；纠错仍失败则返回 422/503，整个批次不产生可应用资源。模型必须覆盖所有需要推荐的工点，允许某工点返回空资源列表并说明无需补充，但不得缺失工点或增加未知工点。

**理由**：LLM 结构化输出仍可能有偶发格式问题，一次纠错提高成功率；严格的第二次失败和原子应用保护当前资源配置，避免用户逐工点排查半成功状态。

**评估的替代方案**：

- 接受有效子集：会造成跨工点不完整且难以判断哪些结果可保存，违反整批原子规则，拒绝。
- 无限纠错：增加成本、延迟和不可预测性，拒绝。

## 决策 5：推荐进入现有页面临时状态，保存边界不变

**决策**：响应返回完整的待新增 `ResourcePool[]`。前端在核对项目版本和资源输入指纹后，通过 Workspace 一次性追加；推荐本身不持久化。用户仍在当前 ResourcesTab 的工点标签中逐个检查，点击现有保存后一次持久化完整池。

**理由**：用户明确拒绝新增全量展示，并要求逐工点确认、统一保存。复用现有脏状态和保存入口能保持任务图/求解结果失效规则一致。

**评估的替代方案**：

- 后端直接保存推荐：剥夺用户确认权并可能覆盖并发修改，拒绝。
- 新增推荐草稿数据库：当前未要求跨会话保留未保存推荐，属于过度设计，拒绝。

## 决策 6：前后端资源目录排除规则必须一致

**决策**：批量初始化候选资源沿用资源配置页的排除规则，至少排除 `precast_beam_team`；后端为此增加明确过滤和契约测试。

**理由**：当前 052 只在前端目录隐藏预制梁生产班组。如果后端不执行同一规则，模型可能生成页面不允许配置的资源，造成展示与接口冲突。

**评估的替代方案**：

- 仅依赖前端隐藏：无法防止 API 或模型越权，拒绝。
- 删除工艺库中的预制梁资源映射：会影响其他排程/梁场语义，超出范围，拒绝。

## 未解决事项

无阻塞性未知项。模型具体 endpoint、model 和 API Key 由用户在本地 `.local.env` 补充，不属于规格或计划资产。
