# 研究结论：AI 多方案按工点推进资源

## 结论

本功能没有待外部研究的阻塞未知项。用户已确认唯一关键业务语义：AI 只调整所选工点资源，但仍计算全项目排程。以下决策来自当前代码与既有资源作用域规格。

## 决策 1：目标工点必须进入共享契约

- **决定**：初始化请求携带必填稳定工点 ID；新生成的每套 `ResourceAssistantPlan` 携带目标工点 ID 与名称。
- **理由**：当前页面只有本地选择状态，后端收到的是完整场景；若目标工点不进入请求和方案，后端无法约束 LLM 输出、人工更新、迟到响应、比较、推荐和历史复用。
- **未采用**：仅在前端过滤资源行。该方式可被直接 API 调用绕过，且方案快照无法说明 AI 修改范围。

## 决策 2：方案继续携带完整资源快照

- **决定**：AI 只生成目标工点本地池的数量增量，后端把增量合并回完整 `scenario.resource_pools` 后形成三套方案。
- **理由**：现有严格固定资源求解通过 `plan.resource_pools` 替换完整场景资源；保持完整快照可继续求解全项目任务，并保留其他工点和共享池的真实容量与互斥关系。
- **未采用**：只把目标工点资源放入方案。该方式会让其他工点任务失去合法候选或被错误解释为无限资源。

## 决策 3：共享池不是目标工点可调资源

- **决定**：所有 `PROJECT_SHARED` 池在三方案中逐池冻结，即使授权范围包含目标工点；仅稳定归属于目标工点的 `WORKPOINT_EXCLUSIVE` 本地池可调。
- **理由**：共享池不归属于单个工点，数量变化会同时影响其他工点；把它当作目标工点资源会违反用户确认的单工点调整边界。
- **未采用**：允许调整“覆盖目标工点”的共享池。该方案无法隔离对其他工点的资源影响。

## 决策 4：前后端双重范围校验

- **决定**：前端只展示目标工点本地资源；后端在生成、更新和求解前按 `pool.id + workpoint_id` 验证允许范围，并逐池校验非目标资源未变化。
- **理由**：当前资源模型允许同类型多池，只有稳定池身份加工点身份能避免错误合并；后端校验同时保护 API、历史方案和人工构造请求。
- **未采用**：按资源类型比较。相同类型可能存在多个独立本地池或共享池，按类型会破坏身份和数量边界。

## 决策 5：历史模型兼容读取、禁止无身份复用

- **决定**：方案上的目标工点字段保持可空以读取历史快照；新初始化请求必须提供工点。缺失身份的历史方案可查看，但不能直接进入新的单工点更新、求解或基准确认链路。
- **理由**：直接把方案字段改为必填会破坏既有计划快照和测试夹具；完全放行又会让旧全项目 AI 方案伪装成单工点方案。
- **未采用**：按方案资源差异推断历史目标工点。该推断在共享池、多个同类池或用户手改后不可靠。

## 决策 6：全项目求解和指标保持原样

- **决定**：不裁剪 `ScenarioInput.project.bridges`、任务、关系、里程碑或指标；继续使用现有 15 秒严格固定资源入口。
- **理由**：用户明确确认只限制 AI 资源变量，不限制排程范围。完整求解才能反映目标工点资源变化对全项目工期和共享资源竞争的影响。
- **未采用**：只生成和求解目标工点任务。该能力属于另一条独立需求，不是本功能范围。
