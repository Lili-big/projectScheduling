# 研究：统一桥台任务生成、工期与资源规则

**日期**：2026-07-17

## 研究范围

本研究核对项目主数据映射、工艺库、任务生成、资源池、求解器、前端展示、历史版本与验证工作包，解决实施计划中的技术选择，不重新讨论用户已确认的产品口径。

## 决策 1：以父结构物类型驱动桥台规范映射

- **决策**：在项目主数据到排程模型的统一投影边界，使用 `structure_type=bridge_abutment` 判定桥台上下文；其中 `pile` 保持不变，其余有效构件投影为 `abutment_body`。新生成的主数据直接写入 `abutment_body`。
- **理由**：当前错误源于 `scheduling_adapter.py` 只做全局 `_COMPONENT_TYPES` 原样映射，验证工作包又把桥台台帽写成 `cap_beam`。父结构物类型是共享契约中的规范字段，能同时区分桥台主体与桥墩盖梁，不需要名称、ID、排序或数值特例。
- **已评估的替代方案**：
  - 根据“台帽”“桥台”名称替换：拒绝，违反禁止字符串硬编码。
  - 全局把 `cap_beam` 改为 `abutment_body`：拒绝，会破坏桥墩盖梁。
  - 在任务生成后改任务名称和工期：拒绝，绕过主数据、工艺库和共享契约。

## 决策 2：复用 `abutment_body_standard` 作为唯一工艺来源

- **决策**：桥台主体继续从现有工艺库选择 `abutment_body_standard`，默认值为 `fixed_days`、`count`、15 天/个，工艺名为“桥台施工”。
- **理由**：产品文档、`historical_default_process_library()` 和发布默认配置三者一致。`_PREVIOUS_BUILTIN_DEFAULTS` 中的 10 天只用于识别并升级历史内置默认，不是当前默认口径。
- **已评估的替代方案**：
  - 在适配器直接写 15：拒绝，形成第二份工期常量。
  - 前端把 10 显示为 15：拒绝，结果与求解输入不一致。
  - 新建桥台专属工艺：拒绝，现有工艺已经满足需求。

## 决策 3：不新增桥台资源池，复用资源池缺失的通用默认充足语义

- **决策**：默认场景与部署配置不新增 `abutment_team` 资源池；任务经过资源池缺失的通用处理后输出空 `compatible_resource_types`，不展开资源实例、不产生分配与等待。
- **理由**：用户在实施阶段明确“不需要增加桥台资源池”；后端 `_required_resource_types_for_task`、`expand_resource_pools` 与求解器已经支持资源池缺失的默认充足语义，无需新增配置对象。
- **已评估的替代方案**：
  - 配置 `abutment_team=UNLIMITED`：通用代码可运行，但会增加用户不需要的资源池，拒绝。
  - 设置极大资源数量：拒绝，属于特殊数值并会展开无意义具名资源。
  - 为桥台跳过资源处理：拒绝，形成桥台专属分支。

## 决策 4：历史确认快照保持不可变并统一重新投影

- **决策**：不直接更新历史 SQLite 构件行；每次任务生成和求解按当前规范重新投影。引入稳定的投影规则版本，写入投影来源和生成结果摘要；派生结果版本不匹配时标记过期并重新生成。
- **理由**：当前 API 在每个带 `project_data_version_id` 的生成/求解请求中都会加载已确认快照并调用 `project_model_from_master`，适合集中修正规范映射。直接改历史确认快照会破坏指纹、审计与版本事实。
- **已评估的替代方案**：
  - 一次性 SQL 更新 `cap_beam`：拒绝，不可审计且会误改桥墩盖梁。
  - 要求用户重新上传工作簿：拒绝，不能覆盖现有历史版本。
  - 仅修正验证工作包输出：拒绝，无法修复已确认历史数据的后续排程。

## 决策 5：投影版本使用开放元数据兼容扩展

- **决策**：投影版本写入 `ProjectBridge.import_source` 和 `GeneratedScheduleInput.source_summary` 的开放字典；需要持久化指纹的消费者把该版本纳入派生结果指纹或当前性判断。
- **理由**：两个字段已是开放字典，不需要破坏共享模型；同时能让工作台、计划版本或验证工具识别旧投影结果。
- **已评估的替代方案**：
  - 修改所有顶层请求/响应模型增加必填字段：拒绝，兼容成本过高。
  - 完全不记录规则版本：拒绝，旧结果与新结果无法可靠区分。

## 决策 6：前端只展示后端规范结果

- **决策**：任务视图和结果视图继续使用共享 `component_type` 标签、`process_name`、`duration_days` 与 `compatible_resource_types`。不新增桥台特殊换算；项目主数据详情允许按规范类型显示通用参数标签。
- **理由**：当前前端没有桥台 10/15 天专属兜底，主要风险是未来为了修正错误数据加入第二套规则。后端规范化后，前端只需补足契约/展示回归测试。
- **已评估的替代方案**：
  - 前端检测“台帽”并替换：拒绝，违反共享契约与硬编码禁令。
  - 在前端重算桥台工期：拒绝，与后端求解输入可能不一致。

## 决策 7：权威名称映射采用显式请求身份和原子状态

- **决策**：任务视图把 `project_data_version_id + sorted(unique(workpoint_ids))` 作为通用显示映射请求身份，状态至少区分 `loading / ready / error`。规范任务到达但映射未 ready 时不构建可见名称 rows；全部请求成功且身份仍为当前值后一次性提交完整映射，任一请求失败则保留错误态和重试入口，旧身份的晚到结果不得提交。
- **理由**：D05 复核确认当前首屏闪错来自异步双阶段展示：任务先到、权威工点映射后到，`buildTaskViewRows` 在中间窗口把原始 ID 与 `"-"` 当作名称。当前逐项 `catch(() => null)` 还会把部分成功映射当成 ready。显式状态和请求身份能解决加载、失败、版本切换与晚到响应，而不引入桥台业务判断。
- **已评估的替代方案**：
  - 保留原始 ID 作为加载兜底：拒绝，用户会看到错误名称闪现。
  - 每个请求成功后增量提交：拒绝，会产生权威名称、原始 ID 与占位符混排。
  - 只用 `cancelled` 布尔值：不足以表达缓存身份、快速切换和多个并发批次。
  - 根据桥台/桥墩类型决定是否等待：拒绝，问题属于所有项目主数据任务的通用展示契约。

## 决策 8：行为测试复用现有 TypeScript 工具链，不新增前端测试依赖

- **决策**：把请求身份、状态转换和晚到响应判定收敛为 taskView 领域内可独立测试的纯状态模块；Node 行为测试直接执行该生产模块的转换结果，可使用仓库已有 TypeScript 工具链完成测试加载，不以源码正则代替行为断言，也不新增 React 测试框架依赖。
- **理由**：当前 `taskView.test.mjs` 只证明源码中出现了 API 和映射函数，无法证明首屏、失败、重试或竞态结果。纯状态模块可以用可控 Promise/请求 token 复现顺序，同时保持 UI 集成轻量。
- **已评估的替代方案**：
  - 继续增加源码正则：拒绝，不能验证时序行为。
  - 新增完整浏览器测试框架：本期拒绝，范围和依赖成本高于该确定性状态问题。
  - 只做人工点击验收：拒绝，无法稳定复现旧请求晚到。

## 决策 9：旧投影结果的当前性必须有实际消费者

- **决策**：投影版本不仅写入 `ProjectBridge.import_source` 和 `GeneratedScheduleInput.source_summary`，还必须由持久化派生结果的通用读取/复用路径比较当前版本；项目主数据派生快照缺少或不匹配当前版本时标记 `stale` 或拒绝复用。非项目主数据结果保持兼容。
- **理由**：只记录版本不能满足“旧任务或旧求解结果失效”的产品要求。当前计划管控仓储已有 `stale` 状态和按指纹复用入口，可在不改历史源快照的前提下承接当前性判断。
- **已评估的替代方案**：
  - 只靠用户手工刷新：拒绝，不能证明旧结果不会混用。
  - 只在前端写死当前版本：拒绝，形成第二份规则源且静态前端无法可靠同步后端版本。
  - 删除旧结果：拒绝，破坏审计证据。

## 决策 10：用一组贯通样例证明规则统一

- **决策**：固定样例至少包含一个 `bridge_abutment` 历史 `cap_beam` 非桩构件、一个桥台 `pile`、一个桥墩 `cap_beam` 和两个可并行桥台主体任务。
- **理由**：单一桥台样例不能同时证明历史兼容、桩基不变、桥墩盖梁不变和无资源串行。
- **已评估的替代方案**：只做字符串扫描或单元测试；拒绝，无法证明端到端输出。

## 结论

所有研究问题均已解决，无待澄清项。实施必须沿用“主数据规范映射 → 现有工艺库 → 通用资源路径 → 后端规范输出 → 前端忠实展示”的单一链路。
