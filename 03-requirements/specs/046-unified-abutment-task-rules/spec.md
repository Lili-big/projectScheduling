## 用户场景与测试（必填）

### 用户故事 1 - 从项目主数据生成规范桥台任务（优先级：P1）

计划工程师选择包含桥台的已确认项目主数据版本并生成任务时，桥台下的非桩构件统一成为桥台主体任务，桩基仍按原规则生成。工程师无需根据“台帽”“盖梁”或桥台编号人工修正任务。

**优先级理由**：这是本次变更的核心价值；若主数据投影仍为 `cap_beam`，后续工期、资源和页面展示都会继续错误。

**独立测试**：使用一个同时包含 `bridge_abutment`、非桩构件和桩基构件的已确认主数据样例生成项目模型与任务，核对桥台非桩构件和桩基的规范输出。

**验收场景**：

1. **假设** 已确认项目主数据中结构类型为 `bridge_abutment` 且包含历史 `cap_beam` 非桩构件，**当** 系统生成排程项目模型，**则** 该非桩构件统一投影为 `abutment_body`，不再投影为 `cap_beam`。
2. **假设** 同一桥台下包含 `pile` 桩基构件，**当** 系统完成投影和任务生成，**则** 桩基的构件类型、工艺、工期、资源匹配和前置关系保持原有规范结果。
3. **假设** 桥墩结构下存在 `cap_beam`，**当** 系统生成任务，**则** 该桥墩盖梁仍按 `cap_beam` 规则处理，不受桥台规范映射影响。

---

### 用户故事 2 - 使用统一工艺和默认充足资源语义（优先级：P2）

计划工程师查看桥台任务时，任务统一显示“桥台施工”、15 天/个；默认配置不增加桥台资源池，并通过资源池缺失的通用默认充足语义排程，不出现桥台具名资源分配或资源等待。

**优先级理由**：规范构件类型必须继续驱动统一工艺、工期和资源链路，才能证明系统未用桥台专属分支修补结果。

**独立测试**：对一个数量为 1 个的 `abutment_body` 构件使用现有默认工艺库且不配置 `abutment_team` 资源池生成并求解，核对任务字段、资源实例、分配结果和时间安排。

**验收场景**：

1. **假设** `abutment_body` 使用现有默认工艺，**当** 系统生成任务，**则** 工艺为“桥台施工”，工效为 15 天/个，数量为 1 个时工期为 15 天。
2. **假设** 默认配置中不存在 `abutment_team` 资源池，**当** 系统生成并求解，**则** 桥台任务的 `compatible_resource_types` 为空，不展开具名资源，不生成资源分配，也不因该资源产生等待。
3. **假设** 同期存在多个桥台任务且仅受桥台资源影响，**当** 系统求解，**则** 它们不会因为 `abutment_team` 被串行化。

---

### 用户故事 3 - 历史主数据按规范映射重新投影（优先级：P3）

项目管理员继续使用历史已确认主数据版本时，系统通过统一投影规则修正其中的桥台 `cap_beam`/台帽语义，并确保旧投影结果不会被误当成当前规范结果。

**优先级理由**：已有数据不能依靠一次性手工改库或项目特例补丁；历史版本必须可重复、可审计地得到相同规范投影。

**独立测试**：准备一个已确认且仍保存 `bridge_abutment + cap_beam` 的历史快照，重复生成两次任务，核对源快照、规范投影、失效语义和结果一致性。

**验收场景**：

1. **假设** 历史已确认快照仍保存桥台 `cap_beam`，**当** 使用当前规范重新投影，**则** 排程输出为 `abutment_body`，且不要求人工逐条修库。
2. **假设** 同一历史版本被重复生成，**当** 输入和规范版本均未变化，**则** 两次规范投影和任务输出一致。
3. **假设** 已存在基于旧 `cap_beam` 投影生成的任务或求解结果，**当** 新规范启用，**则** 旧结果被识别为过期并要求重新生成，不与新结果混用。

---

### 用户故事 4 - 工作台忠实展示后端规范结果（优先级：P4）

计划工程师在工作台查看桥台任务时，页面直接展示后端返回的规范构件类型、工艺、工期和资源状态；工点、桥梁、工区与幅别使用同一 `project_data_version_id` 的权威项目主数据映射。页面不依赖桥台名称、ID、特殊字符串或特殊数值补出正确结果，也不会在权威映射到达前闪现原始 ID。

**优先级理由**：前端必须保持共享契约消费者角色，避免后端修正后仍存在第二套桥台规则。

**独立测试**：向工作台提供一组规范桥台任务，并通过可控异步请求依次覆盖映射未就绪、成功、失败、重试、版本快速切换和旧请求晚到；同时覆盖空任务结果、异常响应与硬编码扫描。

**验收场景**：

1. **假设** 后端返回 `abutment_body`、“桥台施工”、15 天且无兼容资源，**当** 用户查看任务，**则** 页面按共享标签和后端字段显示，不运行桥台专属换算或兜底。
2. **假设** 后端没有生成桥台任务，**当** 用户查看工作台，**则** 页面使用通用空态，不伪造桥台任务或默认工期。
3. **假设** 后端返回校验错误或生成失败，**当** 用户查看工作台，**则** 页面使用通用错误态，不以桥台特殊值隐藏错误。
4. **假设** 规范任务已经到达但同一 `project_data_version_id` 的权威工点映射尚未就绪，**当** 页面首次进入或刷新任务视图，**则** 使用通用加载态或骨架态，不把 `bridge_id`、`work_section_id` 或 `"-"` 当成工点、桥梁、工区或幅别名称展示。
5. **假设** 当前版本所需的全部工点映射加载成功，**当** 映射请求身份仍与当前任务一致，**则** 页面一次性提交完整映射并开始渲染任务名称信息，不出现部分新映射与原始 ID 混排。
6. **假设** 任一权威映射请求失败，**当** 页面处理该失败，**则** 使用通用错误/不可用态并提供重试，不静默吞错、不提交部分映射、不回退显示原始 ID。
7. **假设** 用户快速切换 `project_data_version_id` 或所需工点集合，且旧请求晚于新请求返回，**当** 页面接收旧响应，**则** 忽略该响应，不将旧版本映射与新版本任务混用。

### 边界与异常场景

- `bridge_abutment` 下只有桩基时，只生成原有桩基任务，不凭结构名称补造桥台主体任务。
- `bridge_abutment` 下非桩构件被禁用或工程量不大于 0 时，沿用统一构件启用与工程量校验规则，不生成桥台特例任务。
- 桥台非桩构件缺少必要的稳定标识、数量或单位时，使用项目主数据通用校验与诊断，不用名称或默认数值静默补齐。
- 非桥台结构中的 `cap_beam` 继续生成盖梁施工、10 天/个并按其现有资源规则处理。
- `abutment_team` 资源池缺失、禁用或为 `UNLIMITED` 时，均只能通过现有通用资源充足语义处理；本期规范默认不配置该资源池，不得另设桥台分支。
- 默认充足的桥台任务仍可受前置关系、里程碑或其他非资源约束影响；“无资源等待”不等于忽略这些约束。
- 历史快照保持可追溯；规范重新投影不得无记录地覆盖已确认源数据。
- 前端收到空 `compatible_resource_types` 时显示通用“无受限资源/默认充足”语义，不显示虚构的桥台班组编号。
- 规范任务已经生成但项目主数据映射尚未返回时，任务视图保持通用加载态；加载态不是“无任务”空态，也不得用 ID 或 `"-"` 冒充名称。
- 权威映射采用全量就绪后原子提交；任一工点失败时不提交部分成功结果，避免同一页面混用权威名称与原始 ID。
- 映射请求身份由 `project_data_version_id` 与规范化后的所需 workpoint ID 集合共同确定；相同身份可以复用通用缓存，不同身份不得共享 ready 结果。
- 版本或所需工点集合切换时，旧映射可以保留在独立缓存中，但不得继续作为当前任务视图的可见映射；晚到响应必须通过请求身份校验后才能提交。

## 需求（必填）

### 功能需求

- **FR-001**：系统必须以项目主数据结构物的规范 `structure_type` 判断桥台上下文；`bridge_abutment` 是本功能唯一的桥台结构判定依据。
- **FR-002**：系统必须将 `bridge_abutment` 下所有启用且工程量有效的非桩构件统一投影为 `abutment_body`；不得继续投影为 `cap_beam`。
- **FR-003**：系统必须保持 `bridge_abutment` 下 `pile` 构件及其任务生成、工期、资源、前置和标识规则不变。
- **FR-004**：系统不得根据桥台名称、构件名称、ID 前后缀、中文特殊字符串、构件排序或 10/15 等特殊数值判断或修正桥台规则。
- **FR-005**：项目主数据导入、生成或重新投影所使用的规范映射必须与 `bridge_abutment → abutment_body` 口径一致，新生成的桥台非桩构件不得再写成 `cap_beam`。
- **FR-006**：`abutment_body` 必须从现有统一工艺库选择默认工艺 `abutment_body_standard`，工艺名称为“桥台施工”。
- **FR-007**：`abutment_body_standard` 的默认工期计算必须为固定工期，数量来源为构件数量，默认工效为 15，单位为“天/个”；数量 1 个的默认工期必须为 15 天。
- **FR-008**：桥台规范映射不得改变源构件的稳定标识、项目主数据结构物/构件引用、启用状态、有效工程量和可追溯来源。
- **FR-009**：本期默认场景和部署配置不得新增 `abutment_team` 桥台资源池；资源池缺失必须通过现有通用路径表达默认资源充足。
- **FR-010**：`abutment_body_standard` 可以保留 `resource_type=abutment_team` 作为工艺资源类型元数据，但默认资源池集合中不得据此补造 `pool-abutment` 或其他桥台池。
- **FR-011**：任务生成后的桥台任务必须具有空 `compatible_resource_types`；资源池展开结果不得包含 `abutment_team` 具名资源。
- **FR-012**：求解结果不得为默认充足的桥台任务生成具名资源分配、资源等待或同资源互斥串行化。
- **FR-013**：资源池缺失的默认充足语义必须复用任务生成和求解器现有通用路径，不得通过跳过桥台任务、伪造资源、直接改开始时间或桥台专属条件分支实现。
- **FR-014**：历史已确认主数据中 `bridge_abutment + cap_beam`/台帽数据必须通过同一规范映射重新投影为 `abutment_body`；不得要求一次性手工逐条补丁。
- **FR-015**：历史源快照必须保持可追溯；如采用重新投影而非源数据迁移，系统必须能识别规范投影版本变化，并使旧任务或旧求解结果失效后重新生成。
- **FR-016**：共享契约必须同时保留 `cap_beam` 与 `abutment_body` 的合法类型：`cap_beam` 继续服务桥墩盖梁，`abutment_body` 服务桥台主体，不得全局删除或重命名 `cap_beam`。
- **FR-017**：前端必须只使用后端规范生成结果和共享标签展示桥台任务，不新增或保留桥台名称、ID、字符串、10/15 特殊值或 `cap_beam → abutment_body` 的页面兜底。
- **FR-018**：系统必须为正常、异常、兼容、空态和历史重新投影提供可复现输入与预期输出，并覆盖任务生成、工期、资源、求解和展示链路。
- **FR-019**：系统必须提供可执行的静态与行为验证，证明受影响运行链路中不存在桥台专属硬编码或特殊值分支。
- **FR-020**：回归验证必须按职责覆盖：D01 验证项目主数据映射，D02 验证任务生成、工期和资源语义，D06 复核共享契约与跨模块测试，D05 验收工作台最终显示。
- **FR-021**：任务视图中的工点、桥梁、工区和幅别名称必须来自与当前规范任务相同 `project_data_version_id` 的权威项目主数据映射；不得根据名称、ID 格式、桥台/桥墩类型、排序或特殊字符串补值。
- **FR-022**：当规范任务已经到达但当前请求身份的权威显示映射尚未就绪时，系统必须显示通用加载态或骨架态；不得将 `bridge_id`、`work_section_id` 或 `"-"` 作为最终显示名称渲染。
- **FR-023**：当前请求身份所需的全部工点映射加载成功后，系统必须原子提交完整映射再渲染任务名称；不得提交部分映射或产生权威名称与原始 ID 混排。
- **FR-024**：权威显示映射加载失败时，系统必须显示通用错误/不可用态并提供重试；不得静默吞错、伪造名称或回退显示原始 ID。
- **FR-025**：显示映射的请求与缓存身份必须由 `project_data_version_id + 规范化 workpoint IDs` 共同构成；版本或 ID 集合切换后，旧请求晚到响应不得覆盖当前映射，旧映射不得与新任务混用。
- **FR-026**：前端必须提供可执行的真实 React 组件/浏览器 DOM 行为验证，覆盖首屏未就绪、全量加载成功、任一加载失败、失败后重试、版本或规范化 workpoint ID 集合快速切换和旧请求晚到；不得以源码正则、纯协调器测试或 HTTP 结果替代页面可见性证据，所有场景中业务特例数为 0，原始 ID 冒充名称次数为 0。

### 关键实体（涉及数据时填写）

- **项目主数据结构物**：已确认版本中的结构节点，关键属性为稳定 ID、`structure_type`、所属工点、幅别、工区和构件集合。
- **项目主数据构件**：结构物下的源构件，保留稳定 ID、源 `component_type`、数量、单位、启用状态和来源参数。
- **规范排程构件**：由项目主数据通过统一映射投影得到的构件；桥台非桩构件的规范类型为 `abutment_body`。
- **工艺模板与默认工效**：按规范构件类型选择的工艺及工期规则；桥台使用 `abutment_body_standard`、15 天/个。
- **资源池**：统一资源配置对象；本期默认配置中不创建 `abutment_team` 资源池，资源池缺失由通用链路解释为默认充足。
- **生成任务**：包含规范构件类型、工艺、工期、来源引用和兼容资源类型；桥台任务的兼容资源类型为空。
- **求解结果与工作台展示**：消费规范任务并展示时间、工艺和资源状态，不建立第二套桥台规则。
- **权威显示映射**：由 `project_data_version_id` 和当前任务引用的 workpoint ID 集合标识，包含工点名称、工区名称、幅别标签、加载状态、错误和重试语义；只有当前身份的完整 ready 映射可以驱动可见任务 rows。

## 责任分工与交接

- **D01｜项目主数据与结构底座**：负责 `bridge_abutment` 非桩构件的规范映射、导入/生成口径、历史快照重新投影和项目主数据回归样例。
- **D02｜综合排程算法内核**：负责任务生成、`abutment_body_standard` 15 天/个、桥台资源池缺失的默认充足输入输出、求解无资源等待和桩基不变回归。
- **D06｜架构契约与技术质量**：复核后端/前端共享类型、接口兼容、投影版本失效、显示映射请求身份、可执行行为测试和硬编码扫描。
- **D05｜工作台与结果体验**：负责工作台按后端规范结果显示，以及权威名称映射的通用加载态、原子成功、失败重试、版本竞态隔离和无桥台专属兜底的最终验收。
- **D04｜计划管控与进度预测（依赖交接）**：仅在持久化计划/联合快照需要消费投影版本时，按 G00 路由实施仓储 `stale` 判定；D06 仍负责共享契约与回归验收，不把 D04 扩展为本功能主责。
- **L03｜需求文档与规格管理**：维护本规格、计划、任务和分析一致性；用户确认 `tasks.md` 与分析结果后再按领域交接，不直接实现。

## 成功标准（必填）

### 可衡量结果

- **SC-001**：在至少一个同时包含桥台历史 `cap_beam` 非桩构件和桩基的固定样例中，100% 的桥台非桩构件生成 `abutment_body`，100% 的桥台桩基保持原规范结果。
- **SC-002**：数量为 1 个的规范桥台任务，100% 输出“桥台施工”和 15 天工期；同一工艺库中的桥墩盖梁仍输出“盖梁施工”和 10 天工期。
- **SC-003**：在默认配置不含 `abutment_team` 资源池的固定样例中，100% 的桥台任务输出空 `compatible_resource_types`，桥台具名资源实例数、资源分配数和资源等待数均为 0。
- **SC-004**：包含至少两个无其他互斥约束的桥台任务时，求解结果不存在由 `abutment_team` 导致的串行化；重复求解的资源语义一致。
- **SC-005**：同一历史已确认 `bridge_abutment + cap_beam` 快照重复重新投影两次，规范构件、任务、工期和资源输出 100% 一致，且旧投影结果被识别为需重新生成。
- **SC-006**：共享契约、后端任务和工作台展示中的桥台构件类型、工艺名称、工期和资源状态逐项一致，页面没有额外桥台换算或兜底。
- **SC-007**：受影响运行路径的自动化扫描和代码评审发现 0 处依据桥台名称、ID、特殊字符串或 10/15 特殊数值决定规范结果的分支。
- **SC-008**：D01、D02、D06、D05 对应的正常、异常、兼容、空态与回归场景全部通过，且现有桥墩盖梁和桥台桩基测试无回归。
- **SC-009**：真实 React 组件/浏览器 DOM 中的首屏映射未就绪、加载成功、加载失败、失败后重试、版本或 ID 集合快速切换和旧请求晚到行为验证全部通过；当前 Vite 强制重载的每次 DOM 提交，以及每类场景中的 `bridge_id`、`work_section_id`、section code 或 `"-"` 冒充可见名称次数均为 0。
- **SC-010**：在真实浏览器中令任一映射请求失败的固定样例里，页面提交部分映射的次数为 0，显示通用错误/不可用态并提供一次可执行重试；点击真实重试按钮且全部请求成功后只展示完整权威映射。
- **SC-011**：在真实组件/浏览器中将两个项目主数据版本或同版本不同规范化 workpoint ID 集合的请求顺序人为倒置时，旧请求覆盖新映射的次数为 0，当前任务与显示映射的 `project_data_version_id` 一致率为 100%。

## 默认假设

- 已确认的产品口径优先于历史主数据中的 `cap_beam`/台帽记录；历史记录被视为需要规范重新投影的来源事实，不是继续沿用盖梁规则的依据。
- 已确认项目主数据版本保持只读和可追溯；优先采用统一、可版本化的重新投影策略，而不是直接改写历史快照。
- 资源池缺失只表示该工艺资源不形成有限容量约束，不取消前置关系、里程碑、日历或其他业务约束。
- 本期不新增桥台施工的成本模型；无具名资源分配意味着桥台资源成本不进入按资源实例计算的结果。
- 权威显示映射的缓存只是按版本和工点集合复用已验证数据的通用性能手段，不成为名称规则来源；没有命中缓存时仍须执行同一加载、错误和当前性契约。
