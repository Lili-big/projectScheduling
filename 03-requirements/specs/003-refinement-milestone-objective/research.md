# 研究结论：精排里程碑与工期目标函数调整

## 决策：硬里程碑在精排中直接作为硬约束

**理由**：用户明确要求“硬里程碑不应该权重控制，而直接作为必须满足的节点”。精排结果是最终可执行命名资源方案，不能返回通过高权重折中得到的硬节点晚点方案。

**已评估的替代方案**：

- 继续使用高权重惩罚：拒绝，因为会混淆硬节点和软目标。
- 只在固定资源主流程中约束硬里程碑：拒绝，因为直连精排入口也需要遵守同一业务语义。

## 决策：固定资源快排的事后评价流程不变

**理由**：当前固定资源流程需要先排出当前资源参考计划，再评价强制里程碑是否迟延，以便用户看到现有资源会晚到哪里。用户本次限定“精排时”的目标函数调整，不要求改变资源满足性判断流程。

**已评估的替代方案**：

- 将固定资源快排也改成硬约束不可行：拒绝，因为会丢失当前资源迟延诊断，且超出本次范围。

## 决策：软控制节点迟延复用 `control_node_late` 内部 ID

**理由**：保留内部 ID 能兼容已保存的目标配置和前端/后端契约；业务名称改为“软控制节点迟延”，避免继续使用“强控节点晚点”造成硬软混淆。

**已评估的替代方案**：

- 新增 `soft_control_late` 目标项 ID：拒绝，因为会引入迁移、兼容和前端配置重映射成本。
- 保留旧名称：拒绝，因为用户明确要求调整为软控制节点。

## 决策：普通软里程碑迟延只作为诊断展示

**理由**：用户明确要求“总工期及软节点偏差仅保留总工期”。普通软里程碑仍有业务提示价值，但不应影响精排工期目标。

**已评估的替代方案**：

- 删除软里程碑迟延字段：拒绝，因为结果诊断和里程碑表仍需要展示迟延天数。
- 保留软里程碑迟延在 `weighted_objective` 中：拒绝，因为会继续让用户误解总工期目标包含软节点偏差。

## 决策：`makespan_and_soft_milestone` 保留 ID，但业务口径改为“总工期”

**理由**：目标项 ID 是兼容契约；页面文案和算法公式才是用户理解目标的关键。本次不新增接口字段，因此保留 ID 最稳妥。

**已评估的替代方案**：

- 重命名 ID 为 `makespan`：拒绝，因为会破坏现有目标配置兼容。
- 在页面继续显示旧名称：拒绝，因为不符合用户要求。

## 决策：文档升级而不是覆盖旧版本正文

**理由**：当前 docs 中已有 v3.1 和 v1.1 文档，正式语义变更应升级版本并保持文件名与头部版本一致。

**已评估的替代方案**：

- 原文件内直接改不升版本：拒绝，因为算法语义发生变化。
