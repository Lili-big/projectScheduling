## 用户场景与测试（必填）

### 用户故事 1 - 精排必须守住硬里程碑（优先级：P1）

作为计划工程师，我希望进入精排后的方案不能通过权重折中去牺牲硬里程碑，这样最终展示的命名资源精排结果才不会把必须满足的合同或强制节点排晚。

**优先级理由**：硬里程碑是施工计划的必须满足条件。如果精排把它当作高权重软目标，用户会误以为不可违反的节点仍可用权重折中。

**独立测试**：准备一个包含硬里程碑的精排场景，分别验证可满足和不可满足两种情况；可满足时硬里程碑无迟延，不可满足时精排不得返回硬里程碑迟延的可行主方案。

**验收场景**：

1. **假设** 精排输入中存在匹配任务且可满足的硬里程碑，**当** 用户运行精排，**则** 返回结果中该硬里程碑 `lateness_days = 0`，且不被计入控制节点迟延目标项。
2. **假设** 精排输入中存在匹配任务但不可满足的硬里程碑，**当** 用户运行精排，**则** 系统不得通过高权重迟延罚分返回一个硬里程碑晚点的精排方案。
3. **假设** 固定资源快排阶段当前资源本身迟延硬里程碑，**当** 用户运行固定资源主流程，**则** 原有“保留当前资源参考排程并展示迟延诊断”的流程保持不变。

---

### 用户故事 2 - 软控制节点迟延由最高权重压低（优先级：P2）

作为计划工程师，我希望控制类但允许迟延的节点不再被称为强控硬节点，而是作为软控制节点用最高权重尽量压低迟延，这样既保留控制优先级，又不与硬里程碑语义混淆。

**优先级理由**：用户需要区分“必须满足”的硬节点和“极力压低迟延”的软控制节点，否则无法解释为什么有些节点可以迟延、有些节点不能迟延。

**独立测试**：准备一个软控制节点迟延场景，确认该迟延进入最高权重目标项；再准备普通软里程碑迟延场景，确认普通软里程碑只作为诊断展示。

**验收场景**：

1. **假设** 软控制节点在可行排程中出现迟延，**当** 用户运行精排，**则** 该迟延计入 `control_node_late` 对应的最高权重目标项。
2. **假设** 普通软里程碑出现迟延但不是软控制节点，**当** 用户查看结果，**则** 系统展示迟延天数和诊断罚分，但不把它纳入最高权重控制迟延目标。

---

### 用户故事 3 - 工期目标只表达总工期（优先级：P3）

作为计划工程师，我希望目标配置中“总工期”只表示项目完工跨度，不再混入软节点偏差，这样调权重时能准确理解该目标项的业务含义。

**优先级理由**：当前“总工期及软节点偏差”容易让用户误以为普通软里程碑也会影响精排工期目标。本次要把目标项和诊断项彻底分开。

**独立测试**：运行包含普通软里程碑迟延的精排场景，确认总工期目标贡献只来自项目完工跨度；前端目标配置只显示“总工期”。

**验收场景**：

1. **假设** 精排结果存在普通软里程碑迟延，**当** 用户查看目标函数拆解，**则** 软里程碑迟延只作为诊断字段展示，不进入总工期目标贡献。
2. **假设** 用户打开目标函数配置，**当** 查看工期目标项，**则** 页面名称为“总工期”，说明不再包含软节点偏差。
3. **假设** 用户查看算法文档，**当** 阅读工期目标解释，**则** 文档明确说明软里程碑迟延是诊断/展示信息，不属于总工期目标项。

---

### 边界与异常场景

- 硬里程碑没有匹配任务时，保持现有未评估/告警口径，不把未匹配节点作为硬约束阻断精排。
- 只存在普通软里程碑迟延时，不触发资源建议，不影响总工期目标项，只展示软节点诊断。
- 精排因硬里程碑硬约束无法求得可行解时，沿用现有精排失败或回退提示，不展示硬里程碑迟延的精排主方案。
- 已保存的目标函数配置继续使用现有目标项 ID，不因文案调整而失效。
- 固定资源快排仍可返回当前资源迟延硬里程碑的参考排程，用于说明当前资源不足；该参考排程不等同于最终精排方案。

## 需求（必填）

### 功能需求

- **FR-001**：精排必须把所有已匹配的硬里程碑作为必须满足的节点；硬里程碑事件不得晚于目标日期。
- **FR-002**：硬里程碑不得进入目标函数权重控制，不得计入软迟延罚分、控制节点迟延目标或总工期目标。
- **FR-003**：系统必须将“软控制节点”定义为允许迟延但具备控制属性的里程碑，包括控制层级软里程碑和显式关联控制范围的软里程碑。
- **FR-004**：软控制节点迟延必须进入 `control_node_late` 目标项，并使用当前最高权重压低迟延。
- **FR-005**：普通软里程碑迟延必须保留在里程碑结果和目标拆解诊断中，但不得参与精排目标函数。
- **FR-006**：`makespan_and_soft_milestone` 的内部 ID 必须保留，但当前业务名称和计算口径必须改为“总工期”。
- **FR-007**：总工期目标项只能按项目完工跨度计算，不得再叠加软里程碑迟延罚分。
- **FR-008**：`weighted_objective` 的解释性汇总必须与新目标口径一致，不得把普通软里程碑迟延加入工期项贡献。
- **FR-009**：前端目标函数配置必须显示“软控制节点迟延”和“总工期”，并移除旧文案中“强控节点晚点”“总工期及软节点偏差”的目标项表述。
- **FR-010**：算法文档必须同步升级，明确硬里程碑是硬约束、软控制节点是最高权重软目标、软里程碑迟延是诊断/展示字段。
- **FR-011**：固定资源快排的硬里程碑事后评价、当前资源迟延参考排程和资源建议触发条件必须保持不变。

### 关键实体（涉及数据时填写）

- **硬里程碑**：`mode="hard"` 且能匹配到任务范围的里程碑；在精排中是必须满足的硬约束。
- **软控制节点**：`mode="soft"` 且具备控制属性或关联控制范围的里程碑；在精排中是最高权重软目标。
- **普通软里程碑**：`mode="soft"` 但不属于软控制节点的提醒节点；只用于结果诊断和展示。
- **总工期目标项**：保留内部 ID `makespan_and_soft_milestone`，但业务含义为项目完工跨度。
- **目标拆解结果**：用于解释 `objective_terms_used`、`objective_weights`、`objective_breakdown` 和里程碑诊断字段。

## 成功标准（必填）

### 可衡量结果

- **SC-001**：包含可满足硬里程碑的精排测试中，100% 的成功结果都满足硬里程碑 `lateness_days = 0`。
- **SC-002**：包含不可满足硬里程碑的精排测试中，系统不会返回硬里程碑迟延的精排主方案。
- **SC-003**：软控制节点迟延场景中，`control_node_late` 目标贡献和 `weighted_objective` 均能反映该迟延。
- **SC-004**：普通软里程碑迟延场景中，总工期目标贡献只等于总工期相关贡献，不包含软里程碑迟延罚分。
- **SC-005**：目标函数配置页面和算法文档中，不再出现“强控节点晚点”“总工期及软节点偏差”作为当前目标项名称。

## 默认假设

- 保留现有目标项 ID 是兼容要求，不代表继续保留旧业务名称。
- 本次不调整 `penalty_per_day` 的数据模型含义；普通软里程碑的罚分可继续作为诊断展示。
- 未匹配硬里程碑沿用现有“未评估”处理，不新增阻断规则。
- 本次实现只覆盖本地 FastAPI/React 主链路；Netlify 演示 API 不新增精排 CP-SAT 行为。
