# 研究结论：移除资源共享模式

## 结论

本功能没有待外部调研的阻塞未知项。用户已明确：项目共享数据清空即可，求解器不需要新增忽略或拒绝共享资源的规则。

## 决策 1：在项目数据边界清理

- **决策**：默认场景、本地配置加载/保存、前端场景标准化和 Demo API 参考镜像只保留工点独享池。
- **理由**：正常项目计算统一从这些入口取得场景；清理数据后不会触发共享求解，同时不改变底层求解能力。
- **替代方案**：在 `resource_scope.py` 或 solver 中忽略 `PROJECT_SHARED`。用户明确否决，且会改变底层显式输入契约。

## 决策 2：保留共享契约和求解能力

- **决策**：继续保留 `ResourceScopeMode` 的 `PROJECT_SHARED`、共享池字段、共享候选/互斥/零转场实现及其底层测试。
- **理由**：本次只取消项目产品入口和项目数据，不要求破坏已有算法能力或公开读取兼容。
- **替代方案**：从 Pydantic/TypeScript 类型中删除共享枚举。会造成不必要的公开契约破坏，并使旧数据无法被识别和清理。

## 决策 3：加载本地配置时完成一次性持久化清理

- **决策**：本地配置发现共享池后，过滤共享记录、保留其他配置并使用现有临时文件替换完成原子写回；bundled 默认通过受跟踪 JSON 直接清空。
- **理由**：仅内存过滤会让旧共享数据长期残留并可能再次出现，不满足“已有项目数据清空”。用户已明确授权该限定删除。
- **替代方案**：等待用户下一次点击保存。无法保证已有项目立即完成数据清理。

## 决策 4：允许空资源池配置

- **决策**：本地配置请求和保存服务接受 `resource_pools=[]`。
- **理由**：仅共享项目清理后必然为空；空态是合法的“尚未配置工点资源”，后续任务按既有缺口诊断阻断。
- **替代方案**：自动创建数量为 0 的工点资源。会无依据地生成资源归属，违反不转换共享数量的要求。

## 决策 5：现有 legacy 独享迁移继续保留

- **决策**：`WORKPOINT_EXCLUSIVE` 旧记录继续先按 048 规则展开为直接工点记录，只有共享记录被删除。
- **理由**：用户要求删除共享数据，不要求丢失可无损识别的工点资源。
- **替代方案**：按是否缺少 `workpoint_id` 一概删除。会误删合法旧工点配置。

## 决策 6：派生结果通过现有指纹失效

- **决策**：前端标准化后的资源集合进入现有场景指纹；清理使旧当前任务图、求解和 AI 结果自然失效。历史保存结果不追溯修改。
- **理由**：复用现有失效机制即可形成最小闭环。
- **替代方案**：增加共享清理版本号或新缓存层。当前没有需求证据，会增加平行状态。
