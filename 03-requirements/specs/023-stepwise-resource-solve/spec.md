# 功能规格：AI资源助手分步求解与独立推荐

**功能目录/分支**：`023-stepwise-resource-solve`

**创建日期**：2026-07-10

**状态**：待计划

**输入**：用户描述：“将 AI 资源助手改为用户手动分步求解经济、平衡、抢工三套方案，并在三套结果完成后由独立按钮触发 LLM 推荐解释；保持现有 CP-SAT 规则和资源方案生成不变。”

## 来源与评审上下文（必填）

- **来源文档**：`AGENTS.md`、`agent.md`、`README.md`、`docs/AI资源配置与排程优化助手验证说明.md`、`specs/022-ai-resource-scheduling-assistant/spec.md`。
- **评审结论**：用户处于思路验证阶段，已确认采用四按钮的人工顺序操作；该改造改变前后端请求编排与页面状态，需进入 Spec Kit。
- **使用的 Demo/代码事实**：当前页面将“确认并求解”固定为全量批量请求；后端按 A、B、C 串行求解，且在同一响应中生成 LLM 推荐解释。请求超时阈值为 90 秒。现有请求已有 `solve_scope` 字段，但页面未提供单方案入口。
- **不在范围内**：不修改 CP-SAT 输入、硬约束、软约束、目标函数、资源方案生成、模型配置、超时阈值、后台任务队列、持久化、权限或部署方式。

## 用户场景与测试（必填）

### 用户故事 1 - 手动求解单个资源方案（优先级：P1）

计划工程师生成 A/B/C 三张资源方案卡后，按自己的验证顺序分别发起某一方案求解，并立即查看该方案的排程结果，不必等待另外两套方案完成。

**优先级理由**：这是消除“三方案串行累积超时”和验证不同资源投入效果的最小闭环。

**独立测试**：生成三方案后点击“求解方案 A”，验证仅 A 进入求解中、A 的结果独立显示、B/C 保持待求解。

**验收场景**：

1. **假设** 三张方案卡均待求解，**当** 用户点击“求解方案 A”，**则** 仅 A 的按钮和卡片显示求解中，B/C 仍可单独操作。
2. **假设** A 求解完成，**当** 用户查看方案卡和计划视图，**则** A 立即显示状态、指标、诊断与对应计划，B/C 不显示 A 的结果。
3. **假设** A 的请求失败，**当** 用户再次点击 A 的求解按钮，**则** 只重试 A，已完成的 B/C 结果不被清空。

---

### 用户故事 2 - 逐步查看方案对比（优先级：P1）

项目经理在每套方案完成时查看逐步形成的指标对比，能够区分“尚未求解”与“已求解但无可行结果”。

**优先级理由**：逐个展示结果是本次交互验证的核心价值，避免将等待误解为系统无响应。

**独立测试**：先完成 A，再完成 B、C；每次完成后，对比区只更新对应列，已完成列保持不变。

**验收场景**：

1. **假设** 仅 A 已完成，**当** 用户查看对比区，**则** A 显示其结果，B/C 明确显示待求解。
2. **假设** 某方案返回不可行、未知或模型无效，**当** 用户查看对比区，**则** 该方案显示状态和不可用原因，不沿用旧指标。
3. **假设** 三方案均完成，**当** 用户查看对比区，**则** 显示完整横向比较。

---

### 用户故事 3 - 手动生成完整推荐解释（优先级：P2）

项目经理确认三套方案都已完成后，手动点击“生成 LLM 推荐”，取得基于完整对比结果的确定性推荐和 AI 业务解释。

**优先级理由**：推荐解释应与耗时的求解解除绑定，并且只能基于完整横向比较产生。

**独立测试**：三方案完成前，推荐按钮不可用；三方案完成后点击该按钮，验证此时才发生 LLM 调用，且推荐结论未由 LLM 改写。

**验收场景**：

1. **假设** 任一方案仍待求解或请求失败，**当** 用户查看推荐按钮，**则** 按钮不可点击并显示缺少的方案数量。
2. **假设** A/B/C 都有一次有效求解响应（包括不可行、未知或模型无效结果），**当** 用户点击推荐按钮，**则** 系统根据完整结果生成推荐或明确输出暂无推荐原因。
3. **假设** 外部 LLM 调用失败或超时，**当** 用户点击推荐按钮，**则** 系统返回已有确定性推荐和本地解释，不影响三方案结果。

### 边界与异常场景

- 用户重新生成三方案、切换项目或变更场景指纹时，所有单方案结果、对比与推荐解释必须清空。
- 用户修改某方案资源数量时，只使该方案结果失效；完整推荐与对比结论同时失效，其他方案结果保留。
- 单方案求解完成但无可用排程时，该方案仍记为“已完成”；推荐阶段必须使用已有规则处理无可比较结果。
- 推荐请求发生网络错误时，仅推荐区显示失败和重试入口，不能清空任一方案结果。

## 需求（必填）

### 功能需求

- **FR-001**：系统必须保留“生成三方案”行为和 A/B/C 资源方案生成口径。
- **FR-002**：系统必须以“求解方案 A”“求解方案 B”“求解方案 C”“生成 LLM 推荐”四个显式操作替代原全量“确认并求解”操作。
- **FR-003**：每个方案的求解必须独立发起、独立加载、独立重试和独立更新结果；一次求解不得触发其他方案的 CP-SAT 求解。
- **FR-004**：单方案求解响应必须包含该方案的最新求解状态、排程结果、核心指标和诊断，不包含 LLM 推荐解释。
- **FR-005**：页面必须在单方案响应返回后立即展示该方案结果，并在对比区保留其余方案的现有状态与结果。
- **FR-006**：页面必须清楚区分“待求解”“求解中”“已完成但不可用”和“可用结果”。
- **FR-007**：推荐按钮必须仅在 A/B/C 都完成一次有效求解响应后可用；HTTP 或网络失败的方案不计为完成。
- **FR-008**：推荐请求必须基于三套方案的当前结果生成完整比较、确定性推荐和解释；LLM 只生成解释，不能改变推荐方案标识或规则证据。
- **FR-009**：LLM 推荐失败时，系统必须返回本地模板解释和 LLM 状态，不得使推荐请求整体失败。
- **FR-010**：修改某方案资源数量时，系统必须只失效该方案结果，并失效完整比较与推荐；其他方案结果保持可见。
- **FR-011**：已有批量求解接口在本期可保留兼容，但资源助手页面不得再调用它。
- **FR-012**：本期不得改变任一方案的 CP-SAT 算法规则、默认求解预算或前端通用 90 秒请求超时。

### 关键实体（涉及数据时填写）

- **单方案结果**：某个资源方案一次独立求解得到的状态、排程、指标和诊断；按方案标识覆盖更新。
- **方案完成状态**：页面判断方案是否已获得一次有效求解响应的状态，用于推荐按钮门禁。
- **完整推荐**：基于 A/B/C 当前结果生成的比较、确定性推荐结论与 LLM 或本地解释。

## 成功标准（必填）

### 可衡量结果

- **SC-001**：用户点击任一方案求解按钮后，页面在该请求完成时立即显示该方案结果，不等待另外两套方案。
- **SC-002**：单方案求解期间，另外两套方案始终可独立启动或保持既有结果，且其数据不被覆盖。
- **SC-003**：三方案完成前，推荐按钮 100% 不可用；三方案完成后，用户可通过一次独立操作获得推荐结果。
- **SC-004**：单方案求解请求中不发生推荐解释调用；只有点击推荐按钮才调用解释能力。
- **SC-005**：LLM 推荐失败时，用户仍能看到确定性推荐或“暂无推荐”的本地解释，且三方案结果完整保留。
- **SC-006**：修改 B 后，A/C 结果继续可见，B、完整对比与推荐显示需要更新。

## 默认假设

- A/B/C 的名称、排序、资源方案内容和 LLM 初始生成逻辑均沿用当前实现。
- 三方案“完成”指单方案服务已返回业务结果，不等同于一定存在可行排程。
- 推荐仅支持基于完整 A/B/C 集合生成；不支持阶段性推荐、任意方案组合推荐或后台自动推荐。
- 本次为本地 Demo 验证；推荐请求可使用页面持有的当前方案结果，不新增服务端持久化。
