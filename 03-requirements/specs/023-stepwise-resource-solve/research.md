# 研究结论：AI资源助手分步求解与独立推荐

## 决策 1：新增单方案求解入口

- **决策**：为单个资源方案提供独立求解入口，直接复用现有 `_solve_single_plan` 和 CP-SAT 调用链。
- **理由**：当前批量服务按 A/B/C 串行调用，并在循环后生成推荐；即使传入 `solve_scope`，仍会产生完整批量响应并执行解释。独立入口才能保证一次按钮只触发一次求解。
- **已评估的替代方案**：仅让页面向现有批量接口传 `solve_scope`。不采用，因为推荐仍在同一请求中执行，且无法自然合并旧结果。

## 决策 2：对比与推荐分为两个无求解/有 LLM 的入口

- **决策**：单方案结果返回后，页面调用轻量对比入口刷新当前已完成方案的指标；推荐入口只在三方案均完成时由用户点击。
- **理由**：保持指标定义和不可用原因由后端统一计算，同时让对比刷新不触发 CP-SAT 或外部 LLM。
- **已评估的替代方案**：前端复制指标行生成逻辑。不采用，避免与后端指标口径漂移。

## 决策 3：以页面内存作为本轮结果来源

- **决策**：对比与推荐请求携带当前三套资源方案和已完成结果；服务端不保存会话状态。
- **理由**：项目当前为无状态 Demo，页面已持有方案与结果，新增持久化超出验证范围。
- **已评估的替代方案**：服务端缓存任务或数据库保存。暂不采用，避免引入过期、清理和跨项目隔离问题。

## 决策 4：完整推荐以“已得到业务响应”为门槛

- **决策**：可行、不可行、未知和模型无效都属于已完成；网络或 HTTP 失败不属于已完成。只有 A/B/C 都完成时推荐按钮可用。
- **理由**：确定性推荐规则需要完整横向信息，并能对不可比较结果返回“暂无推荐”。
- **已评估的替代方案**：基于部分方案输出阶段性推荐。用户已明确不采用。
