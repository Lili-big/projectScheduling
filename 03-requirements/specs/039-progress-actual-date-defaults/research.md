# 研究与决策：实际进度日期默认赋值

## 决策 1：默认日期是前端建议草稿，不是后端静默补值

- **决策**：只在用户主动切换任务状态时生成建议，并在保存前允许编辑；后端不自动补实际日期。
- **理由**：实际日期是可审计现场事实。用户可见、可修改、主动保存的建议既降低录入成本，又不制造未经确认的事实。
- **已评估的替代方案**：后端保存时补值会让请求与落库事实不一致；页面加载即补值会污染历史快照语义，均不采用。

## 决策 2：计划日期只取活动计划的求解快照

- **决策**：按 `task_id` 关联 `PlanVersion.schedule_result_snapshot.tasks`，读取 `start_date` 和 `finish_date`。
- **理由**：该快照是被确认为执行基准的真实排程结果；`generated_snapshot.schedule_input.tasks` 只有任务工期，没有最终排程日期。
- **已评估的替代方案**：用项目开始日期加偏移重算会复制排程逻辑并产生口径漂移；用预测日期会混淆基准计划和未来预测。

## 决策 3：日期上限取状态日期与系统当前本地日期的较早值

- **决策**：`cutoff = min(statusDate, localToday)`，其中 `localToday` 按浏览器本地年月日生成，不使用 `toISOString()` 的 UTC 日期。
- **理由**：状态日期表达数据截止日，系统当前日期防止建议未来实际；本地日期避免中国时区午夜附近出现前一日偏差。
- **已评估的替代方案**：只用状态日期无法防止未来日期；只用系统日期无法正确处理历史补报；UTC 截断不符合本地业务日。

## 决策 4：建议来源采用会话级逐字段标记

- **决策**：每个任务分别记录实际开始和实际完成是否仍为自动建议。用户修改某字段后取消该字段标记；状态日期变化只重算仍有标记的字段。
- **理由**：`ProgressEntry` 没有来源字段，新增持久化字段会扩大共享契约和迁移范围。会话级标记足以区分本次建议与服务端已保存事实。
- **已评估的替代方案**：通过“当前值是否等于公式值”推断来源会误判用户恰好填写相同日期；增加后端来源字段超出本次目标。

## 决策 5：状态转换遵循最小写入和既有清理规则

- **决策**：进行中/暂停只补空的实际开始；已完成补空的实际开始和完成；未开始清空两项；取消不生成建议；从已完成切换到非完成状态继续清空实际完成。已有人工或历史实际开始不覆盖。
- **理由**：与现有状态必填校验和状态转换行为一致，并满足“只补空值”的事实保护要求。
- **已评估的替代方案**：每次切换都重算会覆盖事实；保留非完成状态的实际完成会与后端状态语义冲突。

## 决策 6：保存与加载是建议来源的事实边界

- **决策**：历史快照加载、页面刷新、项目切换和保存成功后均清空建议标记；服务端返回日期一律视为已保存事实。
- **理由**：建议来源不持久化，且保存后日期已通过用户确认和后端校验，不能再随状态日期自动变化。
- **已评估的替代方案**：跨刷新恢复标记需要新增存储字段或浏览器持久化，容易把旧建议错误带入新修订。

## 决策 7：使用 Node 24 内置测试运行器验证纯函数

- **决策**：将日期规则放入不依赖 React/DOM 的 TypeScript 模块，使用 `frontend/tests/*.test.mjs` 和 `node --test` 直接验证；生产构建继续由 `tsc && vite build` 验证。
- **理由**：当前前端没有 Jest/Vitest，Node 24 已能直接加载可擦除类型的 TypeScript；该方案不新增依赖且能执行真实规则。
- **已评估的替代方案**：只做构建无法验证日期矩阵；引入 Vitest 对本次小范围规则过重；浏览器手工验证保留为端到端补充而非唯一证据。

## 无待澄清项

规格中的日期公式、状态矩阵、人工保护、历史兼容、计划日期来源和保存边界均已确定，不存在 `NEEDS CLARIFICATION`。
