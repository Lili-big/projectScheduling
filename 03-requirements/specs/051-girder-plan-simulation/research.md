# Phase 0 研究结论：架梁计划推演

本阶段没有外部资料或依赖需要新增检索；阻塞性决策均可由已确认需求、当前项目主数据契约和现有架梁模块事实解决。

## 决策 1：新路径与现有架梁专项完全分离

- **决策**：新增独立方案、计算服务、API、页面和持久化状态；只引用相同项目主数据稳定 ID，不写回现有 `GirderPlanningConfig`、专项版本、联合快照或计划版本。
- **理由**：用户明确要求两条计算路径，现有页面先不动，新结果首期是独立策划成果。独立生命周期还能避免新页面输入变化使现有联合计算结果失效。
- **已评估替代方案**：直接扩展 `GirderPlanningPanel`；向 `PlanControlStore` 增加新列表；把新结果转换为现有专项版本。三者都会扩大现有路径影响面或模糊确认与发布语义，首期不采用。

## 决策 2：线路图以确认项目主数据为唯一事实源

- **决策**：直接读取 `ProjectMasterSnapshot`；按 `alignment_code` 分组，以 `start_mileage_m`、`end_mileage_m` 和 `sort_order` 形成同一走廊的有序节点和相邻连接。缺少里程、区间反转、重叠冲突、断点和多义连接形成诊断，不能沿用当前把缺失里程折算为 0 的兼容投影。
- **理由**：当前 `ProjectMasterWorkpoint` 已提供工点类型、线路编码和起止里程；新功能需要区分真实 0 里程与数据缺失，并解释自动补齐路径。
- **已评估替代方案**：复用现有 `derive_route_workpoints()` 的扁平列表；引入 GIS/道路图；只按 `sort_order` 串联。前者丢失缺失里程语义，GIS 超出范围，单用排序号无法验证里程与走廊一致性。

## 决策 3：多义连接使用方案级人工确认，不反写主数据

- **决策**：线路图自动生成确定性相邻边；断点、支线或多个可达通道由方案中的连接覆盖记录确认。覆盖必须记录两端节点、方向、移动天数、原因和确认人，并进入输入指纹。
- **理由**：用户要求中间工点自动补齐，但仅凭里程无法可靠判断支线、便道和掉头连接；人工确认是安全默认，又不改变项目主数据权威事实。
- **已评估替代方案**：静默选择里程最短路径；把连接修改写回项目主数据；首期实现全自动路径搜索。静默选择不可解释，写回越过主数据确认流程，全自动搜索超出固定人工顺序 MVP。

## 决策 4：排序对象为桥梁＋幅别，需求量按梁型聚合

- **决策**：从确认快照的桥梁上部结构提取左右幅、梁型、分跨和梁片数量，按“桥梁＋幅别”生成待架目标，保留分跨明细用于计算总片数和结果追溯。缺少左右幅、梁型或片数时阻断片级计划。
- **理由**：用户手工排序的是待架桥梁而不是全部路桥隧节点；当前架梁业务也以桥梁＋幅别作为稳定路线节点，而生产和架设单位已确认使用片。
- **已评估替代方案**：按单跨排序；按整座桥不分幅排序；允许缺失数量时默认 1 片。单跨排序增加前期操作量，整桥排序不能表达换幅，默认数量会产生伪精确结果。

## 决策 5：采用确定性逐日事件仿真，不引入 CP-SAT

- **决策**：固定人工顺序后，按自然日推进分梁型生产、期初库存、架设消耗、线路串行、转场、换幅和跨线路通行依赖，计算最早可行日期。先构建路线/通行依赖图，循环时直接阻断；无循环时按事件可用日推进。
- **理由**：本功能没有自动改序或资源组合决策，目标只有固定顺序下最早可行；确定性仿真更容易复现库存台账和控制原因，也不会影响通用 CP-SAT 求解器。
- **已评估替代方案**：复用现有专项 `route_simulator`；调用综合排程 CP-SAT；单纯用总片数除以能力。现有模拟器单位和结果生命周期不同，CP-SAT 增加不必要复杂度，平均除法无法保证逐日库存不为负。

## 决策 6：采用保守日界与可解释库存台账

- **决策**：当日生产在日末入库，从下一自然日开始可用于架设；当日架设消耗不得超过日初库存和片日架梁能力。台账保存日初库存、当日产量、当日消耗和日末库存。
- **理由**：该口径不依赖班次、运输时点和当天即时供梁假设，适合作为前期策划的保守默认，并能通过固定样例复现。
- **已评估替代方案**：当日产梁当日可用；整桥所需梁片全部到齐后再开架。前者需要班次和运输细节，后者过于保守且无法体现流式生产与架设。

## 决策 7：交付控制日期是结果，不反向改变架梁计划

- **决策**：先根据生产、能力和通行依赖生成最早可行架梁计划，再由工点首次使用日扣减对应缓冲得到最晚交付日期；现有项目计划完成日晚于控制日时只形成风险诊断。
- **理由**：用户要用架梁计划倒排路桥隧交付目标。若再用当前计划完成日推迟架梁，会把目标日期和现状日期混为循环输入。
- **已评估替代方案**：把项目当前计划完成日作为硬约束；自动修改项目计划；把控制日期写成现有综合排程软目标。三者均改变了独立策划成果的边界。

## 决策 8：独立 JSON 状态仓储与稳定指纹

- **决策**：方案版本和计算快照保存到 `.local-data/state/girder-plan-simulation-store.json`；复用现有 `state_path()`、稳定 ID/指纹和原子写入模式，按输入指纹复用非失效快照。
- **理由**：该数据是本地持久业务状态，不是缓存；独立文件可避免扩大 `PlanControlStore` 并便于验证现有专项完全不变。
- **已评估替代方案**：写入项目主数据 SQLite；扩展 plan-control JSON；只保存在浏览器。项目主数据不应承载策划结果，plan-control 会扩大失效链，浏览器状态不能支持版本追溯。

## 决策 9：新契约使用独立领域文件和 API 命名空间

- **决策**：后端契约位于 `contracts/girder_plan_simulation.py`，前端契约位于 `contracts/girderPlanSimulation.ts`，API 使用 `/api/girder-plan-simulation/...`；新 router 由 `bootstrap.py` 注册并同步演示镜像与架构契约。
- **理由**：当前 contracts 已支持领域文件，新能力没有历史兼容负担；独立命名可阻止调用方误把结果当作现有专项或综合排程结果。
- **已评估替代方案**：继续扩大 `_models.py`；加入 `/api/girder-planning` 路由组；复用现有专项 API 响应。三者都会模糊边界或增加无关冲突。

## 决策 10：前端作为独立 feature 组合

- **决策**：新增 `features/girderPlanSimulation/`，由 `WorkspaceNavigation.tsx` 和 `Workspace.tsx` 接入；线路图、梁场配置、人工排序和结果分别由内部组件承担，使用 feature 自有样式和 API client。
- **理由**：现有 `features/girderPlanning/` 保持不动，独立 feature 可以做边界测试并避免共享可变状态。
- **已评估替代方案**：在现有面板增加模式切换；复用现有 `RouteEditor`；把全部内容写入 `Workspace.tsx`。这些方案会直接影响现有页面或继续扩大工作区组合文件的业务职责。
