# 研究结论：工点级资源配置

日期：2026-07-17

## 1. 当前实现事实

- `ScenarioInput.resource_pools` 是项目级平铺列表，`ResourcePool` 只有资源类型、模式、数量、上限、日历、启用、成本和并行规则，无工点作用域。
- `generate_schedule_input_from_scenario` 先按资源类型写入任务候选，再按 `quantity` 或 `max_quantity` 展开全项目命名资源。
- `Resource` 只有 `pool_id/type` 等字段；求解器 `_resource_candidates_by_task` 只按类型筛选，资源组按 `pool_id or type` 聚合。
- 同一命名资源通过 `NoOverlap` 或等价容量约束避免重叠；因此现有项目级池事实上是全项目共享资源。
- 固定工期最少资源底层容量变量下界从 0 和推导最小值开始，并非天然受 `quantity` 限制；产品文档旧表述存在漂移。
- 资源页和 AI 资源助手按资源类型编辑；本地配置按资源池 ID 合并，计划/AI 快照保存完整资源池。

## 2. 决策 1：扩展现有 ResourcePool，而非新增平行顶层模型

**决定**：在 `ResourcePool` 增加 `scope_mode`、`authorized_workpoint_ids` 和 `workpoint_overrides`。

**理由**：保持 `ScenarioInput.resource_pools`、现有端点和历史快照为单一权威源；全局默认与工点覆盖可以同一对象表达。

**拒绝的替代**：

- 新增独立 `workpoint_resource_configs` 顶层列表：会让全局池和工点配置形成两个权威源，保存、AI 和快照容易漂移。
- 为每个工点复制完整 `ResourcePool`：共享模式难以表达，且数量/成本/日历重复。

## 3. 决策 2：先解析 EffectiveResourcePool

**决定**：场景生成阶段把资源池标准化成内部 `EffectiveResourcePool`：共享模式每种资源一个有效池，独享模式每个获准工点一个有效池。

**理由**：命名资源展开、成本组、数量建议和诊断均可复用同一中间结构，避免不同求解入口各自解释继承。

**关键规则**：无覆盖即继承；集合去重排序；未知/旧版本工点报错；显式空获准集合无可用工点。

## 4. 决策 3：Resource 显式携带工点作用域

**决定**：命名资源增加 `scope_mode`、`eligible_workpoint_ids`、`exclusive_workpoint_id`。

**理由**：`ScheduleInput` 必须是可独立求解的完整输入；求解器不应回读 `ScenarioInput` 或 UI。

**拒绝的替代**：解析 `Resource.id` 中的工点 ID。ID 只用于唯一性和诊断，解析字符串会违反统一规则源和兼容性。

## 5. 决策 4：未配置工点不再被误判为默认充足

**决定**：工点没有 override 时必须继承全局默认。对已启用、`LIMITED` 且有效上限大于 0 的有效池，无候选或失配工点产生阻断诊断；显式停用、`UNLIMITED` 或零上限继续沿用既有统一默认充足 warning。

**理由**：上游只明确修正“未配置工点”的语义，并未授权改变显式停用/无限/零上限的既有行为；该边界避免无意扩大需求。

## 6. 决策 5：三类数量边界分离

**决定**：

- 固定资源最短工期：固定容量 `quantity`；
- 增配建议：离散搜索 `[quantity,max_quantity]`；
- 固定工期最少资源：上界 `max_quantity`，下界 0 + 求解推导必要下界，不读 `quantity`。

**理由**：`quantity` 是当前默认投入，不是最低允许投入。新增 `min_quantity` 会创造未确认业务概念。

## 7. 决策 6：现有项目池兼容为 PROJECT_SHARED

**决定**：缺少新字段的旧资源池统一按项目共享、全部当前桥梁工点、无覆盖读取。

**理由**：这与当前全项目命名资源候选和互斥语义一致，能无损兼容。

**迁移方式**：统一 Pydantic/前端标准化和本地配置 schema 升级；不直接改历史 JSON，不写项目 ID 特例。

## 8. 决策 7：项目共享转场只提示，不建模

**决定**：共享资源跨工点仍只受资源互斥；MVP 转场持续时间和成本均为 0，并在配置页、结果页、诊断中明确。

**理由**：非零转场需要路径、距离、到离场和审批等新业务输入，属于明确排除范围。

## 9. 决策 8：AI 只建议数量，不改变作用域

**决定**：AI 上下文和方案保留作用域；共享池输出项目数量，独享池输出工点数量。旧 map 输入只兼容共享，新结构化更新承载独享。

**理由**：作用域是用户配置决策，不应由模型推断。继续只按 type 输出会丢失独享工点维度。

## 10. 决策 9：语义字段全部进入指纹

**决定**：作用域、获准工点、覆盖、数量、上限、启用和日历进入场景、AI 方案、计划版本和结果复用指纹；集合先标准化。

**理由**：任何一项变化都可能改变候选、容量或分配。旧结果保留审计，但不能作为当前结果复用。

## 11. 无需澄清项

上游已明确作用域、继承、数量、转场、兼容和排除范围。技术设计可在不新增业务规则的前提下完成，无需制造澄清问题。
