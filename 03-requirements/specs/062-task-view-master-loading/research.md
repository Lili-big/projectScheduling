# 研究结论：任务视图权威主数据快速加载

## 决策 1：使用任务视图专用最小批量投影

- **决定**：为一个主数据版本和一组规范化工点 ID 提供一次批量读取，返回工点与工区/幅别显示所需的最小字段。
- **理由**：当前任务视图只使用工点名称、顺序以及结构物的 `section_code`、`section_name`、`side`、`sort_order`。完整工点详情中的构件、参数、备注和来源证据没有被任务视图消费。
- **替代方案**：继续并发逐工点详情并增加浏览器并发或缓存。该方案仍会在首次加载时重复构建完整版本快照，无法消除 30 秒级根因，拒绝。
- **替代方案**：一次下载完整版本快照。虽然只有一次请求，但仍携带大量无关构件和参数，不满足最小载荷目标，拒绝。

## 决策 2：使用 POST 承载批量只读请求

- **决定**：使用 `POST /api/project-master/versions/{version_id}/task-view-display-map`，请求体携带 `workpoint_ids`。
- **理由**：项目主数据性能基线可达 500 工点，查询字符串存在长度限制；请求体能稳定表达集合且不要求持久化副作用。
- **替代方案**：GET 重复查询参数。小集合可用，但规模增长后受 URL 长度和代理限制，拒绝。

## 决策 3：后端精确查询，前后端双重完整性校验

- **决定**：仓储只查询请求版本下的目标工点和含有效 `section_code` 的结构物；后端发现缺失工点时整体返回稳定 404，前端校验响应版本与工点集合后才提交。
- **理由**：后端校验能避免部分业务结果，前端校验能防止错误代理响应、契约漂移或竞态结果进入 DOM。两层校验使用不同证据，且都属于数据完整性边界。
- **替代方案**：允许部分成功并逐步补齐。该方案违反既有原子展示和原始 ID 零泄漏规则，拒绝。

## 决策 4：保留协调器状态机，只替换 loader 粒度

- **决定**：继续使用 `loading/ready/error`、请求身份、成功缓存、generation/token 和 retry；loader 改为一次接收版本与完整工点集合并返回批量映射。
- **理由**：现有状态机已覆盖原子提交、缓存和旧响应隔离，最小修改即可消除 N+1 请求。
- **替代方案**：重写 TaskViewWorkspace 或引入全局请求库。当前需求没有新状态管理能力或依赖证据，拒绝。

## 决策 5：精确优化单工点详情但保持响应语义

- **决定**：让现有 `get_workpoint(version_id, workpoint_id)` 使用按单个 ID 的精确查询并继续返回完整工点详情。
- **理由**：该接口仍被资源配置等页面使用；保留字段和错误语义可避免兼容破坏，同时消除其每次构建完整版本快照的问题。
- **替代方案**：本期不碰单工点实现。批量任务视图虽可变快，但遗留的明显全快照缺陷仍影响其他调用者，且精确查询可复用同一仓储筛选逻辑，拒绝。

## 无新增未知项

语言、框架、存储、错误结构、任务视图显示字段、运行基线和测试入口均可由现有代码与规格确定；没有需要外部调研或用户澄清的阻塞项。
