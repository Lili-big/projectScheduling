# Phase 0 研究结论：架梁专项与综合排程融合

## 1. 正式计算的权威位置

- **决策**：架梁校验、产存梁、路线推进、通道、唯一归属和倒排全部迁入主后端，前端只负责配置、调用、展示和确认；原 TypeScript 实现仅用于生成黄金样例。
- **理由**：计划版本、综合任务、CP-SAT 和滚动预测均在主后端，单一权威实现可以避免浏览器与服务端结果不一致，也能保证发布结果可复现。
- **已评估的替代方案**：保留前端计算并把结果上传；启动独立 Node 服务；长期双引擎运行。三者都会扩大部署和一致性风险，拒绝采用。

## 2. 领域边界与现有求解器的关系

- **决策**：新增独立 `girder_planning` 领域包、任务适配服务和联合编排服务；现有 `solver.py` 继续只处理通用任务、资源、日历、前后置和目标函数。
- **理由**：库存日序列、路线经过和通道释放不是通用 CP-SAT 模型职责，直接塞入 `scenario.py` 或 `solver.py` 会使测试和后续演进失控。
- **已评估的替代方案**：把所有架梁逻辑放入 `scenario.py`；把库存和路线全部建成 CP-SAT 变量。前者耦合过高，后者首期模型规模和解释成本过大。

## 3. 统一模型与持久化版本

- **决策**：在现有计划管控存储中增加 `ProjectDataVersion`、`PlanningScenarioVersion` 和 `IntegratedCalculationSnapshot`；发布的 `PlanVersion` 引用三者并继续保留完整快照以兼容现有读取链路。
- **理由**：规格要求多个方案共享同一项目主数据且结果只读。现有 `PlanVersion` 已具备原子写入、冲突检测、快照和失效机制，扩展它比引入新数据库更符合当前 Demo 架构。
- **已评估的替代方案**：继续只在浏览器内保存方案；为本功能立即引入数据库；在每个场景中重复嵌入项目而不设项目版本。前两者分别无法追溯和扩大基础设施，后者无法满足共享与失效要求。

## 4. 共享字段的兼容方式

- **决策**：为 `ScenarioInput` 增加可选 `project_data_version_id`、`scenario_version_id` 和 `girder_planning`；为 `GeneratedScheduleInput` 增加可选架梁快照摘要；为 `ProgressSnapshot` 增加可选架梁实绩。未提供这些字段的旧请求保持原行为。
- **理由**：这允许现有页面、兼容接口和非架梁项目渐进迁移，同时使新联合链路具有稳定引用和完整快照。
- **已评估的替代方案**：破坏性替换 `ScenarioInput`；另建完全平行请求模型。破坏性替换会造成大范围回归，平行模型会导致任务生成和求解入口长期重复。

## 5. 路线粒度与排程任务粒度

- **决策**：配置层使用“桥梁＋幅别”的路线经过，`side` 表达幅别，里程递增/递减另用线路方向表达；生成层按 `UpperStructureComponent.span_index` 形成分跨 `beam_erection` 任务；梁片数量作为任务工程量、生产需求和库存消耗，不生成单片任务。
- **理由**：路线层需要可操作性，综合排程需要与下部结构支点、资源和里程碑精确关联；单片任务会显著放大模型且没有当前业务价值。
- **已评估的替代方案**：全程桥梁级粗排；每片梁一任务。前者无法精确约束，后者规模过大。

## 6. 多路线共享桥梁与唯一归属

- **决策**：路线节点只记录“经过”，正式 `resolved_role` 由每轮实际计算到达日期派生；最早到达路线为唯一 `erect`，其余为 `pass`。同日且依赖图无法判序时返回 `blocked`，由用户保存 `owner_override` 后重算。
- **理由**：这严格落实用户确认的“第一次经过架梁，后续经过通道”，并避免配置阶段手工标注与联算日期变化产生冲突。
- **已评估的替代方案**：配置时固定 `erect/pass`；按路线列表顺序决定归属；同日随机取一条。三者都不能反映实际排程到达关系或缺乏可解释性。

## 7. 通行释放日期

- **决策**：`passable_date = max(erection_finish + post_erection_buffer, explicit_readiness_date, linked_task_finish_dates)`。新建方案必须显式确认桥梁架后通行缓冲；旧输入没有该字段时可带 `0` 建立草稿和预览，但保持 `needs_confirmation`，不得发布。
- **理由**：旧应用只有下构交验和路基/隧道缓冲，不能代表桥梁架后可通行条件。显式确认可以避免把技术默认误当现场事实。
- **已评估的替代方案**：沿用下构交验 7 天；架完立即通行；全局硬编码新天数。三者均缺少已确认业务依据。

## 8. 联合迭代与收敛

- **决策**：默认最多 10 轮；每轮重新校验、模拟、生成任务并求解。连续两轮的架梁归属映射和全部相关日级日期完全一致即 `converged`；发现历史状态指纹重复则提前 `not_converged` 并记录循环区间；无日期容差。
- **理由**：当前计划粒度为自然日，零日容差可避免“看似收敛但通行或归属仍变化”。10 轮为可配置默认，配合状态循环检测可以控制总耗时并保留完整诊断。
- **已评估的替代方案**：固定一次单向求解；允许 1～2 天容差；无限迭代。分别无法闭环、可能隐藏归属变化和无法保证响应时间。

## 9. 硬约束、软控制与失败语义

- **决策**：结构就绪、唯一归属、库存非负、通道释放、资源覆盖、固定路线顺序和显式合同承诺为硬约束；倒排建议最迟日期为高优先级软控制。结果统一为 `converged`、`not_converged`、`infeasible`、`blocked`。
- **理由**：物理不可违反条件必须阻止错误计划，管理目标允许在无法同时满足时输出有惩罚和原因的可行结果。
- **已评估的替代方案**：全部设为硬约束；为求得结果自动放松硬约束。前者容易产生不可解释无解，后者产生物理错误计划。

## 10. 架梁实绩与物料平衡

- **决策**：扩展现有 `ProgressSnapshot`，记录梁场累计产量、期初/修订库存、架梁消耗、架桥机位置和通道状态；已发生事实锁定。计划偏差保留并告警，负库存、重复实绩和无法平衡产耗返回 `blocked`。
- **理由**：任务进度百分比不足以恢复库存状态；沿用现有进度快照和修订机制可以保持统一审计与预测失效逻辑。
- **已评估的替代方案**：把库存只作为任务备注；每次滚动由用户重新输入完整未来方案。前者不可计算，后者破坏事实与计划的连续性。

## 11. API 与前端工作流

- **决策**：新增项目数据版本、方案版本、专项校验/预览和联合求解接口；发布继续复用计划管控入口但要求 `integrated_snapshot_id`；进度快照请求扩展架梁实绩。前端新增原生 `girderPlanning` 功能区并复用现有项目状态、方案比较和计划管控组件。
- **理由**：明确的资源版本和快照 ID 可实现幂等、并发冲突和结果失效；原生融合才能形成连续业务旅程。
- **已评估的替代方案**：iframe/微前端；直接复用旧应用根状态；只在现有求解接口中塞入所有动作。分别造成体验割裂、双状态和接口职责不清。

## 12. 黄金样例、影子验证与归档

- **决策**：将旧测试输入转换为版本化 JSON 夹具，标记 `legacy_parity` 或 `confirmed_rule_change`；后端端到端测试覆盖多梁场、共享桥梁、同日冲突、通道等待、库存短缺和实绩滚动；至少一个真实项目通过后归档旧应用。
- **理由**：算法迁移不能只验证代码覆盖率，需要同时证明未变规则保持一致、新规则符合确认口径，并保留差异证据。
- **已评估的替代方案**：仅人工点页面；一次性大切换；长期双写。均无法可靠定位差异或控制退役风险。

## 13. 依赖与部署

- **决策**：不新增运行时依赖，不引入新服务或数据库；沿用现有 FastAPI、Pydantic、OR-Tools、openpyxl、React 和本地原子文件存储，生产级持久化仍属于后续产品化议题。
- **理由**：本期核心风险在规则迁移和联合计算，不应同时扩大基础设施范围。
- **已评估的替代方案**：单独部署架梁服务、引入消息队列、立即迁移数据库。当前均缺乏必要性。

## 14. 数据权威与稳定引用

- **决策**：桥梁结构来源负责桥梁、工区、墩台、支点、梁跨和梁片数量；架梁工点来源负责非桥工点、走廊、里程、幅别、通道关联和导入路线顺序；用户确认配置负责梁场、设备、最终路线、人工通道和归属覆盖。项目主数据只保存稳定结构/构件/里程碑条件引用，联合计算时才解析为当次任务 ID。
- **理由**：显式权威矩阵可以避免导入顺序决定结果；稳定业务引用不会因方案任务重建而失效。
- **已评估的替代方案**：后导入覆盖先导入；在项目主数据中保存生成任务 ID。两者分别导致冲突静默丢失和跨方案引用失效。

## 15. 性能基准

- **决策**：固定性能夹具下限为 50 个桥梁幅别节点、300 个架梁分跨、2 个梁场、2 条启用路线和 800 个综合任务，联合计算需在 10 分钟内返回明确终态。
- **理由**：固定规模能形成可重复回归，同时真实项目影子验证可保留实际规模，不把某个客户数据集作为唯一性能标准。
- **已评估的替代方案**：只使用未固化的“真实项目”；只测小型单路线场景。前者不可重复，后者不能验证融合规模。
