# 研究结论：桩基、承台与墩身结构摘要聚合

## 1. 当前摘要拆行与单位缺失原因

**决策**：在 `workpointStructureSummaryProjection` 内按结构类型选择摘要参数，并在领域层统一尺寸文本；不在 React 页面二次合并。

**依据**：当前签名包含构件全部非工艺参数，桩长、墩高和 `form` 会拆分桩基/墩身。承台尺寸以无单位的 `form` 文本进入普通文本分支，因此 `16.5*16.5*6.0` 后没有 `m`。

**替代方案**：在 DOM 渲染阶段按文本合并。未采用，因为会产生第二套签名和数量计算，无法稳定处理单位、冲突和测试。

## 2. 类型专用摘要键

**决策**：

- 桩基：工艺身份＋`diameter_m`＋构件单位；
- 圆形墩身：工艺身份＋`diameter_m`＋构件单位；
- 矩形/变截面墩身：工艺身份＋`dimensions_m`＋构件单位；
- 承台：继续按既有完整参数与工艺分组，只修正尺寸文案单位。

桩长、墩高和柱位继续保存在主数据中，但不进入桩基或墩身摘要键。

**理由**：用户希望按设备/模板规格统计数量；直径或长宽是规格，高度和内外柱位置不是本页面的分组维度。

## 3. 尺寸文本规范化

**决策**：对可识别的米制尺寸表达式将 `*`、`x`、`X` 统一为 `×`，保留源文本小数精度，并在整个表达式末尾追加一次 `m`。斜线保持原语义。

示例：

- `16.5*16.5*6.0` → `16.5×16.5×6.0m`；
- `2.0*1.5` → `2.0×1.5m`；
- `8.0*6.0/4.0` → `8.0×6.0/4.0m`。

**替代方案**：把所有尺寸解析为数值数组再格式化。未采用，因为会丢失 `6.0` 的源精度，并可能误解变截面斜线含义。

## 4. 原始矩形墩身数据链

**决策**：在泸古客户构建脚本中区分墩身截面单元格：单个数字映射到 `diameter_m`，含乘号的合法尺寸表达式映射到 `dimensions_m`；高度和位置继续映射到 `height_m` 与 `form`。

**依据**：只读检查《泸古高速TJ-1标桥梁进度统计表4.27(1)》“永宁河特大桥”发现，墩身截面列为“直径（m）”，其中既有 `1.5`、`1.8` 等数值，也有 `3.0*3.0`、`3.0*4.0`、`8.0*6.0/4.0`。当前构建脚本用 `numeric()` 读取该列，尺寸表达式返回空；最新确认主数据中 500 个墩身有 80 个没有 `diameter_m`，且没有长宽参数。

**替代方案**：从 `height_m`、`form` 或构件名称推断长宽。未采用，因为这些字段只含高度与内柱/外柱等位置，不能恢复原始截面。

## 5. 参数与公共契约

**决策**：使用既有通用参数代码 `dimensions_m`，不新增 API 顶层字段或数据库列。

**依据**：项目主数据工作簿解析器已接收任意 `param.*`，`ProjectMasterParameter` 可携带文本值，前端领域代码也已把 `dimensions_m` 列为物理尺寸参数。仅需构建脚本保留该值并由 UI 契约明确其含义。

## 6. 当前项目数据更新

**决策**：重建统一工作簿后，先在隔离状态验证，再通过现有导入/确认 API 创建新项目主数据版本。不得直接编辑 SQLite 表或覆盖旧版本。

**理由**：当前确认版本已经丢失矩形尺寸，前端代码无法恢复；版本化导入能使页面获得真实值，同时保留原版本审计链和失败原子性。

## 7. 工作树保护

**决策**：实施必须保留 `build_lugu_project_master.mjs` 中现有未提交的线路空间对应组修改，只在相邻构件参数处理路径加入截面保留。

**依据**：该文件及生成输出在本功能开始前已存在未提交改动，属于用户/并行工作成果。

## 8. 验证策略

**决策**：使用前端纯领域样例证明摘要规则；运行客户构建脚本并检查生成工作簿/报告证明矩形值无丢失；在隔离项目主数据状态验证导入，再执行受控版本化更新。运行类型检查、构建和文档验证，不新增浏览器运行时门禁。
