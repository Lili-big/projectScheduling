# 研究结论：工点主导资源配置与范围共享流转

日期：2026-07-18

## 1. 当前实现事实

- `ScenarioInput.resource_pools` 是资源配置、AI 方案、计划快照和任务生成的唯一权威集合；`ResourcePool.id` 已被本地配置按 ID 合并，适合承载同类型多池。
- 当前 `resolve_effective_resource_pools()` 按资源类型检查唯一性，同类型超过一个池即输出 `RESOURCE_SCOPE_DUPLICATE_TYPE` 并跳过整类资源，这是多共享池的首个硬阻断点。
- 当前 047 工点独享仍是“一个资源类型池 + 多工点 `workpoint_overrides`”；资源页以资源池为一级对象，并在卡片内反向勾选获准工点。
- `Resource` 已携带 `pool_id`、`scope_mode`、`eligible_workpoint_ids` 和 `exclusive_workpoint_id`；求解候选按类型和显式工点范围筛选，不解析资源 ID。
- 命名资源精排已对每个实例使用互斥约束，容量求解已按资源组使用容量约束；共享池只要具有独立 `pool_id` 就可自然保持实例互斥和池间独立。
- 固定资源按 `quantity` 展开，最大资源/最少资源按 `max_quantity` 展开；当前可用性预检使用 `max_quantity > 0`，导致所有当前数量为 0 时可能退化成“默认充足”而未阻断。
- 前端 `resources.ts`、AI fallback/LLM 校验、资源助手结果和计划调整仍有多处按 `resource_type` 单值映射或广播更新，同类型多池会被覆盖或合并。
- 计划管控资源指纹已按池 ID 稳定排序并包含范围、数量、上限、状态和日历，基础可以复用；但资源调整仍可能按类型同时修改多个池。
- 当前没有独立持久化资源目录。工艺库资源类型、默认资源池元数据和当前配置可以形成只读目录投影。

## 2. 决策 1：继续使用统一 `ScenarioInput.resource_pools`

**决定**：不新增 `workpoint_resource_configs`、`shared_resource_pools` 等第二套顶层权威。`resource_pools` 允许同类型多个记录，以 `pool.id` 全局唯一。

**理由**：现有保存、场景、AI 方案、计划快照、生成和求解均围绕该列表；按 ID 合并与指纹也已具备。只放宽“类型唯一”并增加记录不变量，比双模型同步更可控。

**已评估的替代方案**：新增两个顶层列表。该方案会要求所有 API、快照、AI 和结果层维护双向同步，拒绝采用。

## 3. 决策 2：工点本地资源使用显式 `workpoint_id`

**决定**：在 `ResourcePool` 增加可选 `workpoint_id`。048 新建工点本地记录必须满足：

- `scope_mode=WORKPOINT_EXCLUSIVE`；
- `workpoint_id` 为当前权威桥梁工点；
- `authorized_workpoint_ids=null`、`workpoint_overrides=[]`；
- 同一 `(workpoint_id,type)` 最多一条；
- `quantity/max_quantity/enabled` 直接属于该工点记录。

**理由**：显式字段比把单工点身份塞进“获准集合”更清晰，能稳定支持 UI upsert、AI 精确更新、指纹和诊断，也避免继续暴露反向适用范围概念。

**已评估的替代方案**：使用 `authorized_workpoint_ids=[workpoint]` 作为本地身份。该方案复用字段较多，但会混淆“本地归属”和“共享获准范围”，拒绝作为新写入规范。

## 4. 决策 3：范围共享池以独立 ID 表达

**决定**：048 新建共享记录必须满足：

- `scope_mode=PROJECT_SHARED`；
- `workpoint_id=null`、`workpoint_overrides=[]`；
- `authorized_workpoint_ids=null` 表示当前项目全部桥梁工点；显式非空数组表示固定范围；
- 同类型共享池数量不限，但每个池的 ID、数量、上限、状态、日历、成本和范围独立。

**理由**：现有 `Resource` 与求解分组已按 `pool_id` 区分；无需新增“共享池类型”或转场实体。

**已评估的替代方案**：把多个共享组织合并成一个池并为实例附范围。该方案无法为每个池独立维护数量和上限，拒绝采用。

## 5. 决策 4：047 旧独享形态只通过统一迁移器处理

**决定**：

- 旧 `PROJECT_SHARED` 池保持一条记录，缺失新字段时继续按共享读取，不拆分。
- 旧 `WORKPOINT_EXCLUSIVE` 且 `workpoint_id=null` 的多工点默认/覆盖形态标记为 legacy 输入；统一迁移器先用现有有效值解析器得到每个工点的 `enabled/quantity/max_quantity`，再生成稳定单工点记录。
- 新 ID 使用确定性结构（例如 `{legacy_pool_id}::workpoint::{workpoint_id}`），并保留来源 ID用于诊断。
- 未知工点、重复覆盖、无法确认有效值或迁移后发生 ID 冲突时，不保存部分结果；保留原数据并输出阻断诊断。

**理由**：旧共享保真是明确验收；旧独享可无损展开时自动转换能复用已实现的有效值语义，无法证明无损时必须停止猜测。

**已评估的替代方案**：直接删除 `workpoint_overrides` 或依赖 Pydantic 忽略字段。该方案会静默丢失历史内容，拒绝采用。

## 6. 决策 5：资源目录是派生视图，不新增持久化权威

**决定**：资源目录由当前工艺/任务需要的资源类型、默认资源池元数据和当前项目已知资源类型形成稳定只读投影。目录补充只创建当前工点的本地 `ResourcePool` 记录。

**理由**：本期只要求“从资源目录补充”，未要求目录维护、审批或跨项目治理；派生视图足以支持选择且不会形成第二套资源类型权威。

**已评估的替代方案**：新增持久化 `ResourceCatalogItem[]`。这会扩大共享契约和产品范围，拒绝在本期采用。

## 7. 决策 6：候选为本地与全部合法共享实例的并集

**决定**：任务先通过现有工艺映射得到资源类型，再按任务权威 `bridge_id` 收集：

1. 相同类型且 `workpoint_id == task.bridge_id` 的启用本地池实例；
2. 相同类型、启用且 `task.bridge_id` 位于共享范围内的所有共享池实例。

同一工点属于同类型多个共享池时，所有匹配池都提供候选。范围外、本地属于其他工点或停用池均不得提供候选。

**理由**：现有求解器已经对合法命名资源执行 `AddExactlyOne` 并对每个实例互斥；候选并集不需要新求解目标。

**已评估的替代方案**：强制本地优先或只选一个共享池。用户未确认这类优先级，且会不必要地收窄可行域，拒绝采用。

## 8. 决策 7：数量 0 采用模式感知语义

**决定**：

- 当前资源最短工期只使用 `quantity`。本地数量 0 不展开本地实例；所有合法本地/共享当前实例均为空时，任务生成直接阻断。
- 增配与固定工期最少资源可以在对应池 `max_quantity` 内形成候选和建议；建议未采纳前不得改变当前配置或把当前资源计划标记为可执行。
- 诊断结构至少包含 `code/task_id/workpoint_id/resource_type/relevant_pool_ids/reason`。
- `quantity=0`、停用、`UNLIMITED`、范围不匹配和资源类型缺失分别诊断，不再统一折叠为默认充足。

**理由**：同时满足“0 表示当前没有资源”和保留 `max_quantity` 作为潜在增配上限；不同求解入口的业务问题不同，不能共享一个可用性布尔值。

**已评估的替代方案**：继续以 `max_quantity > 0` 判断当前可用。该方案会让当前数量 0 的计划错误通过，拒绝采用。

## 9. 决策 8：复用实例互斥，修正多候选容量下界

**决定**：继续复用命名实例互斥和按池容量约束，不新增转场任务、前置、持续时间、费用或人工顺序。对同一任务可落入多个池的情况，容量下界诊断只对唯一候选池任务做逐池下界，或对候选池集合做联合下界，禁止把同一任务重复计入每个池。

**理由**：现有互斥已满足共享实例不能并发；多范围重叠的新增风险在诊断下界重复计数和对称解，而不是互斥缺失。

**已评估的替代方案**：为流转建立路线/时间/费用变量。属于明确排除范围，拒绝采用。

## 10. 决策 9：所有数量更新和结果按 `pool.id` 定位

**决定**：AI、前端编辑、计划调整、结果诊断和推荐数量统一使用 `resource_pool_id`。现有 `scoped_resource_updates` 作为新标准更新通道：共享池使用 `workpoint_id=null`，本地池必须携带并校验 `workpoint_id`。旧 `resource_updates: {type:quantity}` 只在该类型唯一对应一个旧共享池时兼容，否则拒绝歧义。

**理由**：同类型多池后，类型只能用于任务需求匹配，不能再承担配置记录身份。

**已评估的替代方案**：按类型广播到所有池。会造成数量和计划被批量误改，拒绝采用。

## 11. 决策 10：指纹与失效保留池身份

**决定**：场景池、AI 方案池和计划资源快照按 `pool.id` 排序；新增 `workpoint_id`、范围、数量、上限、状态、日历及成本保留在标准序列化和指纹中。集合顺序等价不改变指纹，任何单池语义变化必须改变指纹并使旧任务图、求解、AI 解释、比较、预测和调整建议 stale。

**理由**：现有 `resource_semantics_fingerprint()` 已具备大部分基础，只需补新字段并消除按类型合并。

**已评估的替代方案**：只对资源类型和总数量做指纹。无法区分同类型池范围和来源，拒绝采用。

## 12. 决策 11：页面分为工点区和共享池区

**决定**：

- 工点资源区一级对象为权威桥梁工点；二级资源行只编辑本地当前投入、上限和状态，支持目录补充，不展示适用工点选择。
- 共享池区一级对象为稳定池 ID；支持同类型多池、独立范围和数量编辑。
- Workspace 以 `pool.id` 和 `workpoint_id` 做 upsert/add/remove，停止使用数组下标作为业务身份；版本 ID + 资源指纹继续保护晚到响应。
- 结果和助手以 `pool_id + pool_label` 展示，同类型多池不能只取第一条标签。

**理由**：直接对应用户心智和验收条件，同时复用现有工作点加载、保存失败重试和结果失效链。

**已评估的替代方案**：继续以资源类型卡片为一级对象。无法满足工点主轴且会保留反向适用工点配置，拒绝采用。

## 13. 决策 12：性能和验证策略

**决定**：定向测试先证明契约、迁移、候选、数量 0、三类求解、AI、计划和页面；增加一个中等规模重叠共享池性能样例，记录变量数、求解状态和耗时趋势。全量门禁只由最终 R3 执行一次。

**理由**：同类型多个重叠池会增加可选区间和对称解，必须验证但不能为此引入未经确认的分配优先级。

**已评估的替代方案**：在业务规则中增加本地优先或共享池顺序以降低对称。用户未授权，拒绝采用。

## 14. 无需澄清项

用户已经明确工点主轴、同类型多池、共享范围、数量 0、互斥、求解器自动顺序、零转场、旧共享兼容和排除项。本研究没有遗留 `NEEDS CLARIFICATION`；三类求解模式感知和旧独享无损迁移作为计划中的显式默认假设，等待 tasks/analyze 门禁统一确认。
