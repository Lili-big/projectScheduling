# 面向研发交底的 PRD 生成

## 目标

生成一份研发可以直接理解和执行的产品需求文档。文档要说清楚实际工程项目要做什么、使用什么数据、用户如何交互、前后端如何分工、如何影响上下游模块，以及研发和测试如何验收。

PRD 是产品目标文档，不是 demo 实现说明、技术设计记录或生成过程记录。`docs/` 下只保留最终版本，不描述“系统生成版 vs 手工修改版”的比较过程，也不记录“我是如何生成这份文档的”。

## 核心原则

- 面向实际工程项目写需求。demo 代码只用于理解当前页面原型、已有字段、数据流和可复用逻辑，不等价于工程化目标。
- 当 demo 与实际工程目标冲突时，PRD 应表达工程化产品目标，不应把 demo 的临时接口、全局模拟、无项目隔离、显式保存等限制写成产品要求。
- 若无法判断某处是 demo 限制还是产品目标，先向用户确认，不要照搬代码。
- 默认少写 HTTP 路径、请求体、返回体、数据库表等实现细节；重点写清楚前后端职责、数据对象、输入输出、查询/保存/初始化能力。
- 只有用户明确要求接口契约，或研发必须依赖具体字段/接口才能开工时，才补充最小必要接口细节。
- 用产品语言说清楚做什么，例如“系统应”“用户可”“研发需支持”“保存后”。避免把需求写成代码讲解。

## 标准流程

1. 明确用户要整理的页面、模块、功能或业务流程。
2. 查找当前项目已有需求文档，通常位于 `docs/` 目录。
3. 阅读当前产品材料：
   - 截图、附件或页面描述用于捕捉最新页面效果和产品口径。
   - 前端组件用于理解页面结构、字段、控件、状态和交互原型。
   - 类型定义、标签映射、常量、领域逻辑和 API 客户端用于理解数据对象和联动关系。
   - 后端模型、默认数据、服务层、仓储层、API 路由和计算逻辑用于理解已有数据结构、初始化来源和约束。
4. 提炼产品需求，而不是复述实现：
   - 页面字段、标题、按钮、输入控件、禁用状态、排序规则、默认值和保存行为。
   - 数据模型结构、字段含义、枚举、单位和默认数据。
   - 默认数据初始化规则、项目级/全局级/模板级数据归属。
   - 前端与后端的职责边界。
   - 对任务生成、计算、资源匹配、权限、缓存或结果失效的影响。
5. 将 demo 限制转译为工程化目标：
   - demo 使用全局数据时，实际工程可写为项目级数据隔离。
   - demo 使用临时接口时，实际工程可写为查询、保存、初始化能力。
   - demo 写死默认数据时，实际工程应写为系统模板初始化到项目配置。
6. 输出或更新唯一一份 PRD，让研发知道交付边界，让测试知道验收方式。
7. 修改文件后复读最终文档，并尽量运行轻量检查，例如 `git diff --check -- <file>`。

## 推荐文档结构

除非当前项目已有更合适的固定模板，否则优先采用以下结构：

```markdown
# <模块或页面>需求文档

版本：
日期：
适用范围：
面向对象：

## 1. 功能模块核心定位
### 1.1 模块定位
### 1.2 当前页面效果 / 当前业务场景
### 1.3 模块边界

## 2. 数据定义
### 2.1 主数据对象
### 2.2 子对象 / 配置项
### 2.3 枚举、状态、单位、标签
### 2.4 默认数据或初始化规则

## 3. 默认数据初始化
### 3.1 初始化原则
### 3.2 当前默认数据清单
### 3.3 项目级、全局级或模板级数据归属

## 4. 页面功能交互
### 4.1 进入页面
### 4.2 查看、编辑、新增、删除、保存
### 4.3 状态、禁用、校验、错误提示
### 4.4 与截图或最新页面一致的交互细节

## 5. 前后端接口
### 5.1 查询能力
### 5.2 保存能力
### 5.3 初始化或重置能力

## 6. 联动规则
### 6.1 上游输入
### 6.2 下游影响
### 6.3 计算、生成、匹配、失效规则

## 7. 校验与异常处理

## 8. 验收标准

## 9. 后续扩展建议
```

按模块实际情况取舍章节。不要省略数据定义、页面交互、前后端职责、默认数据初始化、联动规则和验收标准，除非该模块确实不涉及。

## 写作规则

- 明确模块定位和非范围，避免研发误以为一期要做所有扩展能力。
- 精确描述当前可见 UI：页面标题、副标题、表头、控件、按钮状态、标签、行内分组、弹窗或提示。
- 页面截图中的辅助说明区、提示区和解释性信息，应按研发交付价值取舍；只有影响实现、数据、交互、保存、联动或验收时才写入核心章节，否则可简短说明，不要自动扩展为独立数据章节或验收标准。
- 当用户说明“现有页面数据作为默认数据初始化到项目中”时，要明确写出系统模板、项目级配置、用户后续增删改和持久化规则。
- 明确前后端分离：前端负责渲染、编辑、提交标准数据；后端负责初始化、校验、持久化、权限、迁移和返回标准化数据。
- 数据对象使用表格列出字段、类型、是否必填和说明。研发需要精确契约时保留代码字段名。
- 枚举、状态、单位、计算方式、来源字段和展示标签使用表格列出。
- 公式只在定义必要业务行为时出现。
- 验收标准必须可执行、可测试。
- 避免“支持管理”“支持维护”这类空泛表述；必须拆成查看、新增、编辑、删除、保存、校验、重置等具体动作。
- 删除或压缩生成过程说明、历史版本差异说明、过细实现解释、demo 专属说明。
- 不要写“我比较了哪些版本”“本次修改来自哪里”等过程性内容。

## 代码阅读清单

前端模块优先阅读：

- 页面或 Tab 组件。
- 状态更新函数和保存函数。
- TypeScript 类型定义。
- 标签、排序、单位归一化、计算、资源展示等领域 helper。
- API client 方法；仅提炼查询、保存、初始化等能力，不默认展开路径和请求体。
- CSS 仅在布局、可见状态或截图效果影响 PRD 时阅读。

后端模块优先阅读：

- 请求/响应模型。
- 默认数据工厂。
- 服务层。
- 仓储层或持久化层。
- API 路由；默认转译为前后端能力，不照抄 demo 路径。
- 消费该数据的计算、生成或求解函数。
- 能体现预期行为的测试。

文档资料优先阅读：

- 当前模块已有 PRD。
- 相关模块需求文档。
- 项目总览、README 或架构说明；只在它们能帮助解释范围和边界时使用。

## 附件和格式处理

当用户提供 `.md`、富文本导出、表格复制文本或截图时：

- 保留用户文档的产品语义。
- 清理导出噪声，例如孤立的项目符号、制表符表格、丢失的标题层级。
- 转换为仓库内规范 Markdown：标题层级、表格、列表、代码字段反引号。
- 不在目标 PRD 中保留附件来源说明或版本比较说明。
- 当用户提供手动修改版 PRD 用于同步时，应区分产品语义修改和导出格式噪声；同步角色、边界、交互、字段说明、验收口径等真实变化，不把纯文本表格、缺失标题符号、项目符号样式等格式退化覆盖到仓库文档。
- 当手动修改版与当前最新明确产品口径冲突时，不要盲目覆盖；优先保留最新明确决策，并在最终总结中说明该冲突和取舍。
- 同步手动修改版 PRD 时，以用户修改后的产品语义为准，以仓库 Markdown 结构为准。保留仓库中的标题层级、Markdown 表格、字段反引号和列表风格，避免把富文本导出的纯文本格式覆盖回去。
- 如果手动修改版删除了生成版中的非范围说明、异常提示、验收项或扩展说明，应视为潜在的产品收口；只要不与用户最新明确口径冲突，就同步删除，而不是为了保持生成版完整性自动补回。
- 最终总结中应区分“已同步的产品语义差异”和“已忽略的格式噪声”，让用户确认哪些变化真正进入了仓库文档。

## 质量标准

一份合格的研发交底 PRD 应满足：

- 研发不看聊天上下文，也能理解实际工程项目的模块目标和业务边界。
- 研发可以根据文档实现或校验数据契约。
- 测试可以根据交互和验收章节拆出测试用例。
- 页面效果、产品口径和工程目标已经同步到文档。
- demo 实现和实际工程项目要求没有混淆。
- 默认数据初始化和用户编辑持久化规则明确。
- 下游影响明确，尤其是会导致任务、计算结果、资源匹配或求解结果失效的变更。

## 文件编辑要求

更新仓库内文档时：

- 保留已有文档中仍然正确且有价值的内容，但旧结构不适合研发交底时可以重组。
- 手工编辑文件使用 `apply_patch`。
- 修改后复读文档。
- 尽量执行 `git diff --check -- <file>`。
- 最终说明中提及未处理的无关脏文件，但不要改动它们。
