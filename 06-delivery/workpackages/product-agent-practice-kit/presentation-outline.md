# 产品 Agent AI Coding 实践分享：PPT 框架

> 本文件是项目内的汇报设计资产，由发布白名单排除，不进入对外分发 ZIP。

## 使用说明

- 推荐页数：8 页。
- 目标受众：希望复用产品 Agent 工作方法的产品、研发与团队负责人。
- 汇报目标：说明项目如何搭建、SOP 如何运行、Skill 如何承接方法，以及产品经理如何以最小输入驱动 Agent。
- 本框架只定义内容和布局，不生成 PPT 文件。

## 第 1 页：产品经理 AI Coding 的本质：人做判断，Agent 做执行，项目沉淀能力

### 核心结论

产品的AI Coding不是万能Prompt，不是好看的heml页面，而是项目框架承载事实、Skill 封装方法、Agent 执行流程、产品经理负责业务判断和执行授权。

### 内容元素

- 产品经理：问题、证据、决策、授权。
- Agent：读取事实、调用 Skill、生成产物、执行验证。
- Skill：方法、步骤、质量标准、停止条件。
- 项目框架：业务输入、项目基础、需求想法、Demo、验证、PRD文档。
- 结果链：模糊需求 → 可验证 Demo → 有结果的需求实现。

### 布局

- 上方 20%：标题和一句结论。
- 中部 60%：四层同心结构或自上而下分层图。
- 下方 20%：端到端结果箭头。
- 产品经理用橙色、Agent 用紫色、Skill 用蓝色、项目框架用深灰色。

### 讲述重点

- 产品经理不需要成为 Prompt 工程师。
- 方法要进入项目和 Skill，而不是留在个人聊天记录。
- 后续页面都围绕四层如何真正运行展开。

## 第 2 页：一个项目应该怎么搭

### 核心结论

项目框架的作用是让 Agent 知道事实在哪里、当前处于哪个阶段、下一步应该生成什么产物。

### 内容元素

左侧目录树：

```text
project/
├─ AGENTS.md
├─ .specify/memory/constitution.md
├─ .agents/skills/
├─ 01-inputs/
├─ 02-product-baseline/
├─ 03-requirement-discovery/
├─ specs/
├─ 04-demo/
├─ 05-validation/
└─ 06-deliverables/
```

右侧职责映射：

| 区域 | 回答的问题 |
| --- | --- |
| 业务输入 | 客户、业务实际输入了什么 |
|  产品实现| 当前产品实现是什么 |
|  需求分析| 真实的问题是什么，有什么解决思路 |
| 产品方案 | 产品如何实现，方案如何设计 |
| Demo 与验证 | 能否运行、规则是什么 |
| 交付 | 研发最终接收什么 |

底部三项治理资产：

- `AGENTS.md`：流程路由。
- Constitution：可固化的规则。
- Skill：具体执行方法。

### 布局

- 左侧 40%：目录树。
- 右侧 60%：职责映射。
- 底部横向三块治理说明。

### 讲述重点

- 每个目录只回答一种问题。
- `AGENTS.md` 不堆项目事实，Skill 不重复治理规则。
- 通用方法可以全局共享，实际执行使用项目本地 Skill。

## 第 3 页：完整 SOP 怎么运行

### 核心结论

实践流程不是“输入需求—生成页面”，而是 11 步受控流水线，每一步都有产物和退出条件。

### 内容元素

阶段一，建立事实：

1. 建立 Agent 工作区。
2. 原始资料入库。
3. 还原产品基线。

阶段二，收敛需求：

4. 需求发现。
5. 形成产品确认快照。

阶段三，实现验证：

6. Spec Kit 规格化。
7. 用户确认实施。
8. Demo 实现。
9. 分级验证。

阶段四，迭代交付：

10. Demo 反馈回流。
11. PRD 与研发交接。

### 布局

- 使用横向四阶段泳道或地铁线路图。
- 11 个节点按阶段排列。
- “产品口径确认”和“实施授权”使用橙色闸门。
- 每阶段下方只显示一个核心产物。

### 讲述重点

- Agent 不能从模糊输入直接跳到实现。
- 产品口径确认不等于实施授权。
- Demo 验证是下一轮需求输入，不是流程终点。

## 第 4 页：先把需求分析正确

### 核心结论

资料入库、现状还原和需求发现的共同目标，是阻止未经证明的信息进入正式需求。

### 内容元素

| SOP | 核心动作 | 注意事项与坑 |
| --- | --- | --- |
| 资料入库 | 保留原件、编号、哈希、登记限制 | 截图不证明后台规则；文档声明不等于已实现 |
| 产品基线 | 核对文档、页面、代码和测试 | 不能边还原现状边加入新方案 |
| 需求发现 | 分离问题与解法、比较方案、定义 MVP | 不直接改代码；一次只确认一个高影响问题 |
| 确认快照 | 固化有效口径、范围和被替代决策 | 用户确认不能只留在聊天中 |

真实案例：

- 多项目看板：墙面照片只证明信息组织方式，不能证明颜色和图标规则。
- 排程算法：代码核查发现资源模型和旧文档口径并不完全一致。

### 布局

- 上方 15%：结论。
- 中部 65%：四行三列表格。
- 下方 20%：两个案例证据条。
- 核心动作用蓝色，风险和坑用红色。

### 讲述重点

- 第一生产力不是生成速度，而是证据分层。
- 区分事实、用户表达、产品推断、默认假设、冲突和待验证。
- 这套方法由 `requirement-discovery` 承接，不由产品经理反复提示。

## 第 5 页：从规格走到 Demo

### 核心结论

规格链和人工门禁共同控制 Agent 的实施范围，防止 Demo 越做越偏。

### 内容元素

顶部流程：

```text
产品确认快照
→ speckit-specify
→ speckit-plan
→ speckit-tasks
→ 一致性检查
→ 用户授权
→ speckit-implement
```

三组关键动作：

1. 规格化：用户故事、边界、数据、契约、兼容、成功标准。
2. 实施门禁：确认范围和规则，用户明确授权，高风险操作另行确认。
3. Demo 实现：按用户故事形成闭环，使用稳定脱敏数据，明确标识 Mock。

避坑区：

- Tasks 生成后自动开工。
- 为演示写死核心业务规则。
- 把 Demo 接口写成正式产品要求。

### 布局

- 顶部 30%：横向规格流水线。
- 下方左侧 70%：三块并列操作区。
- 下方右侧 30%：红色避坑区。
- 用户授权节点放大并使用橙色。

### 讲述重点

- Spec、Plan、Tasks 分别解决做什么、怎么规划、如何执行。
- Agent 只能实施已确认任务。
- Demo 验证产品行为，不替研发确定生产架构。

## 第 6 页：验证、反馈与交付

### 核心结论

后半程的关键是让每条反馈进入正确通道，而不是把所有问题都变成继续改页面。

### 内容元素

左侧三级验证：

1. 日常迭代：定向单测、单条 E2E。
2. 用户评审：Typecheck、Smoke、真实浏览器、多视口。
3. 正式交付：完整门禁、契约、构建、残余风险。

中央反馈分流：

```text
Demo 反馈
├─ 业务规则变化 → 需求发现 / 更新 Spec
├─ 数据契约变化 → 更新 Plan 与 Tasks
├─ 纯视觉变化 → UI Skill 与视觉验证
├─ 实现缺陷 → 定向修复
└─ 证据不足 → 保留待验证
```

右侧交付包：

- 当前有效 PRD。
- 业务与数据规则。
- 异常、边界与兼容。
- Demo 与验证证据。
- 已验证结论和未验证假设。

底部真实演进：

- `047 → 048`：一级产品模型改变，应建立新 Feature。
- `风险 → 完成/延期 → 预测/实际延期`：新口径必须同步更新决策、规格和验证。

### 布局

- 三栏：验证 30%｜反馈分流 40%｜交付 30%。
- 底部横跨全页放真实案例时间线。

### 讲述重点

- 测试通过不等于用户体验正确。
- 内部回归稳定与外部产品贴近度需要分开验证。
- 交付给研发的是需求基线和行为证据，不是 Demo 内部实现。

## 第 7 页：Skill 如何接管方法

### 核心结论

可复制能力应该沉淀为全局方法、项目适配和自动路由，而不是个人 Prompt 库。

### 内容元素

三级 Skill：

1. 全局通用：`requirement-discovery`、`write-prd`、`research-summary`、资料处理。
2. 全局管理：`manage-speckit-project-skills`。
3. 项目本地：项目 `speckit-*`、算法解释、UI 原型、项目验证规则。

Agent 路由：

```text
模糊需求 → requirement-discovery
口径确认 → specify → plan → tasks
实施授权 → implement
算法解释 → demo-algorithm-explainer
UI 校准 → ui-spec-to-html-prototype
评审完成 → write-prd
```

合格 Skill 必须说明：

- 使用与禁用条件。
- 最低输入。
- 执行步骤。
- 输出与非输出。
- 完成与停止条件。
- 下一阶段路由。

### 布局

- 左侧 55%：三级 Skill 分层堆栈。
- 右侧 45%：Agent 路由流程和质量检查。
- 连线强调实际执行使用项目副本。

### 讲述重点

- 全局 Skill 沉淀方法，项目 Skill 沉淀业务和工程约束。
- Agent 根据阶段自动选择 Skill。
- Skill 不能擅自越过用户确认门禁。

## 第 8 页：产品经理只需这样输入

### 核心结论

产品经理只需要表达业务意图、证据、确认口径和阶段授权，复杂执行方法由 Skill 负责。

### 内容元素

左侧四项最小输入：

1. 当前要解决的问题。
2. 可用资料或评审反馈。
3. 已确认的业务口径。
4. 希望推进到哪个阶段。

右侧最小触发语：

- “先还原这些资料，不要形成新需求。”
- “先分析清楚这个需求，不要实现。”
- “比较方案，说明推荐和不选理由。”
- “口径确认，进入正式规格，不要实施。”
- “Tasks 确认，可以进入 Demo 实现。”
- “先判断反馈属于业务、UI 还是缺陷。”
- “按当前有效口径输出研发交底 PRD。”

底部原则：

> Prompt 只表达意图；Skill 负责方法；项目资产负责记忆；人工门禁负责决策。

### 布局

- 左侧 40%：四项输入表单。
- 右侧 60%：最小触发语对话气泡。
- 底部使用高亮横幅收束。

### 讲述重点

- 最小触发语只是调用入口，不是流程说明书。
- 每次都需要复制长 Prompt，说明方法还没有真正进入 Skill。
- 同事拿到工具包后，应能用自然语言直接启动实践。
