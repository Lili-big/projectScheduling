# 脱敏案例：里程碑看板从风险视角演进到预测/实际延期

## 背景

产品经理收到功能清单、接口说明、产品说明书、当前页面截图和现场年度目标图照片。资料并不直接等于一个完整需求，需要先还原现有产品，再比较年度总览方案。

## 第一轮：建立年度目标图

需求发现比较了：

1. 继续增强明细台账。
2. 年度目标总览加明细下钻。
3. 建设完整里程碑治理平台。

第二种方案能验证全年分布和会议扫描价值，又不提前引入审批、责任和销项等证据不足的能力，因此进入首个Feature。

## 第二轮：用户推翻风险视角

Demo评审后，用户明确指出主看板不应以风险等级为核心，而应回答：

- 里程碑是否完成。
- 是否已经延期。

这属于业务规则变化，因此建立后续Feature，显式替代旧风险表达，而不是只调整颜色。

## 第三轮：延期进一步拆分

用户继续确认：

- 未完成节点需要区分预测延期和实际延期。
- 默认使用预测延期。
- 已完成节点只展示实际结果。
- 延期基准优先采用要求完成时间，缺失时才回退计划完成时间。

这又形成一轮独立规格和验证。

## 实际流程

```text
多源资料入库与来源登记
→ 产品基线
→ requirement-discovery与三方案比较
→ 用户确认MVP
→ Feature 1规格化与Demo
→ 评审反馈分类为业务规则变化
→ Feature 2替代风险视角
→ 新反馈进一步扩展延期口径
→ Feature 3规格化与验证
→ 当前有效规则进入PRD
```

## 视觉验证踩坑

内部视觉账本一度达到满分，但用户仍认为Demo不像真实系统。原因是账本只和内部样板比较，没有使用真实系统同视口证据。

修正后将两个门禁分开：

- 内部回归：防止已确认页面意外变化。
- 外部贴近度：用真实系统截图、相同视口和信息密度校准。

## 可复制经验

1. 多源资料先建产品基线，不直接拼成PRD。
2. 现场照片可提供信息组织线索，但不能凭颜色和图标猜业务枚举。
3. Demo评审是需求收敛环节，不只是缺陷验收。
4. 视觉自动化通过不等于符合真实产品；内部回归和外部证据必须分开。
5. 被替代的旧决策保留历史，但不得继续作为当前权威。

## 不应复制

- 客户现场照片、账号和项目名称。
- 实际系统未脱敏截图。
- 真实接口地址和业务数据。
