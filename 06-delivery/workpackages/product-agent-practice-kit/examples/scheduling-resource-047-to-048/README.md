# 脱敏案例：资源配置从类型主导转向工点主导

## 背景

一个复杂排程Demo已经支持按资源类型配置“项目共享”和“工点独享”。功能实现和测试均已完成，但计划工程师实际评审后指出：真实操作不是先选资源类型再勾选工点，而是先进入工点，再维护该工点拥有的资源。

同时，同一种机械可能存在多个独立共享池，每个池有自己的数量和适用工点。

## 为什么不能直接改页面

这个反馈同时改变：

- 产品一级对象和信息架构。
- 资源唯一身份与作用域。
- 求解器候选匹配。
- AI建议更新目标。
- 历史数据迁移和结果失效规则。

因此它属于产品模型变化，不是视觉缺陷。

## 实际处理

```text
Demo评审反馈
→ requirement-discovery判断影响范围
→ 新建后续Feature并显式替代旧规则
→ 明确工点本地资源与多个范围共享池
→ 规定AI只能建议数量，不能猜作用域
→ 定义旧数据无损迁移和阻断条件
→ specify → plan → tasks
→ 用户确认实施门禁
→ implement与固定双工点样例验证
```

## 关键产品规则

- 工点资源必须有显式工点身份。
- 同一资源类型可以存在多个共享池。
- 更新和诊断按池ID定位，不能只按资源类型。
- 数量为0表示当前没有资源，不能解释为默认充足。
- 无法无损迁移的历史配置必须阻断，不得静默丢字段。

## 可复制经验

1. 已完成Feature不是继续打补丁的理由。
2. 用户改变一级对象时，先检查数据、算法、AI和迁移，不只检查页面。
3. AI可以建议参数，但作用域和高影响规则必须由人决定。
4. 新规格应显式声明替代关系，保留历史证据但只维护一套当前权威。

## 不应复制

- 具体客户或项目名称。
- 生产资源数量、算法样例和真实排程数据。
- Demo内部接口或研发工程架构。
