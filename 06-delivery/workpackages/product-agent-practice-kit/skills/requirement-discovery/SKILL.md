# 需求发现

## 目标

把需求线索转化为与其影响和不确定性相匹配的产品结论：小型需求形成最小验收快照，中型需求形成经过方案比较的紧凑设计，复杂需求形成可进入 PRD 和正式规格化流程的确认输入。

本 Skill 只负责需求还原、澄清、方案选择和交付路由。默认不修改业务代码、不替代正式 PRD、不创建 Spec Kit 任务；用户明确要求继续时，再交给相应流程。

## 核心原则

1. **先查事实，再提问题**：先读取足以判断需求的项目规则、现有文档、代码、测试、运行结果和近期相关变更。能从项目确认的事实不要反问用户。
2. **先还原问题，再完善方案**：把用户提出的功能或做法视为候选解法，先确认它要解决的角色、场景、任务和损失。
3. **证据分层**：明确区分项目事实、用户表达、产品推断、默认假设、冲突和待验证问题。
4. **按影响分级**：分级依据业务不确定性、影响面、契约和数据风险、验证成本，不依据代码行数或用户称呼。
5. **一次只问一个最高影响问题**：只询问会改变价值判断、需求级别、范围、业务语义、数据契约或验收的问题。
6. **有意义地碰撞方案**：中型和复杂需求比较真实可选路径，给出推荐和不选理由，不为凑数量制造伪方案。
7. **主动控制范围**：优先形成可验证闭环，去掉不影响核心价值验证的增强能力。
8. **定义反证**：除成功标准外，说明什么证据会表明问题不值得做、方案不可采用或需要停止扩大范围。
9. **项目规则优先**：项目自己的 `AGENTS.md`、宪章、资产规则和实施门禁高于本 Skill 的通用路由。

## 工作流

### 1. 判断任务是否属于需求发现

使用本 Skill 的典型情况：

- 用户只有目标、想法或功能线索，尚未形成可测试行为。
- 现有需求需要还原业务目标、MVP、规则、边界或验收。
- 用户要求比较方案、讨论怎么做或进入正式规格前先澄清。
- 一个看似明确的功能可能隐藏业务语义、算法、数据或跨角色决策。

不使用本 Skill 的情况：

- 用户已经给出明确目标、范围、行为和验收，并要求直接实施。
- 用户只要求解释、定位、评审代码或诊断缺陷。
- 用户明确要求撰写正式 PRD；此时使用项目指定的 PRD Skill。
- 用户已经确认正式规格并要求执行计划或任务。

### 2. 最小化读取项目事实

先读取当前项目的执行规则和最小相关事实，再决定是否需要更多材料：

- 项目入口、阶段说明、权威需求和现有规格。
- 目标页面、接口、模型、算法模块和邻近测试。
- 与本需求直接相关的近期提交或运行证据。
- 用户提供的截图、表格、访谈、反馈或历史方案。

读取只服务于以下判断：当前行为是什么、正式口径是什么、临时 Demo 是什么、已有能力和限制是什么、哪些问题项目已经回答。定位到足够证据后停止搜索。

### 3. 还原真实问题

在讨论功能前，形成最小问题定义：

```text
谁，在什么情境或触发条件下，
为了完成什么业务任务或决策，
目前使用什么方式，
哪里产生时间、质量、风险或协作损失，
为什么需要现在解决？
```

同时区分：

- **问题**：需要改善的业务结果。
- **用户提出的方案**：当前候选解法，不自动等于最终需求。
- **目标行为**：用户最终需要观察或完成的结果。
- **替代方式**：流程调整、人工校核、复用现有能力或暂不开发。

需要详细方法时读取 [references/reconstruction-framework.md](references/reconstruction-framework.md)。

### 4. 建立证据账本

只记录会影响决策的信息，并标注为：

| 类型 | 含义 |
| --- | --- |
| 项目事实 | 可由当前文档、代码、测试或运行结果证明 |
| 用户表达 | 用户明确说明的目标、限制或偏好 |
| 产品推断 | 基于材料形成、仍需验证的判断 |
| 默认假设 | 风险较低且可安全继续的补全 |
| 冲突 | 来源之间存在不兼容口径 |
| 待验证 | 当前材料不足，不能升级为结论 |

若冲突会改变业务语义、范围、数据或验收，先展示冲突并请求决策，不自行选择。

### 5. 对需求分级

输出一张需求分级卡：

```text
需求级别：小型 / 中型 / 复杂
判断依据：业务不确定性、影响范围、数据/契约、算法/风险、验证成本
强制升级项：无 / 具体项目门禁
本轮采用流程：实际执行的步骤
明确省略：不需要的文档、确认或门禁
```

分级概要：

- **小型**：目标和验收明确，局部、可逆，不改变共享语义、数据契约或核心规则。
- **中型**：存在局部产品决策，影响一个完整流程或多个相邻组件，需要比较方案和一次设计确认。
- **复杂**：核心问题或规则仍有不确定性，跨模块/角色/端，或影响算法、共享契约、持久化、安全、迁移及高风险边界。

先执行项目自身的强制门禁；需要完整评分、升级规则和示例时读取 [references/requirement-levels.md](references/requirement-levels.md)。

### 6. 按级别澄清

#### 小型需求

- 若项目事实和用户输入已能确定目标行为与验收，不提问。
- 若只有一个阻塞缺口，只问该问题。
- 使用保守默认值处理低风险细节，并明确记录。

#### 中型需求

- 内部整理全部缺口，但一次只向用户提出一个最高影响问题。
- 优先澄清目标用户、核心流程、范围边界、数据含义和成功标准。
- 当答案已足够选择方案时停止提问，不追求模板完整。

#### 复杂需求

- 先判断是否包含多个可以独立验证的子需求；过大时先拆分依赖和实施顺序。
- 逐个澄清决定业务语义、算法、数据、权限、验收和范围的阻塞问题。
- 客户、业务或数据证据不足时明确标记“材料不足”，并设计下一轮验证，不以产品推断填空。

提问时优先给出推荐选项及影响，开放问题只用于无法合理枚举的场景。

### 7. 开展方案碰撞

- 小型需求只有在确有不同用户行为或风险时才比较方案。
- 中型需求比较 2 个或 2～3 个有意义的方案。
- 复杂需求比较 2～3 个方案，并在相关时加入“不开发、调整流程或复用现有能力”的替代方案。

每个方案说明：核心思路、解决程度、收益、代价、风险、依赖、可逆性和验证方式。先给推荐，再说明不选其他方案的原因。

详细比较框架见 [references/approach-comparison.md](references/approach-comparison.md)。

### 8. 形成分级设计并确认

- **小型**：给出几句话的需求快照。用户原意和验收已经明确时，不增加设计确认门禁。
- **中型**：给出一份紧凑设计，包含推荐方案、用户流程、状态/数据影响、异常和验收；用户要求后续实施时，获得一次整体确认。
- **复杂**：按问题与范围、产品方案、规则/数据、异常/兼容、验证五个主题分段呈现；仅对仍含重要决策的部分请求确认，避免机械逐段确认。

设计完成后做一次自检：

1. 是否仍有 `TBD`、模糊词或未说明的默认值。
2. 问题、推荐方案、流程、数据和验收是否相互一致。
3. 是否可以由一个工作项完成；否则继续拆分。
4. 是否存在两种合理解释。
5. 是否包含无证据的价值、效率、准确率或用户意愿结论。

### 9. 定义验证与反证

中型和复杂需求至少回答：

- 什么可观察结果证明功能行为完成。
- 什么业务或用户证据证明问题值得继续投入。
- 什么证据会表明现有方式已经足够、用户不会采用或方案方向错误。
- 失败、无解、数据不足、冲突和回退如何处理。
- 谁确认结果，使用什么数据，在什么场景复核。

### 10. 输出并路由

根据需求级别使用 [references/output-contracts.md](references/output-contracts.md) 中的最小模板，不为了模板完整扩大内容。

默认路由：

- **小型需求**：需求快照；如果用户已要求实施且项目允许，回到项目默认最小执行路径。
- **中型需求**：紧凑 Feature Design；需要研发交底时交给 `write-prd`，触发项目强制规格门禁时升级为复杂流程。
- **复杂需求**：需求发现结论或分解方案；研究材料先交给 `research-summary`，确认产品口径后交给 `write-prd` 或项目指定的正式规格流程。

不要在用户只要求需求发现时自动创建 PRD、Spec Kit 目录、任务清单或实现代码。

## 完成条件

完成需求发现必须满足：

- 真实问题和用户提出的解法已分开。
- 事实、推断、假设、冲突和待验证项已分开。
- 需求级别、判断依据和所采用流程清楚。
- 阻塞问题已解决，或明确说明为什么暂时不能继续。
- 中型/复杂需求已经过真实方案碰撞并给出推荐。
- MVP、非范围、成功标准和反证标准可执行。
- 下一步路由明确，且没有提前越过用户或项目门禁。
