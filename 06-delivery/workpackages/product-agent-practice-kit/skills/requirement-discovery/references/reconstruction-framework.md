# 需求还原框架

## 1. 问题定义

先完成以下句式，缺失项按“待确认”处理：

```text
角色：谁承担这项任务或决策？
情境：在什么阶段、入口或触发条件下发生？
任务：用户真正要完成什么，而不是想点击什么？
现状：目前怎样完成，使用哪些工具、数据或人工判断？
损失：哪里耗时、出错、不可解释、不可追溯或影响决策？
时机：为什么现在值得解决？
目标：改进后什么业务结果应该发生？
```

## 2. 问题与解法分离

把用户原始输入拆成四列：

| 项目 | 内容 |
| --- | --- |
| 真实问题 | 需要改善的业务结果或风险 |
| 用户提出的解法 | 用户当前想做的功能、页面、算法或AI能力 |
| 必须达到的结果 | 不依赖具体实现方式的可观察行为 |
| 其他可选方式 | 复用现有能力、调整流程、人工校核、延后或不做 |

如果只能描述功能，不能描述问题和结果，说明需求尚未还原完成。

## 3. 证据账本

```markdown
| 结论或信息 | 类型 | 来源 | 可信度/限制 | 对需求的影响 |
| --- | --- | --- | --- | --- |
```

类型限定为：项目事实、用户表达、产品推断、默认假设、冲突、待验证。

规则：

- 客户认可方向不等于真实使用验证。
- Demo 当前行为不等于正式产品规则。
- 产品介绍不等于用户需求证据。
- 代码行为与已确认产品口径冲突时，先展示冲突。
- 没有实际数据、操作或决策证据时，不承诺提效、准确率、采纳率或商业价值。

## 4. 提问优先级

按以下顺序选择唯一的下一个问题：

1. 答案是否会改变这个问题值不值得做。
2. 是否会改变小型、中型或复杂分级。
3. 是否会改变MVP和非范围。
4. 是否会改变业务语义、算法、数据或权限。
5. 是否会改变验收和失败处理。

低风险的布局、命名和技术细节优先采用项目惯例或保守默认值，不占用用户决策。

提问格式建议：

```text
当前需要先确认的是【问题】。它会影响【范围/规则/验收】。
我建议【选项A】，因为【依据】；如果选择【选项B】，则会【主要差异】。
```

一次只发送一个问题。用户回答后直接更新相关结论，不建立独立的澄清流水账。

## 5. 反证与停止条件

至少检查：

- 问题是否真实发生，频率和后果是否足以支持投入。
- 用户是否会改变行为，还是只认可概念。
- 现有工具或流程是否已经足够。
- 所需数据、责任人和复核机制是否存在。
- 如果核心假设不成立，是否有更小替代方案。

为中型和复杂需求写出：

```markdown
- 支持继续投入的证据：
- 表明需要校准的证据：
- 表明应该停止或改方向的证据：
- 下一次验证的数据、场景和确认人：
```

## 6. 完成检查

- 能否不用功能名描述真实问题？
- 能否说明用户目前怎样处理？
- 能否指出用户提出的解法之外至少一种选择？
- 能否区分已经证明的事实和待验证价值？
- 能否写出成功证据与失败证据？

任一关键答案为否时，不应把需求包装成正式完整方案。
