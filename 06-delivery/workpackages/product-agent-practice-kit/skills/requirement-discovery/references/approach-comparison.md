# 方案碰撞参考

## 目的

让产品选择建立在目标、约束和证据上，而不是把最先提出的功能补写成唯一方案。

## 何时必须比较

- 中型需求存在不同流程、数据或交互路径。
- 复杂需求涉及架构边界、算法、跨端、迁移或多个建设阶段。
- 用户直接给出了解法，但真实问题可以用其他方式解决。
- 完整方案成本较高，可以先用较小方案验证价值。

小型需求没有真实选择时不要强行比较。

## 候选方案类型

根据实际情况选择 2～3 个：

- 最小验证方案：最少改动证明核心价值。
- 平衡方案：在价值、风险和成本之间取得当前最优平衡。
- 完整方案：覆盖长期能力，但投入和依赖更高。
- 流程方案：不开发或少开发，通过流程、配置或人工校核解决。
- 复用方案：扩展现有能力，避免新建平行模块。

不允许把同一方案的细微命名或布局差异包装成多个方案。

## 比较维度

| 维度 | 需要回答的问题 |
| --- | --- |
| 目标覆盖 | 能解决多少核心问题，遗漏什么 |
| 用户行为 | 用户流程和学习成本怎样变化 |
| 数据与契约 | 是否新增权威数据、迁移或兼容负担 |
| 规则与算法 | 是否改变硬规则、目标或解释口径 |
| 实施成本 | 涉及哪些模块、角色和依赖 |
| 风险 | 最可能失败或产生误用的地方 |
| 可逆性 | 失败后能否安全回退或切换 |
| 验证速度 | 多快能获得真实价值证据 |
| 长期演进 | 是否形成重复模型或阻碍后续扩展 |

## 输出格式

```markdown
### 方案A：<名称>

- 核心思路：
- 主要收益：
- 代价与依赖：
- 风险和不适用条件：
- 验证方式：

### 推荐结论

- 推荐：方案X
- 原因：
- 暂不选择其他方案的原因：
- 重新评估条件：出现什么证据时切换方案
```

复杂需求可增加紧凑比较表，但表格不能代替推荐理由。

## 推荐原则

- 先给推荐，不把优先级判断全部退回用户。
- 推荐必须直接对应问题、证据、约束和当前阶段。
- 优先选择能形成完整验证闭环的最小方案，而不是功能最少的残缺方案。
- 长期方案只有在核心价值和关键依赖已经验证时才优先。
- 如果所有方案都依赖同一个未验证假设，先设计验证，不急于选实现方案。

## 反模式

- 只给一个方案并称其为最佳实践。
- 方案数量很多但没有实质差异。
- 只比较开发成本，不比较用户行为和业务价值。
- 为了避免决策把所有方案都放进MVP。
- 不说明为什么不选其他方案。
- 把临时Demo实现升级为长期产品模型。
