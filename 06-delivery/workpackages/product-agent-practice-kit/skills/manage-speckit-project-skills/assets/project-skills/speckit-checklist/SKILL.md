# 需求质量检查表

检查表是“需求写作的单元测试”，检查规格本身是否足以进入实现，而不是检查系统是否已经实现。

## 输入

考虑用户本次输入；未提供额外要求时，从当前 Feature 的 `spec.md`、`plan.md` 和 `tasks.md` 推导检查重点。

## 工作流

1. 从仓库根目录运行：

   ```powershell
   .specify/scripts/powershell/check-prerequisites.ps1 -Json
   ```

   使用返回的 `FEATURE_DIR` 和 `AVAILABLE_DOCS`，文件操作使用绝对路径。

2. 存在 `.specify/memory/constitution.md` 时读取其中的项目原则。

3. 识别检查主题、使用人、使用时点、风险重点和深度。只有缺失信息会实质改变检查表时才提问，首轮最多三个问题；必要时最多再追问两个，合计不得超过五个。

4. 按当前重点读取必要的规格内容，避免整份重复加载：

   - `spec.md`：需求、范围和成功标准。
   - `plan.md`：依赖、数据和契约。
   - `tasks.md`：实施覆盖关系。

5. 在 `FEATURE_DIR/checklists/` 下创建或追加 `[主题].md`：

   - 文件不存在时从 `CHK001` 开始。
   - 文件已存在时保留原内容，从最后一个编号继续追加。
   - 不得删除或覆盖已有检查项。

6. 检查项按以下质量维度组织：

   - 需求完整性。
   - 表述清晰度。
   - 规则一致性。
   - 验收标准可度量性。
   - 主流程、备选流程、异常、恢复和非功能场景覆盖。
   - 边界条件。
   - 依赖和假设。
   - 歧义、冲突和缺口。

7. 至少 80% 的检查项包含一种追溯标记：

   - `[Spec §章节或需求ID]`
   - `[缺口]`
   - `[歧义]`
   - `[冲突]`
   - `[假设]`

8. 候选项超过 40 条时按风险和影响合并、去重，不为低影响细节堆砌条目。

## 写法要求

正确示例：

```markdown
- [ ] CHK001 是否定义了所有接口失败场景的错误响应格式？[完整性，Spec §FR-006]
- [ ] CHK002 “快速加载”是否量化为明确的时间阈值？[歧义，Spec §NFR-002]
- [ ] CHK003 是否说明无数据、部分失败和恢复场景的需求？[缺口]
- [ ] CHK004 页面和接口中的权限规则是否一致？[一致性]
```

禁止写成实现测试：

```markdown
- [ ] 验证按钮可以点击
- [ ] 测试接口返回 200
- [ ] 确认页面正确渲染
```

检查项必须询问“需求是否定义清楚”，不能询问“系统是否运行正确”，也不能引入框架、算法或测试步骤等实现细节。

## 完成

优先使用 `.specify/templates/checklist-template.md` 的结构；模板缺失时使用一级标题、目的与创建时间、二级分类标题及 `- [ ] CHK###` 条目。

向用户报告：

- 检查表绝对路径。
- 新建还是追加。
- 条目数量。
- 检查主题、深度和使用人。
- 已纳入的用户特别要求。
