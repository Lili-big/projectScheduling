# PRD 写作

## 目标

输出产品、研发和测试可以直接理解和执行的中文需求交底文档。文档应脱离聊天上下文也能说清楚业务目标、范围边界、用户可见行为、数据口径、前后端或算法职责、异常处理和验收标准。

`write-prd` 只有一个入口，内部按用户输入路由到两种模式：

- 默认 PRD 模式：输出页面、模块、业务流程或功能点的产品 PRD。
- 显式算法/规则交底模式：当用户明确提到算法、目标函数、约束、指标、CP-SAT、排程规则或“把算法讲清楚”时，输出算法/规则交底文档。

## 路由规则

### 默认 PRD 模式

用户要求写 PRD、需求文档、产品需求、研发交底、完善需求、沉淀文档，且目标对象是页面、模块、交互、业务流程、功能点、截图、原型或用户可见行为时，使用默认 PRD 模式。

默认 PRD 模式关注：

- 业务问题、用户目标和本次范围。
- 页面布局、入口、按钮、弹窗、状态、提示和用户流程。
- 数据来源、字段含义、枚举、单位、默认值和保存/失效规则。
- 前端、后端、数据服务或算法服务的职责边界。
- 异常、空态、禁用、失败态和可执行验收标准。

### 显式算法/规则交底模式

只有用户明确要求算法文档、规则说明、目标函数说明、约束规则、指标解释、CP-SAT/排程算法交底，或明确说“把算法讲清楚”时，使用算法/规则交底模式。

算法/规则交底模式关注：

- 算法或规则在业务链路中的位置。
- 输入对象、字段含义、单位、默认值和来源。
- 硬约束、软目标、诊断指标、展示指标和冲突优先级。
- 正常流程、失败/超时/回退流程和兼容场景。
- 典型案例、结果解释和验收口径。

### 不使用本 skill 的场景

- 用户说“评审、审一下、方案评审、该不该做、判断是否推进”时，进入需求评审流程，而不是直接写 PRD。
- 用户需求边界不清且会影响产品规则时，先澄清或做需求发现，不直接定稿。
- 用户要求实现、修复页面/接口/算法或跑 Demo 时，进入实现流程。
- 用户要求正式 Spec Kit 规格化开发时，进入 Spec Kit 流程。
- 用户只问代码怎么工作、接口怎么调或技术方案怎么设计，默认直接解释，不包装成 PRD。

## 共用原则

- 以产品经理视角写交底文档。读代码是为了确认事实，最终表达要让研发和测试理解“要交付什么、如何判断完成”。
- 区分产品目标、现有代码事实、Demo 限制、临时模拟和默认假设。不要把 Demo 临时接口、写死数据、全局状态或模拟逻辑写成正式产品规则。
- 用户最新明确说明优先于旧截图、旧文档、旧原型和当前代码。
- 精确保留用户明确给出的按钮名、弹窗文案、标签、状态名、流程分支和业务术语。
- 只写会影响实现、数据、交互、计算、展示或验收的内容；不要为了模板完整而扩大范围。
- 少写 HTTP 路径、请求体、数据库表、函数名、组件名和内部状态名；只有用户明确要求接口契约，或研发不开具体字段无法开工时，才补充最小必要技术细节。
- 非范围只写会造成研发误解的边界；后续建议只保留能避免当前误解或明确二期边界的内容。
- 验收标准必须可执行、可测试，能拆成测试场景。

## 输入处理

最低输入：

- 目标对象：页面、模块、流程、功能、算法或规则名称。
- 交付意图：新写、完善、更新、同步人工修改版，或只在聊天中输出。

可选输入：

- 用户说明、截图、原型、现有 PRD、历史文档、人工修改版、代码路径、接口材料、测试样例。

信息不足时：

- 如果缺口会改变产品行为、算法规则、数据契约或验收结论，先问用户确认。
- 如果缺口风险低，选择保守默认值，并在文档的“假设”或最终说明中标明。
- 不要求用户一次性补全所有信息；先用现有材料推进到可评审草稿。

## 默认工作流程

1. 判断任务是否应该使用 `write-prd`，再判断进入默认 PRD 模式还是算法/规则交底模式。
2. 明确输出位置：聊天草稿、更新现有文档，或写入项目文档目录。
3. 最小化读取材料：
   - 有项目规则时先读项目入口说明，例如 `AGENTS.md`、`agent.md` 或同类协作规则。
   - 有现有 PRD 时先读目标文档和相关文档。
   - 只有需要确认字段、状态、接口能力、算法行为或数据流时才读代码。
   - 代码阅读优先锚定模型、入口、领域 helper、服务层、测试和前端展示位置，不做无目的全量扫描。
4. 提炼产品/规则口径，不复述实现过程。
5. 按所选模式输出或更新文档。
6. 自检：范围是否收敛、Demo 是否误写成目标、规则是否可验收、假设是否标明。
7. 若修改仓库文件，按项目要求做轻量格式检查；不默认改 README、`.gitignore`、提交 git 或扩大文档索引。

## 默认 PRD 模式输出结构

项目已有固定模板时优先沿用。没有固定模板时，使用以下结构，并按实际范围删减：

```markdown
# <页面、模块或功能>需求文档

版本：
日期：
适用范围：
面向对象：

## 1. 需求背景
## 2. 需求目标
## 3. 范围边界
## 4. 数据口径
## 5. 页面交互 / 用户流程
## 6. 前后端职责
## 7. 异常处理
## 8. 验收标准
## 9. 假设与后续建议（可选）
```

默认 PRD 模式写作要求：

- 背景写具体业务问题、用户误解、触发场景和改造原因，不写泛化铺垫。
- 页面或流程类需求先写用户看得见的结构、控件、状态和动作，再写职责边界。
- 数据定义优先用表格列出字段、含义、来源、单位、是否必填和展示/编辑状态。
- 交互规则写清楚进入、查看、新增、编辑、删除、保存、提交、禁用、加载和错误提示。
- 避免“支持管理”“优化体验”这类空泛表达，拆成具体动作、条件和结果。
- 最终文档只保留最新产品口径；旧文案、历史版本差异或“替换为”的过程说明只在用户要求对比或会影响替换实现时保留。

## 算法/规则交底模式输出结构

项目已有固定模板时优先沿用。没有固定模板时，使用以下结构，并按复杂度删减：

```markdown
# <算法或规则>需求文档

版本：
日期：
适用范围：
面向对象：

## 1. 文档目标
## 2. 在系统链路中的位置
## 3. 输入与前置条件
## 4. 核心算法 / 规则思想
## 5. 硬约束、软目标和诊断输出
## 6. 指标解释与展示口径
## 7. 典型案例
## 8. 前后端 / 算法与展示职责
## 9. 异常、降级与回退
## 10. 验收标准
## 11. 交付边界
```

算法/规则交底写作要求：

- 先解释业务问题和算法位置，再解释输入、约束、目标和输出。
- 明确区分硬约束、软目标、诊断指标和展示指标。
- 不把诊断指标写成已实现目标项，不把展示解释值写成完整求解器目标值，除非代码和文档均能证明。
- 复杂算法优先补充链路图、目标分层图、指标树或典型案例；不要为了形式强行补图。
- 目标函数或评分指标较多时，用统一表格说明：业务问题、风险/惩罚场景、计算口径、数值解释、冲突优先级和验收口径。
- 验收标准覆盖入口分支、成功主路径、失败/超时回退、硬约束满足性、主要软目标正反场景、诊断和展示口径。

### 算法计算方式写法

算法/规则交底中的计算方式要让研发知道如何实现，也要让产品和测试读懂业务口径。默认写法如下：

- 先用业务名解释公式，再在必要时补充最小字段名；不要把代码变量名、函数名或 CP-SAT 模型变量作为正文主表达。
- 目标函数贡献统一写成“业务罚分 × 业务权重”，例如“普通工程均衡罚分 × 普通工程均衡权重”。
- 复杂指标使用“计算步骤”，不要压缩成一行代码式公式。步骤通常包括：参与范围、排序/分组、时间或空间窗口、单项偏差、汇总罚分、目标贡献。
- 内部字段名只在以下场景保留：接口契约必须对齐、测试验收需要定位字段、或用户明确要求研发看具体字段。
- 公式中的名称优先使用业务术语，例如“实际计划开始时间”“理想开始时间”“展开窗口”“缓冲不足天数”；避免直接写 `abs()`、`max()`、临时变量名或内部 helper 名。

推荐示例：

```text
普通工程均衡罚分 =
所有普通任务“实际计划开始时间与理想开始时间的偏差天数”之和

普通工程均衡目标贡献 =
普通工程均衡罚分 × 普通工程均衡权重
```

当指标较复杂时，先写“只统计普通工程任务”，再写“按桥梁、工区、左右幅、墩台 / 支承位置、任务顺序形成稳定排序”，再写“在允许展开窗口内计算每个任务的理想开始时间”，最后写偏差和目标贡献。

## 编辑与版本规则

写入或更新项目文档时：

- 先遵守项目自己的 `AGENTS.md`、`agent.md` 或同类规则。
- 保留已有文档中仍正确且有价值的内容；旧结构不适合研发交底时可以重组。
- 正式文档发生需求语义更新时更新版本和日期；纯错别字、空白、链接、格式修复可不升级版本。
- 如果文件名和文档头部同时包含版本号，两处必须一致。
- 不在正文记录“我是如何生成的”“比较了哪些版本”“从哪个版本改到哪个版本”等过程性内容。
- 不默认修改 README、文档索引、`.gitignore` 或 git 提交，除非用户明确要求。

## 人工修改版或附件同步

用户提供人工修改版、富文本导出、表格复制文本或截图时：

- 吸收产品语义变化：角色、边界、字段可编辑性、流程分支、状态、验收口径。
- 忽略格式噪声：标题编号丢失、圆点符号变化、制表符表格、反引号丢失、空行变化。
- 当人工修改删除非范围、异常提示、验收项或扩展说明时，视为可能的产品收口；只要不与最新明确口径冲突，就不要为了模板完整性自动补回。
- 当人工修改与最新明确口径冲突且会改变产品逻辑时，先说明冲突并要求确认。

## 质量自检

输出前检查：

- 是否选对模式：默认 PRD，还是显式算法/规则交底。
- 是否只覆盖本次目标对象，没有扩展到相邻系统。
- 是否把 Demo、mock、写死数据或临时接口误写成产品目标。
- 是否区分产品目标、代码事实和默认假设。
- 是否保留用户最新明确口径。
- 是否少写了会影响实现和验收的关键字段、状态、异常或分支。
- 验收标准是否能直接拆成测试用例。

## 路由示例

- “帮我把资源配置页面写成研发交底 PRD” -> 默认 PRD 模式。
- “完善任务视图页面需求文档，补充空态和错误态” -> 默认 PRD 模式。
- “把精排目标函数讲清楚，形成算法需求文档” -> 算法/规则交底模式。
- “说明固定资源下最短工期的分支规则和验收口径” -> 算法/规则交底模式。
- “评审一下这个需求该不该做” -> 不使用本 skill，进入需求评审。
- “直接修复这个接口报错” -> 不使用本 skill，进入实现/调试流程。
