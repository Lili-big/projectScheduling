# 排程算法当前实现交底文档

版本：v1.2

日期：2026-07-09

适用范围：桥梁施工排程 Demo 的任务生成、固定资源最短工期、固定工期最少资源、资源成本优化、目标函数、桩基资源规则、现浇连续梁规则和结果诊断

面向对象：产品、算法研发、后端研发、前端研发、测试、计划工程师

文档性质：算法 / 规则交底文档

## 1. 文档目标

本文档回答当前实现如何工作，以及下游研发和测试应按什么口径理解结果。核心目的是把排程算法拆成可验证的产品规则：

- 用户点击“固定资源条件下，推算最短工期”后，系统如何流转。
- 用户点击“固定工期条件下，推算最少资源”后，系统如何流转。
- 任务关系、资源关系、目标函数和诊断指标分别承担什么职责。
- 桩基工程和现浇连续梁分别有哪些硬逻辑、弱约束和诊断输出。
- 当前文档需要下游明确改什么、为什么改、怎么验收。

本文以当前后端 Python 实现为准；Netlify 演示 API 仅作为演示参考。

## 2. 总体链路

当前排程链路为：

```text
ScenarioInput
  -> GeneratedScheduleInput / ScheduleInput
  -> ScheduleResult
  -> ScenarioSolveResult / ScenarioAlternativeResult
```

产品上可以理解为四步：

1. 前端提交项目结构、工艺工效、工艺逻辑、资源池、里程碑和求解策略。
2. 后端先生成任务图，包括任务、工期、候选资源和前后置关系。
3. 求解器基于当前入口选择命名资源模型或容量模型。
4. 前端展示主结果、候选方案、里程碑偏差、目标函数拆解和诊断。

主要入口如下：

| 用户入口 | 后端含义 | 当前结果定位 |
| --- | --- | --- |
| 生成任务图 | 生成任务、资源候选和关系 | 用于求解前校验 |
| 固定资源条件下，推算最短工期 | 使用当前资源数量跑完整目标函数精排 | 主方案，回答“现有资源能排到哪里” |
| 固定工期条件下，推算最少资源 | 使用资源上限搜索满足目标的最少资源数量，并默认复排 | 资源建议，回答“要满足目标至少需要多少资源” |
| 固定工期资源成本优化 | 在目标工期下搜索增量成本更低的资源组合 | 主方案之外的成本测算 |
| 方案对比 | 读取已有结果指标做比较 | 展示层汇总 |

## 3. 任务图如何生成

任务图生成是所有求解入口的前置步骤。生成阶段的产品口径如下：

| 输入 | 产品作用 |
| --- | --- |
| 项目结构 | 决定桥梁、工区、墩台、构件和上部结构范围 |
| 工艺工效库 | 决定每类构件用什么工艺、资源类型和工期算法 |
| 工艺逻辑 | 决定任务之间谁先谁后、间隔多少天 |
| 上部结构逻辑 | 决定现浇箱梁、现浇连续梁和下部结构之间的衔接 |
| 资源池 | 决定可展开多少台设备或班组，以及资源上限 |
| 里程碑 | 决定结果是否满足目标节点 |
| 求解策略 | 决定目标函数项、权重、普通任务窗口和工作面上限 |

生成阶段做的事情：

1. 按桥梁、工区、结构物和构件生成下部结构任务。
2. 根据工艺工效库计算每个任务工期，单位统一为自然日。
3. 根据工艺逻辑生成 `PrecedenceLink`，作为后续求解硬关系。
4. 派生现浇箱梁、现浇连续梁任务和上部结构关系。
5. 按当前资源池展开命名资源，或按最大资源生成候选上限。
6. 为任务匹配兼容资源类型。
7. 输出任务数、关系数、资源数、连续梁任务数和生成诊断。

若生成阶段出现错误级诊断，求解入口返回 `MODEL_INVALID`，求解流程在任务图校验阶段结束。

## 4. 关系算法如何计算

关系算法的产品含义是：把配置中的施工逻辑转换成求解器必须满足的时间关系。

### 4.1 通用工艺关系

当前关系支持 4 种：

| 关系 | 产品含义 |
| --- | --- |
| `FS` | 前置完成后，后续才能开始 |
| `SS` | 前置开始后，后续才能开始 |
| `FF` | 前置完成后，后续才能完成 |
| `SF` | 前置开始后，后续才能完成 |

所有关系都支持 `lag_days`。例如“承台在桩基完成 3 天后施工”，产品表达为：

```text
承台开始时间 >= 桩基完成时间 + 3 天
```

这些关系是硬约束。排程结果必须满足前后置关系。

### 4.2 下部结构关系

下部结构关系主要来自工艺逻辑规则：

| 后续任务 | 当前默认前置口径 |
| --- | --- |
| 承台 | 同一结构物内所有桩基完成后施工 |
| 地系梁 | 同一结构物内所有桩基完成后施工 |
| 墩身 | 优先承台；没有承台时回退到地系梁或桩基 |
| 盖梁 | 墩身 / 中系梁完成后施工 |
| 桥台台身 | 优先承台；没有承台时回退到桩基或扩大基础 |

### 4.3 现浇连续梁关系

现浇连续梁会额外生成专项关系：

| 关系 | 当前硬逻辑 |
| --- | --- |
| 下部前置 | 0 号块和边跨连续段等待对应墩台下部完成锚点 |
| T 构链路 | 0 号块完成后，左 / 右标准段才能开始 |
| 左右标准段同步 | 同一 T 构左 / 右标准段开始时间相同、完成时间相同 |
| 边跨合龙 | 边跨连续段和相邻 T 构对应侧标准段都完成后才能开始 |
| 中跨合龙 | 相邻两个 T 构面向合龙口的标准段都完成后才能开始 |
| 合龙同步窗口 | 边跨或中跨合龙两侧前置完成时间差默认上限为 7 天 |
| 合龙顺序 | 默认边跨先于中跨；多个中跨按配置顺序推进 |

合龙段具备条件后的开始时间，主要由总工期、控制节点迟延和资源约束共同影响；当前目标函数按第 7 章的 4 个目标项计算。

## 5. 固定资源最短工期分支

用户点击“固定资源条件下，推算最短工期”后，系统使用当前资源数量求解。流程如下：

```text
生成当前资源任务图
  -> 按 ResourcePool.quantity 展开命名资源
  -> 运行完整目标函数精排
  -> 计算 target_achievement
  -> 返回当前资源主结果
  -> 如业务目标未达成，再进入资源增量建议
```

### 5.1 为什么保留当前资源结果

当前资源只要能形成物理可行排程，系统就保留这份排程。产品原因是：计划工程师需要看到现有资源与目标之间的差距，包括晚点天数、超期天数和资源建议入口。

### 5.2 主结果状态

| 情况 | 结果来源 | 产品解释 |
| --- | --- | --- |
| 可行且业务目标达成 | `current_resources_control_priority_balanced` | 当前资源满足目标 |
| 可行但业务目标未达成 | `current_resources_target_failed` | 当前资源有参考排程，但节点或工期失败 |
| 求解超时无法确认 | `target_unconfirmed` | 当前预算内无法判断资源是否足够 |
| 物理不可行 | `physical_infeasible` | 工艺关系、资源覆盖或硬规则无法形成排程 |

业务目标状态统一看 `target_achievement`：

| 字段 | 产品含义 |
| --- | --- |
| `business_success` | 强制节点迟延和固定工期超期均为 0 时为 true |
| `target_status` | 当前资源、候选资源或最大资源的目标状态 |
| `hard_milestone_late_days` | 强制里程碑累计迟延天数 |
| `fixed_duration_overrun_days` | 固定工期目标超期天数 |
| `failure_reasons` | 目标失败或未确认原因 |
| `evaluated_at_source` | 判定来自当前资源、候选资源或最大资源 |

### 5.3 资源增量建议如何计算

当当前资源能排出计划但目标失败时，系统进入资源建议分支：

1. 先计算剥离资源排队影响的工艺逻辑关键路径。
2. 如果关键路径本身已经晚于目标，返回“关键路径不可压缩”。
3. 使用资源池 `max_quantity` 生成最大资源场景。
4. 根据当前迟延天数形成“压力目标”：每轮把目标向关键路径下界压缩一段。
5. 用容量模型搜索候选资源数量。
6. 若候选数量没有超过当前下界，继续加压；若已经到关键路径下界则停止。
7. 将候选资源数量带回完整目标函数复排。
8. 只有候选复排通过 `target_achievement`，才作为方案 2 返回。

资源建议的结论字段：

| 字段 | 产品含义 |
| --- | --- |
| `resource_recommendation_status` | 推荐状态，例如已验证、上限不足、未确认、关键路径不可压缩 |
| `recommended_resource_counts` | 每类资源当前数量、推荐数量、新增数量和上限 |
| `resource_upper_bound_counts` | 每类资源搜索上限 |
| `resource_capacity_lower_bounds` | 容量粗算下界 |
| `pressure_search_status` | 压力搜索状态 |
| `pressure_search_attempts` | 每轮压力目标、容量模型结果和完整复排结果 |
| `recommended_resources` | 推荐组合和验证结果摘要 |

当前实现采用两段校验：容量模型负责找候选数量；最终可展示候选必须经过完整目标函数复排。

## 6. 固定工期最少资源分支

用户点击“固定工期条件下，推算最少资源”后，系统使用资源上限搜索满足目标所需的最少资源。流程如下：

```text
生成最大资源任务图
  -> 确定目标工期或强制里程碑
  -> 最大资源硬目标快速预检
  -> 资源下界诊断
  -> 容量模型搜索资源数量
  -> 完整目标函数复排
  -> 返回推荐资源数量和排程结果
```

### 6.1 目标来源

目标工期优先来自可匹配的强制里程碑。若没有强制里程碑，可使用固定资源结果的总工期作为 fallback target。

没有可匹配强制里程碑且没有 fallback target 时，系统返回 `MODEL_INVALID`，提示需要先配置目标或先运行固定资源分支。

### 6.2 最大资源预检

系统先用 `max_quantity` 做快速预检：

| 预检结果 | 产品解释 |
| --- | --- |
| 通过 | 说明资源上限理论上可能满足目标，继续搜索最少资源 |
| `UNKNOWN` | 限时内无法确认，保持未确认状态 |
| `max_resources_target_failed` | 最大资源仍无法满足目标，需要提高上限或调整工期目标 |
| `physical_infeasible` | 资源、工艺或任务关系本身存在物理不可行 |

### 6.3 资源数量搜索与复排

容量模型会在每类资源的当前下界和最大上限之间搜索组合。搜索到的数量会形成 `recommended_resource_counts`。

默认情况下，系统还会用推荐数量运行完整目标函数复排。结果来源可能包括：

| 来源 | 产品含义 |
| --- | --- |
| `control_priority_balanced_reoptimization` | 推荐数量通过完整目标函数复排 |
| `minimum_resources_best_effort_refinement` | 严格复排未满足目标，但返回了放松目标后的可查看排程 |
| `capacity_model_verified_schedule` | 容量模型结果已验证，但完整复排没有可用结果 |
| `capacity_model_unverified` | 容量模型候选未能形成可验证排程 |

因此，前端和测试需要同时检查 `status=OPTIMAL/FEASIBLE`、`target_achievement` 和 `recommended_schedule_source`。

## 7. 当前目标函数

当前完整目标函数只保留 4 个可配置目标项：

| 目标项 ID | 名称 | 默认权重 | 原始罚分含义 | 产品优先级 |
| --- | --- | ---: | --- | --- |
| `control_node_late` | 控制节点迟延 | 10,000,000,000 | 软控制节点迟延、放松目标下的强制节点迟延、固定工期超期 | 最高 |
| `makespan_and_soft_milestone` | 总工期 | 5,000,000 | 项目整体完工跨度 | 高 |
| `resource_path_continuity` | 资源路径连续性 | 50,000 | 同一资源路径跳墩、切幅、机械钻机墩组路径跳跃 | 中 |
| `resource_idle` | 资源空闲 | 50,000 | 同一资源两次任务之间的中途空档 | 中 |

业务计算口径：

```text
目标函数业务汇总 =
控制节点迟延罚分 × 控制节点迟延权重
+ 总工期天数 × 总工期权重
+ 资源路径连续性罚分 × 资源路径连续性权重
+ 资源空闲罚分 × 资源空闲权重
```

`weighted_objective` 是上述 4 项 `weighted_contribution` 的业务汇总。前端展示目标函数时，应优先读取 `objective_contributions`。

### 7.1 目标项开启和关闭

`schedule_strategy.objective_terms` 控制每个目标项是否启用和权重。

| 输出 | 产品含义 |
| --- | --- |
| `objective_terms_used` | 用户配置和本次有效权重 |
| `objective_weights` | 求解器本次实际使用的权重 |
| `objective_modeling_gates` | 目标项本次是否真实进入模型 |
| `objective_contributions` | 每个目标项的原始罚分和加权贡献 |

目标项关闭后，只关闭对应软目标。任务工期、工艺前后置、资源互斥、连续梁同步、连续梁班组占用等硬规则仍然生效。

### 7.2 指标分类

| 指标 | 分类 | 是否进入当前 4 项目标函数 |
| --- | --- | --- |
| `objective_contributions` | 目标函数拆解 | 是 |
| `target_achievement` | 业务目标判定 | 由迟延 / 超期计算得出，用于结果判定 |
| `continuity_score` | 施工连续性诊断评分 | 否 |
| `normal_balance_metrics` | 普通工程分布诊断 | 否 |
| `control_priority_analysis` | 控制链解释 | 否 |
| `drill_group_refinement` | 桩基墩组诊断 | 部分路径罚分可能进入资源路径连续性目标 |
| `continuous_beam_team_spans` | 连续梁班组占用诊断 | 班组占用本身是硬资源约束 |

## 8. 桩基工程规则

桩基工程需要同时看工艺逻辑、资源分配和目标函数。资源路径连续性属于软目标，硬逻辑以工艺前后置、资源互斥和机械钻机墩组为准。

### 8.1 桩基硬逻辑

| 规则 | 当前实现口径 |
| --- | --- |
| 工期计算 | 桩基任务按工艺工效库计算，可按根数或桩长等工程量来源换算 |
| 下游前置 | 承台、地系梁等任务必须等待同一结构物桩基完成 |
| 命名资源分配 | 有受限候选资源的桩基任务必须选择一个命名资源 |
| 命名资源互斥 | 同一设备或班组同一时间只能做一个任务 |
| 机械钻机墩组 | 旋挖钻、回旋钻、冲击钻按幅别、墩号、工艺和结构类型形成墩组 |
| 墩组内部排序 | 同一机械钻机墩组内的桩基任务按桩号或系统桩序从小到大施工 |
| 墩组资源一致 | 同一个墩号下、同一施工工艺、同一结构类型的机械桩基任务分配给同一台兼容钻机 |
| 人工挖孔 | 人工挖孔桩按单桩独立任务管理，每个桩基独立分配普通班组资源 |

机械钻机墩组由算法按“幅别 + 墩号 + 工艺 + 结构类型”自动识别；旋挖钻、回旋钻和冲击钻均适用该规则。人工挖孔桩按单桩维度独立管理，每个桩基独立分配普通班组资源。

### 8.2 桩基弱约束

| 弱约束 / 诊断 | 当前实现口径 |
| --- | --- |
| 资源路径连续性 | 倾向同一钻机按相近墩位、相同幅别推进 |
| 左右幅切换 | 属于资源路径连续性软偏好 |
| 跳墩 | 计入路径罚分或连续性诊断；控制节点、资源互斥和工艺关系优先级更高 |
| 资源空闲 | 倾向减少同一设备两次任务之间的中途空档 |
| 连续性评分 | 用于解释结果质量，与目标函数罚分分开展示 |

产品解释示例：

```text
一台旋挖钻在左幅 1#墩完成后转到左幅 4#墩：
系统会识别为同幅跳墩，增加连续性风险或目标罚分。

当 2#、3#墩受前置、资源或节点限制暂缓施工时，
系统可选择跳墩，并在资源路径连续性目标中体现更高代价。
```

## 9. 现浇连续梁规则

现浇连续梁当前实现的重点是“任务可追溯、左右标准段同步、合龙窗口硬约束、班组按联级占用”。

### 9.1 任务生成

一组连续梁按桥梁、工区和连续梁组号生成任务：

| 任务类型 | 当前生成口径 |
| --- | --- |
| 0 号块 | 每个主墩 T 构生成 1 个任务 |
| 左侧标准段 | 标准块循环数大于 0 时，每个 T 构生成 1 个聚合任务 |
| 右侧标准段 | 标准块循环数大于 0 时，每个 T 构生成 1 个聚合任务 |
| 边跨连续段 | 每组连续梁左右边跨各生成 1 个 |
| 边跨合龙段 | 每组连续梁左右边跨各生成 1 个 |
| 中跨合龙段 | 相邻主墩之间各生成 1 个 |

### 9.2 连续梁硬逻辑

| 规则 | 当前实现口径 |
| --- | --- |
| 下部前置 | 0 号块和边跨连续段等待对应下部完成锚点 |
| 左右标准段同步 | 同一 T 构左 / 右标准段同步开始、同步完成 |
| 合龙前置 | 合龙段等待两侧前置任务完成 |
| 合龙同步窗口 | 两侧前置完成时间差默认上限为 7 天 |
| 合龙顺序 | 边跨先于中跨，中跨按配置顺序推进 |
| 联级班组占用 | 按 `bridge_id + work_section_id + group_index` 形成一联连续梁资源组 |
| 整联分配 | 一整联连续梁分配 1 个连续梁班组 |
| 班组互斥 | 一个连续梁班组同一时间只能占用一联连续梁 |

当前班组规则按整联形成占用窗口。系统保留原任务粒度，资源约束作用在整联窗口上，联内 0 号块、左 / 右标准段、边跨连续段和合龙段按工艺逻辑组织施工：

```text
整联班组占用开始 = 该联内最早任务开始
整联班组占用结束 = 该联内最晚任务完成
```

因此，联内任务按工艺逻辑并行、同步或顺序推进；跨联是否并行由连续梁班组数量决定。

### 9.3 连续梁弱目标和诊断

现浇连续梁对当前 4 项目标函数的影响集中在总工期、控制节点迟延、资源互斥和资源建议。

具体体现在：

- 任务工期和合龙顺序影响总工期。
- 连续梁作为控制对象时，影响控制节点迟延。
- 连续梁班组数量不足时，通过硬资源互斥拉长排程。
- 固定工期最少资源和资源建议会把连续梁班组作为可推荐资源池。

诊断输出重点看 `continuous_beam_team_spans`：

| 字段 | 产品含义 |
| --- | --- |
| `enabled` | 联级班组占用是否启用 |
| `span_count` | 连续梁联级资源组数量 |
| `resource_quantity` | 可用连续梁班组数量 |
| `spans` | 每联的班组、占用起止时间和包含任务 |
| `diagnostics` | 缺少桥梁、工区或组号等识别字段时的告警 |

1. 看 `status` 是否是 `OPTIMAL` 或 `FEASIBLE`。

3. 看 `schedule_source` 判断结果来自当前资源、候选资源、容量模型还是最佳努力。
4. 看 `resource_recommendation_status` 判断是否存在资源建议。
5. 看 `objective_contributions` 展示目标函数分解。

## 12. 验收标准

1. 固定资源入口在当前资源可排程但目标失败时，保留当前资源主排程，并输出 `current_resources_target_failed`。
2. 当前资源满足目标时，输出 `current_resources_control_priority_balanced`，且 `resource_recommendation_status=not_needed`。
3. 当前资源目标失败时，资源建议必须记录 `pressure_search_*` 字段和推荐尝试。
4. 推荐资源候选必须经过完整目标函数复排，且通过 `target_achievement` 后才能作为候选方案展示。
5. 固定工期最少资源入口必须先用最大资源做目标预检；最大资源 `UNKNOWN` 时保持未确认状态。
6. 目标函数展示只包含 4 个目标项：控制节点迟延、总工期、资源路径连续性、资源空闲。
7. `weighted_objective` 等于 `objective_contributions` 中加权贡献之和。
8. 普通工程均衡、连续性评分、控制链分析作为诊断展示。
9. 机械钻机桩基墩组按幅别、墩号、工艺和结构类型成组，组内按桩号或系统桩序从小到大施工，并使用同一台兼容钻机。
10. 人工挖孔桩按单桩独立任务管理，每个桩基独立分配普通班组资源。
11. 现浇连续梁左 / 右标准段同步开始、同步完成。
12. 边跨和中跨合龙两侧前置完成差默认上限为 7 天。
13. 连续梁班组按联级资源组输出 `continuous_beam_team_spans`，并在任务上保留可追溯字段。
14. 输入资源、工艺、逻辑、里程碑或目标函数配置变化后，前端应清空或标记已有求解结果失效。
