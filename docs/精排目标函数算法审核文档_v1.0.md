# 精排目标函数算法审核文档

版本：v1.0

日期：2026-06-28

适用范围：固定资源满足后进入命名资源精排、控制优先精排、普通工程均衡推进相关目标函数

面向对象：产品、算法研发、后端研发、测试、计划工程师

## 1. 文档目标

本文档单独梳理当前项目中精排模式的目标函数实现，用于判断现有算法是否合理，以及研发后续是否需要补充优化。

本文档只说明现有实现，不要求修改接口、字段或求解流程。精排入口主要是后端 `solve_control_priority_schedule()`，该函数在以下场景被调用：

| 场景 | 触发方式 |
| --- | --- |
| 固定资源满足强制里程碑后的二次精排 | `solve_scenario()` 中池级快排满足硬节点后调用 |
| 直接按策略求解 | `schedule_strategy.strategy` 为 `control_priority`、`balanced_normal` 或 `comprehensive` 时，`solve_schedule()` 转入精排 |
| 最少资源推荐后的复核精排 | 最少资源候选结果验证或重优化时调用 |

## 2. 审核结论

### 2.1 当前实现成立的部分

当前精排目标函数主链路成立，原因如下：

1. 精排在基础可行约束之上运行，不会用目标函数替代施工逻辑、资源互斥或硬里程碑约束。
2. 目标函数按大权重表达了清晰的业务优先级：控制节点风险优先，其次控制链等待，再其次控制任务早完成，再考虑总工期、软节点、普通工程均衡和连续性。
3. 精排结果会输出 `control_priority_analysis`、`normal_balance_metrics`、`continuity_metrics` 和 `objective_breakdown`，便于前端和测试复核。
4. 资源满足分支中，池级快排结果会作为精排的 `warm_start_result`，有助于命名资源精排更快找到解。

### 2.2 需要补充说明或后续完善的部分

| 审核点 | 当前实现 | 风险或解释 | 建议 |
| --- | --- | --- | --- |
| 权重优先级 | 使用大权重单目标求和 | 表达强优先级，但不是严格数学意义的分阶段/字典序优化 | 文档中明确；如未来必须绝对优先，改为分阶段求解或证明权重上界 |
| `weighted_objective` | 输出为 `objective_days + soft_milestone_penalty` | 不是完整 CP-SAT 加权目标函数值 | 作为业务摘要保留，文档中避免误读 |
| 普通均衡任务集合 | `_build_normal_balance_terms()` 按所有 `control_level == normal` 任务建项 | 若普通任务被纳入控制链前置链，仍可能进入均衡目标 | 文档中提示；如需严格排除控制链，应调整函数入参和过滤条件 |
| 连续性目标 | 优化同结构同工艺拆分和空间资源分配秩序 | 求解后显示的跳墩、跳幅、转向等路径指标不是全部直接入目标函数 | 文档中区分“优化项”和“诊断项”；如需直接优化转场，应新增转场目标 |
| 控制节点迟延项 | 硬里程碑在 `enforce_hard_milestones=True` 时作为硬约束，不再生成迟延变量 | 固定资源满足分支中硬节点迟延不会作为惩罚项，而是被约束禁止 | 文档中说明硬节点和软控制节点的差异 |

## 3. 模型基础约束

精排目标函数只负责在可行解之间排序。进入目标函数前，模型已经建立以下约束：

| 约束 | 实现口径 |
| --- | --- |
| 任务时间 | 每个任务创建 `start`、`end`，并约束 `end = start + duration_days` |
| 命名资源选择 | 每个有候选资源的任务必须选择一个兼容命名资源 |
| 资源互斥 | 同一命名资源上的可选区间加入 `NoOverlap` |
| 施工逻辑 | 全部有效 `PrecedenceLink` 按 `FS`、`SS`、`FF`、`SF` 和 `lag_days` 加入约束 |
| 普通工程窗口 | 普通工程可受最早开始、最晚完成和最大提前完成窗口约束 |
| 普通工程工作面 | 同一桥梁/工区内普通工程并行数不超过配置值 |
| 严格资源保障 | `resource_guarantee = strict` 时，共享资源类型的普通任务需等待控制链任务完成 |
| 强制里程碑 | `enforce_hard_milestones=True` 时，硬里程碑事件时间必须不晚于目标时间 |
| 总工期 | `makespan = max(所有任务 end)` |

因此，目标函数不会允许违反资源互斥、工艺逻辑或硬里程碑的方案成为可行解。

## 4. 控制链识别

精排目标函数的控制优先项依赖 `control_chain_task_ids`。

### 4.1 控制目标任务

系统先识别控制目标任务：

| 来源 | 识别规则 |
| --- | --- |
| 任务自身控制级别 | `task.control_level` 为 `control` 或 `key` |
| 控制里程碑或硬里程碑 | 里程碑满足 `level = control`、`mode = hard` 或存在 `related_structure_ids` |
| 关联结构 | 里程碑配置 `related_structure_ids` 时，该结构下的任务纳入控制目标 |
| 项目/桥梁/工区级里程碑 | 只把范围内控制级别为 `control` 或 `key` 的任务作为广域控制目标 |

### 4.2 前置链扩展

识别出控制目标任务后，系统沿前后置关系反向追溯，把控制目标的前置任务也加入控制链。这样做的业务含义是：控制节点本身要保住，其关键前置工作也要被优先保障。

### 4.3 普通工程集合

精排中普通工程有两套相关集合：

| 集合 | 当前实现 |
| --- | --- |
| 普通工程窗口和工作面约束 | 使用 `_normal_balance_tasks()`，排除控制链任务，只保留 `control_level = normal` 的任务 |
| 普通工程均衡目标项 | `_build_normal_balance_terms()` 当前按所有 `control_level = normal` 的任务构造，不额外排除控制链 |

这意味着：如果一个普通任务因为是控制任务的前置而进入控制链，它仍可能参与普通均衡目标项。当前权重下，控制链等待和完成时间优先级更高，通常不会被普通均衡反向主导；但从语义上看，后续如果要“控制链普通前置任务完全不参与普通均衡”，需要调整 `_build_normal_balance_terms()` 的过滤口径。

## 5. 精排目标函数

当前精排目标函数是单个加权目标：

```text
minimize =
  sum(control_lateness_terms) * CONTROL_NODE_LATE_WEIGHT
+ sum(control_wait_terms) * CONTROL_RESOURCE_WAIT_WEIGHT
+ sum(control_finish_terms) * CONTROL_TASK_FINISH_WEIGHT
+ (makespan + sum(soft_penalty_terms)) * CONTROL_MAKESPAN_WEIGHT
+ sum(normal_balance_terms) * NORMAL_BALANCE_WEIGHT
+ continuity_objective
```

权重常量如下：

| 常量 | 数值 | 含义 |
| --- | ---: | --- |
| `CONTROL_NODE_LATE_WEIGHT` | `1_000_000_000` | 控制节点迟延最高优先级 |
| `CONTROL_RESOURCE_WAIT_WEIGHT` | `1_000_000` | 控制链资源等待优先级 |
| `CONTROL_TASK_FINISH_WEIGHT` | `10_000` | 控制链任务尽早完成 |
| `CONTROL_MAKESPAN_WEIGHT` | `100` | 总工期和软里程碑罚分 |
| `NORMAL_BALANCE_WEIGHT` | `10` | 普通工程均衡 |
| `SAME_STRUCTURE_CRAFT_SPLIT_WEIGHT` | `1_000` | 同结构同工艺资源拆分 |
| `SPATIAL_RESOURCE_ASSIGNMENT_WEIGHT` | `1` | 空间资源分配秩序 |

### 5.1 控制节点迟延项

构造方式：

1. 每个可匹配里程碑先计算事件时间：
   - 完成类：范围内任务最晚完成时间。
   - 开始类：范围内任务最早开始时间。
2. 若里程碑是硬节点且本次要求强制里程碑，则直接添加 `event_var <= target_offset`，不生成迟延变量。
3. 其他里程碑生成迟延变量：`lateness_var >= event_var - target_offset`。
4. 只有控制里程碑、硬里程碑或有关联结构的里程碑对应的迟延变量进入 `control_lateness_terms`。

业务含义：

- 对非硬约束的控制节点，迟延会被最高权重压制。
- 对固定资源满足分支中的强制里程碑，硬节点已经是可行性约束，而不是靠罚分“尽量满足”。

### 5.2 控制链资源等待项

构造函数：`_build_control_wait_terms()`。

该函数只针对“后续任务属于控制链”的前后置关系建立等待项。不同关系类型的等待计算如下：

| 关系 | 等待项下界 |
| --- | --- |
| `FS` | `successor.start - predecessor.end - lag_days` |
| `SS` | `successor.start - predecessor.start - lag_days` |
| `FF` | `successor.end - predecessor.end - lag_days` |
| `SF` | `successor.end - predecessor.start - lag_days` |

等待项范围为 `0..horizon`。由于施工逻辑约束已经保证后续任务不会早于允许时间，等待项表示“在满足逻辑之后额外等了多少天”。该项权重为 `1_000_000`，用于减少控制链上的资源等待和衔接空档。

### 5.3 控制链完成时间项

构造方式：

```text
control_finish_terms = [end(task) for task in control_chain_task_ids]
```

业务含义是：控制链任务在不违反硬约束和资源互斥的情况下尽量早完成。它与控制链等待项不同：

- 等待项关注控制链任务之间的衔接空档。
- 完成时间项关注控制链任务整体时间位置，避免控制任务被排到后面。

### 5.4 总工期和软里程碑罚分项

构造方式：

```text
makespan + sum(soft_penalty_terms)
```

其中：

- `makespan` 是所有任务结束时间最大值。
- `soft_penalty_terms` 是软里程碑迟延天数乘以 `penalty_per_day`。

该项乘以 `CONTROL_MAKESPAN_WEIGHT = 100`。因此它不是第一优先级，而是在控制节点、控制链等待和控制链完成时间之后压缩总体工期和软节点迟延。

### 5.5 普通工程均衡项

构造函数：`_build_normal_balance_terms()`。

实现步骤：

1. 选取所有 `control_level = normal` 的任务。
2. 按空间顺序排序，排序维度包括桥梁、工区、幅别、墩台序号、构件顺序和任务 ID。
3. 确定均衡时间窗口：
   - 起点为 `normal_earliest_start_offset`。
   - 终点优先使用 `normal_latest_finish_offset`。
   - 若未配置终点，则结合基准排程普通任务最晚结束和普通任务平均工期估算。
4. 按空间排序名次在窗口内生成目标开始时间。
5. 对每个普通任务建立偏离变量：

```text
deviation = abs(start(task) - target_start(task))
```

6. 所有偏离量求和后乘以 `NORMAL_BALANCE_WEIGHT = 10`。

业务含义：

- 普通工程不是越早越好，而是尽量按空间顺序和时间窗口均衡铺开。
- 前端展示的 `normal_balance_metrics` 是求解后按周/月桶统计任务负载，和目标函数中的 `normal_balance_terms` 不是同一计算公式。

### 5.6 资源连续性目标

连续性目标由两部分组成：

```text
continuity_objective =
  sum(split_terms) * SAME_STRUCTURE_CRAFT_SPLIT_WEIGHT
+ sum(spatial_terms) * SPATIAL_RESOURCE_ASSIGNMENT_WEIGHT
```

#### 5.6.1 同结构同工艺拆分惩罚

构造函数：`_same_structure_craft_split_terms()`。

系统按以下键分组任务：

```text
(structure_id, component_type, process_name)
```

如果同一组任务被多个资源承担，则产生拆分惩罚：

```text
split_excess = 使用资源数量 - 1
```

业务含义：同一结构、同一构件、同一工艺的多个任务尽量由更少资源连续完成，减少穿插和管理复杂度。

#### 5.6.2 空间资源分配惩罚

构造函数：`_spatial_resource_assignment_term_details()`。

实现步骤：

1. 按资源类型分组资源和任务。
2. 对同类型资源按资源编号排序，得到资源序号。
3. 对同类型任务按空间顺序排序。
4. 根据任务空间顺序为每个任务分配一个目标资源序号。
5. 如果任务实际选择的资源序号偏离目标序号，则产生惩罚：

```text
penalty = abs(actual_resource_rank - target_resource_rank)
```

业务含义：同类资源尽量按空间顺序承担相邻或对应的任务，减少资源分配混乱。

### 5.7 连续性目标和连续性指标的区别

当前直接进入目标函数的连续性项只有：

1. 同结构同工艺拆分惩罚。
2. 空间资源分配序号偏离惩罚。

求解后展示的连续性指标还包括：

| 指标 | 是否直接进入目标函数 | 说明 |
| --- | --- | --- |
| `same_structure_craft_split_count` | 是，口径接近 | 与拆分惩罚相关 |
| `jump_pier_count` | 否 | 求解后按资源路径诊断跳墩 |
| `side_switch_count` | 否 | 求解后诊断跳幅 |
| `cross_side_jump_count` | 否 | 求解后诊断跨幅跳墩 |
| `direction_reversal_count` | 否 | 求解后诊断施工方向反转 |

因此，若业务未来要求“直接减少跳墩、跳幅、转向”，需要新增与资源路径相邻任务相关的转场目标，而不只是依赖当前空间分配惩罚。

## 6. 权重优先级说明

当前实现使用大权重单目标求和，能表达强烈优先级，但它不是严格分阶段优化。

### 6.1 当前权重表达的排序

从业务意图看，优先级可理解为：

1. 控制节点不要迟延。
2. 控制链少等待。
3. 控制链尽量早完成。
4. 总工期和软节点罚分较小。
5. 普通工程更均衡。
6. 资源组织更连续。

### 6.2 不是严格字典序的原因

单目标加权求和的严格性依赖权重是否大于低优先级项的最大可能总影响。如果没有证明每个低优先级项上界，则理论上存在低优先级项总和抵消高优先级一单位变化的可能。

当前权重数值很大，工程上通常足以表达偏好，但研发和测试不应把它理解为“数学上绝对不可被低优先级项影响”的字典序优化。

### 6.3 后续严格化方向

如未来需要严格保证优先级，可选方案包括：

| 方案 | 说明 |
| --- | --- |
| 分阶段求解 | 先最小化控制迟延，固定最优值后再最小化控制等待，逐层推进 |
| 权重上界证明 | 根据任务数、horizon、资源数估算低优先级最大值，设置可证明安全的权重 |
| 输出完整目标分解 | 将完整加权目标值和每项加权前/加权后数值都写入结果，便于复核 |

## 7. 输出字段和解释

### 7.1 `objective_breakdown`

| 字段 | 当前含义 |
| --- | --- |
| `solve_mode` | 精排结果为 `control_priority`，固定资源包装后会被上层覆盖为固定资源模式 |
| `strategy` | 本次策略配置 |
| `resource_guarantee` | 资源保障模式 |
| `makespan_days` | 总工期 |
| `baseline_makespan_days` | 基准排程总工期 |
| `control_lateness_days` | 控制类或硬节点迟延天数汇总 |
| `control_resource_wait_penalty` | 控制链等待项求和值 |
| `normal_balance_penalty` | 普通工程均衡偏离求和值 |
| `soft_milestone_penalty` | 软节点迟延罚分 |
| `same_structure_craft_split_penalty` | 同结构同工艺拆分惩罚 |
| `spatial_assignment_penalty` | 空间资源分配惩罚 |
| `continuity_score` | 求解后连续性评分 |
| `normal_balance_score` | 求解后普通工程均衡评分 |
| `weighted_objective` | 当前仅为 `objective_days + soft_milestone_penalty` 的业务摘要 |

### 7.2 `stats.continuity_objective`

该字段记录连续性目标相关权重和惩罚：

| 字段 | 含义 |
| --- | --- |
| `same_structure_craft_split_penalty` | 同结构同工艺拆分惩罚求和值 |
| `spatial_assignment_penalty` | 空间资源分配惩罚求和值 |
| `primary_weight` | 通用连续性主目标权重 |
| `same_structure_craft_split_weight` | 拆分惩罚权重 |
| `spatial_resource_assignment_weight` | 空间资源分配惩罚权重 |

### 7.3 `stats.control_priority_analysis`

该字段是求解后的解释性分析，主要包括：

- 控制链任务数量。
- 控制级别任务数量分布。
- 控制节点里程碑摘要。
- 控制链涉及的瓶颈资源。
- 普通任务让位、控制任务提前等解释。
- 控制链任务清单。

它不是目标函数本身，但用于解释精排为什么调整了任务顺序。

### 7.4 `stats.normal_balance_metrics`

该字段是求解后的普通工程均衡展示指标：

- 按周或月划分时间桶。
- 统计每个桶内普通任务数量、工期和资源类型。
- 计算峰谷差对应的均衡评分。

它和目标函数中的 `normal_balance_terms` 相关，但不是同一公式。

## 8. 现有测试依据

现有测试已覆盖以下行为，可作为文档复核依据：

| 测试场景 | 预期 |
| --- | --- |
| 固定资源满足强制里程碑 | 返回控制优先和均衡精排结果，包含 `control_priority_analysis` 和 `normal_balance_metrics` |
| 控制任务与普通任务竞争同一资源 | 控制任务先排，普通任务让位 |
| 普通工程配置最早开始和工作面并行 | 普通任务不早于配置时间，且同工区并行受限 |
| 连续性指标 | 同结构同工艺拆分和资源路径指标可输出诊断 |

## 9. 研发复核清单

研发或测试复核精排目标函数时，建议逐项检查：

1. 当前策略是否确实进入 `solve_control_priority_schedule()`。
2. 控制链任务集合是否符合业务预期。
3. 强制里程碑在当前调用中是硬约束还是迟延惩罚。
4. 普通任务窗口和工作面并行约束是否被配置项影响。
5. `resource_guarantee = strict` 是否符合预期，因为它会将普通任务强制排到共享资源控制任务之后。
6. `weighted_objective` 是否被误当成完整加权目标值。
7. 连续性优化项是否能解释用户看到的跳墩、跳幅问题；若不能，应判断是否需要新增转场目标。
8. 精排结果与池级快排差异是否可以通过 `control_priority_analysis` 和 `normal_balance_metrics` 解释。
